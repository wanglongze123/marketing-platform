# 营销活动平台 环境与依赖

## 0. 说明

本文档统一三人的本地环境、依赖版本、中间件启动方式，避免「在我机器上能跑」。

**所有版本号以本文档为准，写死在根 `pom.xml` 的 `<properties>` 里，任何人不得在子模块单独指定版本。**

### 1.1 macOS 安装 JDK 21

> 以下步骤在 macOS 15 / Apple Silicon 上实测通过，已装成 **OpenJDK 21.0.12**。

**先配 Homebrew 国内源**（ghcr.io 在国内易断流，实测下到 94% 报 `PROTOCOL_ERROR`）：

```bash
export HOMEBREW_BOTTLE_DOMAIN=https://mirrors.tuna.tsinghua.edu.cn/homebrew-bottles
export HOMEBREW_API_DOMAIN=https://mirrors.tuna.tsinghua.edu.cn/homebrew-bottles/api
```

**装 JDK 21**，用 formula 而非 cask：

```bash
brew install openjdk@21
```

| | formula `openjdk@21` | cask `zulu@21` |
| --- | --- | --- |
| 安装位置 | `/opt/homebrew/opt/openjdk@21` | `/Library/Java/JavaVirtualMachines/` |
| 是否需要 sudo | **否** | 是（要输密码） |
| `java_home -v 21` 能否找到 | 否，需手写路径 | 能 |

**选 formula**：不需要密码、不碰系统目录、brew 卸载干净。代价是 keg-only，`JAVA_HOME` 要写死路径。

`~/.zshrc` 加（把上面的镜像源也一并写进去）：

```bash
# JDK 21（brew formula，keg-only，需显式加入 PATH）
export JAVA_HOME="/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"
# Homebrew 走清华镜像
export HOMEBREW_BOTTLE_DOMAIN=https://mirrors.tuna.tsinghua.edu.cn/homebrew-bottles
export HOMEBREW_API_DOMAIN=https://mirrors.tuna.tsinghua.edu.cn/homebrew-bottles/api
```

**开新终端**后验证，三条都要显示 21：

```bash
java -version                     # openjdk version "21.0.12"
javac -version                    # javac 21.0.12
mvn -version | grep "Java version"  # 21.0.12
```

第三条最容易漏 —— Maven 可能仍在用旧 JDK。

### 1.1.1 Docker Desktop（Apple Silicon 必读）

**装完先手动装 Rosetta，否则 Docker 引擎起不来。**

实测现象：Docker Desktop 界面报 `Docker Desktop is unable to start`，`docker info` 返回 `Error response from daemon`，但报错完全看不出与 Rosetta 有关。翻 `~/Library/Containers/com.docker.docker/Data/log/host/com.docker.backend.log` 才能看到真正原因：

```
installing Rosetta: Failed to install Rosetta
engine linux/virtualization-framework failed to start
```

解法：

```bash
softwareupdate --install-rosetta --agree-to-license   # 需要密码
```

装完重启 Docker Desktop 即可。

> 替代方案：Docker Desktop → Settings → General → 取消勾选 "Use Rosetta for x86_64/amd64 emulation"。但这样只有 amd64 版本的镜像会跑不动，不推荐。

### 1.1.2 Docker 镜像加速（必配）

不配的话 Testcontainers 拉 `mysql:8` 会卡到超时 —— Docker Hub 在国内基本不通。

写 `~/.docker/daemon.json`：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://docker.xuanyuan.me"
  ]
}
```

配多个互为备份 —— 国内镜像站近两年陆续关停，单个不可靠。

改完重启 Docker，验证：

```bash
docker info | grep -A3 "Registry Mirrors"    # 应列出上面三个
docker pull mysql:8                          # 实测约 1.12GB，几分钟内完成
```

**`docker info` 显示了不代表能用**，必须实际 pull 一次才算数。

> 若三个源都失效，退路是让 Testcontainers 走指定前缀：`~/.testcontainers.properties` 加 `hub.image.name.prefix=<可用的加速站>/`。

### 1.2 IDEA 配置

### 2.2 四条硬性注意

**⓪ failsafe 必须指定 `classesDirectory`（V0 实测踩坑）。**

本工程不继承 `spring-boot-starter-parent`（用自己的根 pom 当 parent），必须手动补上 starter-parent 本来会给的这项配置：

```xml
<plugin>
  <artifactId>maven-failsafe-plugin</artifactId>
  <configuration>
    <classesDirectory>${project.build.outputDirectory}</classesDirectory>
  </configuration>
</plugin>
```

缺失时 failsafe 会把 Boot repackage 后的 fat jar 放到类路径上，其类嵌在 `BOOT-INF/classes/` 下，测试 classloader 解析不到注解元数据，所有 `@SpringBootTest` 报：

```
IllegalStateException: Failed to find merged annotation for @BootstrapWith(SpringBootTestContextBootstrapper.class)
```

这个报错完全指不到真正的原因，排查成本很高。见 [spring-boot#25473](https://github.com/spring-projects/spring-boot/issues/25473)。

**不要用 `@SpringBootTest(classes=...)` 绕过它** —— 那只会把症状换成另一个报错。结构正确时空的 `@SpringBootTest` 就够用。


**① MyBatis-Plus 必须用 boot3 专属 starter。**

普通的 `mybatis-plus-boot-starter` 是给 Spring Boot 2.x 的，在 Boot 3.x 下会因 `factoryBeanObjectType` 类型不匹配抛 `IllegalArgumentException`。必须用 `mybatis-plus-spring-boot3-starter`。

**② 用 BOM 统一锁版本。**

Dubbo 会传递进来自己的 Spring 版本，与 Boot 管理的版本冲突。根 pom 的 `dependencyManagement` 同时 import `spring-boot-dependencies` 和 `dubbo-bom`，且 **Boot 的 BOM 放在前面**。

首次构建后跑一次 `mvn dependency:tree -Dverbose` 核对 `spring-core`、`spring-context` 的最终版本。

**③ 虚拟线程开启后要调连接池。**

`spring.threads.virtual.enabled=true` **从 V1 起就开启**，不留到 V3 —— 越晚开启改动面越大。

开启之后，HikariCP 的连接数不再受平台线程数天然限制：虚拟线程可以创建几万个，都去抢连接会直接打爆数据库。连接池大小必须显式设定，不能沿用默认值。

同时注意临界区用 `ReentrantLock` 而非 `synchronized` —— 虚拟线程在 `synchronized` 块内阻塞会 pin 住载体线程，抵消收益。

### 2.2.1 测试插件的分工

surefire 与 failsafe 按文件名区分，配错会导致集成测试在 `mvn test` 阶段执行（此时 Testcontainers 容器尚未就绪）或根本不执行。

| 插件 | 匹配 | 阶段 |
| --- | --- | --- |
| surefire | `*Test.java` | `mvn test` |
| failsafe | `*IT.java` | `mvn verify` |

failsafe 需绑定 `integration-test` 与 `verify` 两个 goal，否则测试失败不会让构建失败。

### 2.3 版本确认

以上版本号需在 V0 阶段首次构建时确认可用（尤其 Dubbo 与 Boot 3.2 的组合）。确认后回填精确的三位版本号到本表和 `pom.xml`，之后不再变动。

若某个组合确实不兼容，在本文档记录：原版本、问题现象、改用版本。

## 3. 中间件

### 3.1 docker-compose

`docker-compose.yml` 放仓库根目录。按阶段分 profile，避免 V1 就起一堆用不到的东西。

| 阶段 | 需要的中间件 | 启动命令 |
| --- | --- | --- |
| V1 | MySQL | `docker compose up -d mysql` |
| V2 | MySQL + Redis | `docker compose up -d mysql redis` |
| V3 | 全部 | `docker compose up -d` |

### 3.2 端口约定

| 服务 | 端口 |
| --- | --- |
| MySQL | 3306 |
| Redis | 6379 |
| RocketMQ NameServer | 9876 |
| RocketMQ Broker | 10911 |
| Nacos | 8848 |
| 应用（V1 单进程） | 8080 |
| mock-downstream | 8090 |

V3 拆服务后的端口在该阶段方案里定。

### 3.3 数据库初始化

四个库，由 Flyway 各自管理，**不手工建表**：

| 库 | 归属模块 |
| --- | --- |
| `db_activity` | mp-activity |
| `db_benefit` | mp-benefit-order |
| `db_reward` | mp-reward |
| `db_fission` | mp-fission（V3 才建） |

docker-compose 的 MySQL 挂一个初始化脚本，只负责 `CREATE DATABASE`，表结构全部走 Flyway。

**V1 实际形态**：仅配一个 `DataSource` 指向 `db_reward`，`flyway.locations: classpath:db/migration` 将全部迁移执行于该库，其余三库为空。多数据源在 V2 配置，届时上表的归属关系才真实生效。原因与改造方式见《分阶段方案》§7.3 第 8 条。

**本地库可以随便删重建**：`docker compose down -v && docker compose up -d mysql`，Flyway 会重新跑全部迁移。这也是验证迁移脚本从零可用的方式。

### 3.4 Testcontainers

集成测试不连本地 MySQL，由 Testcontainers 自己起容器。好处是每次测试环境干净，且 CI 上不需要额外配置。

首次运行会拉镜像，比较慢；之后走本地缓存。

## 4. 构建与运行

### 4.1 常用命令

| 命令 | 作用 |
| --- | --- |
| `mvn clean install -DskipTests` | 全量构建 |
| `mvn spotless:apply` | 格式化代码，**提交前必跑** |
| `mvn spotless:check` | 检查格式，CI 会跑 |
| `mvn test` | 单测 |
| `mvn verify` | 单测 + 集成测试 + 格式检查，**合入前必跑** |
| `mvn dependency:tree -Dverbose` | 排查版本冲突 |

### 4.2 启动

V1/V2 为单进程模块化单体，启动 `mp-gateway` 一个即可（其余模块以 `injvm` 在同进程内调用）。

```bash
docker compose up -d mysql
mvn -pl mp-gateway spring-boot:run
```

V3 拆服务后改为分别启动，届时补充。

### 4.3 Maven Profile

| profile | 用途 |
| --- | --- |
| `local`（默认） | 本机开发，`injvm`，连 localhost 中间件 |
| `test` | CI，Testcontainers |
| `dist` | V3 分布式，`tri` + Nacos |

配置文件按 `application-{profile}.yml` 组织，**敏感配置不进仓库**（本项目全是本地环境，暂无真实密钥；若后续有，走环境变量）。

## 5. Git 钩子

`git-build-hook-maven-plugin` 在 `mvn validate` 阶段自动把 `.githooks/` 安装为仓库钩子。

| 钩子 | 作用 |
| --- | --- |
| `commit-msg` | 校验 Conventional Commits 格式 |
| `pre-commit` | 跑 `spotless:check`（快，只查不改） |

**克隆仓库后第一件事跑 `mvn validate`**，否则钩子不生效。

本地钩子可被 `--no-verify` 绕过，因此 CI 会再校验一次。

## 6. CI

GitHub Actions，触发条件：向 `main` 提 PR、以及 push 到 `main`。

必过项：

1. `mvn spotless:check` — 格式
2. `mvn test` — 单测
3. `mvn verify` — 集成测试（Testcontainers）
4. Flyway 迁移在干净库上从零执行成功
5. commit message 格式校验

**任一不过不允许合入。**

CI 用的 JDK 同样是 21，与本地保持一致。

## 7. 环境问题排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `IllegalArgumentException` 涉及 `factoryBeanObjectType` | 用了 Boot 2.x 的 MyBatis-Plus starter | 换 `mybatis-plus-spring-boot3-starter` |
| `UnsupportedClassVersionError` | JDK 版本不对 | 确认 `mvn -version` 显示 21 |
| Flyway checksum 校验失败 | 改了已合入的迁移脚本 | 回滚该改动，另写修正脚本 |
| Testcontainers 启动超时 | Docker 未启动或在拉镜像 | 确认 Docker Desktop 运行中；首次拉镜像需耐心 |
| `spotless:check` 失败 | 没跑 `apply` | `mvn spotless:apply` 后重新提交 |
| 依赖版本诡异 | Dubbo 传递了不同的 Spring 版本 | `mvn dependency:tree -Dverbose` 定位，在根 pom 加 `<exclusion>` |
