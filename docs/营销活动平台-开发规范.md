## 1. 提交规范

### 1.1 格式

```
<type>(<scope>): <描述>

[可选正文]

[可选脚注]
```

### 1.2 type

| type | 适用范围 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构，不改变外部行为 |
| `perf` | 性能优化 |
| `test` | 测试代码 |
| `docs` | 仅文档变更 |
| `chore` | 构建、依赖、配置 |
| `style` | 格式调整（通常由 Spotless 产生） |

### 1.3 scope

取模块名：`activity` / `reward` / `fission` / `benefit` / `gateway` / `common` / `api`。跨模块变更可省略。

### 1.4 示例

```
feat(benefit): 实现支付回调与主单条件更新
fix(reward): 修正重试时重新生成 opNo 导致的重复发放
refactor(common): 抽出幂等键生成工具类
chore: 引入 Spotless 与 commit-msg 钩子
```

### 1.5 校验

- 本地：`.githooks/commit-msg` 正则校验，`mvn validate` 阶段自动安装钩子
- CI：重复校验一次，覆盖本地 `--no-verify` 绕过的情形

校验正则：

```
^(feat|fix|refactor|perf|test|docs|chore|style)(\([a-z-]+\))?: .{1,72}$
```

## 2. 分支与 PR

| 项 | 约定 |
| --- | --- |
| 主干 | `main` 受保护，禁止直接 push |
| 分支命名 | `<type>/<简述>`，如 `feat/pay-callback` |
| 合入方式 | squash merge，合入后删除分支 |
| 分支存活 | 不超过 3 天。超期表明拆分粒度过大 |
| Review | 每个 PR 至少一人 review 通过方可合入 |
| 优化型 PR | 必须独立成 PR、基于最新 `main`、不修改当前阶段正在变更的模块 |

### 2.1 PR 模板

`.github/PULL_REQUEST_TEMPLATE.md`：

```markdown
## 变更内容

## 对应阶段与条目
V?  §?.?

## 自查
- [ ] `mvn clean verify` 通过
- [ ] 新增/变更的状态迁移全部使用条件更新
- [ ] 新增的幂等键符合《开发规范》§5 两条铁律
- [ ] 新增的下游调用已处理四分类的全部分支
- [ ] 事务内无 RPC、发消息、sleep
- [ ] 新增表/字段已写 Flyway 脚本，且未修改历史脚本

## Review 结论
> 由 reviewer 填写，见《开发规范》§11.2
```

## 3. 工程结构

### 3.1 模块划分

每个 module 对应终态的一个服务。

```
marketing-platform/
├── mp-common/            结果码、四分类枚举、单号生成、幂等键工具、异常
├── mp-api/               对外接口定义（Dubbo 接口 + DTO），按服务拆子 module
│   ├── mp-api-activity/
│   ├── mp-api-reward/
│   ├── mp-api-fission/
│   ├── mp-api-benefit/
│   └── mp-api-mock/      mock 支付与 mock 供应方的契约，V3 换真实下游时整体替换
├── mp-gateway/           接入层
├── mp-activity/          公共能力：活动配置、资格决策
├── mp-reward/            公共能力：统一发奖
├── mp-fission/           玩法：裂变
├── mp-benefit-order/     玩法：权益售卖
└── mp-mock-downstream/   mock 支付、mock 供应方
```

### 3.2 依赖方向（编译期强制）

四层，依赖严格自上而下（对应《技术方案》§1.2）：

```
接入层      gateway
              ↓
玩法层      fission          benefit-order
              ↓                   ↓
公共能力层  activity / reward      │
              ↓                   ↓
下游        mock-downstream ←──────┘
```

| # | 规则 |
| --- | --- |
| 1 | 上层可依赖下层，**可跨层**（玩法层直接调下游是允许的） |
| 2 | **下层不得依赖上层** |
| 3 | **同层不互调**（`fission` 不依赖 `benefit-order`；`activity` 不依赖 `reward`） |

**「跨层向下」是允许的**：`benefit-order` 直接调 `mock-downstream` 的支付服务（不经过公共能力层），因为支付是权益售卖的玩法私有依赖，不是两玩法共用能力。同理 `reward` 调 mock 供应方。二者都是向下，不违反方向。

**典型违规**：`reward` 收到供应方回调后想通知玩法层，写成 RPC 调 `benefit-order` 的接口。这是下层调上层，必须改为发事件（V3 引入 RocketMQ 后）。

实现方式：`pom.xml` 只声明允许方向的依赖，违反时编译失败。相比 review 检查，此方式不依赖人的注意力。

`mp-common` 与 `mp-api` 是例外，可被任意模块依赖，但二者自身不依赖任何业务模块。

### 3.3 包结构

```
com.mp.<module>/
├── facade/       接口实现，参数校验、DTO ↔ 领域对象转换
├── service/impl/ 业务逻辑，事务边界只允许出现在此层
├── repository/   数据访问，Mapper 与自定义 SQL
├── entity/       数据库实体
├── enums/
├── task/         可靠任务处理器（V2 起）
└── config/
```

### 3.4 配置文件

| 项 | 约定 |
| --- | --- |
| 组织方式 | `application.yml` 放公共配置，`application-{profile}.yml` 放环境差异 |
| profile | `local`（默认，本机）/ `test`（CI，Testcontainers）/ `dist`（V3 分布式） |
| 命名 | 自定义配置一律 `mp.` 前缀，如 `mp.reward.rpc-timeout-ms` |
| 硬编码 | 超时时间、退避序列、批量大小一律走配置，不写死在代码中 |
| 敏感信息 | 不进仓库。本项目暂无真实密钥，后续如有走环境变量 |

### 3.5 Lombok

允许使用，限定以下注解：

| 允许 | 禁止 | 原因 |
| --- | --- | --- |
| `@Getter` `@Setter` | `@Data` | `@Data` 隐含 `equals`/`hashCode`，实体类上易引发意外行为 |
| `@Builder` | `@AllArgsConstructor`（public 类） | 参数顺序变更不会引发编译错误，是隐蔽的缺陷来源 |
| `@Slf4j` | `@SneakyThrows` | 绕过受检异常，异常路径不可见 |
| `@RequiredArgsConstructor` | | 用于构造器注入 |

DTO 一律 `@Getter @Setter`，不用 `@Data`。

## 4. 数据库规范

### 4.1 Flyway

| 项 | 约定 |
| --- | --- |
| 位置 | 各 module 的 `src/main/resources/db/migration/` |
| 命名 | `V<阶段><序号>__<描述>.sql`，如 `V1103__create_play_biz_record.sql` |
| 编号规则 | `V<阶段><库><序号>`，共 4 位：第 1 位阶段、第 2 位库、后 2 位序号 |
| 阶段位 | V0 用 `0`，V1 用 `1`，V2 用 `2`，V3 用 `3` |
| 库位 | `0` 活动库、`1` 权益库、`2` 发奖库、`3` 裂变库 |
| 序号位 | `01`~`89` 结构变更（建表、改表、删表）；`90`~`99` 数据（seed、回填） |
| 历史脚本 | **已合入 `main` 的脚本不得修改**。需要修正时另写新脚本；修改历史脚本会导致 checksum 校验失败，CI 拦截 |

示例：

| 文件名 | 含义 |
| --- | --- |
| `V0201__create_smoke_record.sql` | V0 · 发奖库 · 建冒烟表 |
| `V1103__create_play_biz_record.sql` | V1 · 权益库 · 建主单表 |
| `V1190__seed_sku.sql` | V1 · 权益库 · 演示数据 |
| `V1203__drop_smoke_record.sql` | V1 · 发奖库 · 删冒烟表（01/02 已被建表占用，顺延到 03） |

**每个库的迁移脚本放在拥有该库的 module 下**，各库的 Flyway 独立管理、各有自己的 `flyway_schema_history`。因此不同库之间的序号互不影响，`V0201` 与 `V1103` 不会相互干扰 —— 库位主要用于人读时快速定位。

### 4.2 建表

| 项 | 约定 |
| --- | --- |
| 引擎字符集 | `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4` |
| 主键 | 物理主键 `id BIGINT AUTO_INCREMENT`；业务主键用业务号（字符串），另建唯一索引 |
| 时间 | `DATETIME(3)`，`create_time` 默认 `CURRENT_TIMESTAMP(3)`，`update_time` 带 `ON UPDATE`。**例外**：不可变版本快照表（`activity_config_version`、`benefit_package`、`benefit_item`）只有 `create_time` —— 带 `update_time` 会暗示可原地修改，与「历史单据据快照履约」的语义冲突 |
| 金额 | `BIGINT`，单位分。禁止浮点类型 |
| 枚举 | `VARCHAR`，禁止 MySQL `ENUM` 类型（新增取值需改表） |
| 乐观锁 | 以条件更新为主；`version INT` 仅用于无自然条件可写的场景 |
| 软删除 | 仅配置类表提供 `deleted TINYINT`；流水/单据/操作记录只增不删，靠终态标记 |
| 索引命名 | `uk_xxx` / `idx_xxx` |
| 注释 | 每个字段必须有 `COMMENT`，枚举字段的注释必须列出全部取值 |

### 4.3 唯一索引与 NULL

MySQL 唯一索引**不对 `NULL` 去重** —— 多行 `NULL` 可以共存。这个特性既是陷阱也是工具，取决于该字段是否承担去重职责。

**规则一：承担去重职责的字段一律 `NOT NULL DEFAULT ''`。**

若 `op_seq` 允许为 `NULL`，`uk_biz_op` 完全失效，重复退款无法拦截。同理 `idempotent_key`、`op_no`、`revoke_no` 都必须 `NOT NULL`。

**规则二：「后填充的外部单号」保持 `NULL`，此时唯一索引只防串号、不防重复。**

`play_biz_record.trade_no` 是典型：建单时支付方还没返回单号，只能是 `NULL`；`uk_trade_no` 的作用是「同一个支付单号不能挂到两个业务单上」，而不是「每单必须有支付单号」。多行 `NULL` 共存在这里正是需要的行为 —— 若强行 `DEFAULT ''`，第二笔未回填的订单会在空串上冲突，**建单直接失败**。

同类字段：`refund_no`、`provider_order_no`。

| 字段类别 | 可空性 | 唯一索引的职责 |
| --- | --- | --- |
| 幂等键、`op_seq` | `NOT NULL DEFAULT ''` | 去重（防重复执行） |
| 后填充的外部单号 | `NULL` | 防串号（防一号多挂） |

判据：**这个字段在插入行的那一刻是否已经知道值**。知道 → `NOT NULL`；不知道 → `NULL`。

### 4.4 建表不裁字段

每个阶段建表按《技术方案》的终态 DDL **全量建**，不因「本阶段用不到」而删减字段。新增字段需要 migration，可能还要回填数据；多几个 `NULL` 字段的成本为零。

可以裁的是**表本身** —— 本阶段没有写入方的表不建。

### 4.5 跨库约束

按服务划分独立 schema：`db_activity` / `db_benefit` / `db_reward` / `db_fission`。

**禁止跨库 JOIN，禁止跨库本地事务。** 需要跨库比对时（如对账），走批量查询接口。这是把服务边界前置到开发期的手段，使 V3 拆分时业务代码零改动。

**约束的强制力依赖多数据源配置**。V1 以单数据源承载全部表，本条仅靠 review 保证；V2 配置四套数据源后由运行期拦截。在此之前，涉及跨库读的需求（对账、库存统计）一律不实现，避免留下拆库时需要重写的查询。见《分阶段方案》§7.3 第 8 条。

## 5. 单号与幂等键

> 本章是 review 的首要检查项。

### 5.1 两类标识必须分清

这是最容易混淆的一处：**业务单号**与**幂等键**规则相反。

| | 业务单号 | 幂等键 |
| --- | --- | --- |
| 例 | `play_biz_record_no`、`fulfillment_no` | `opNo`、`refundNo`、`revokeNo` |
| 作用 | 标识一个业务对象 | 标识一次操作，用于去重 |
| 要求 | **全局唯一**，每次生成必须不同 | **确定性可重算**，同一操作重试必须得到同一个值 |
| 可否用 UUID/时间戳 | **可以** | **禁止** |

**混淆的后果**：把业务单号规则套到幂等键上，重试会产生新键，唯一索引失效，出现重复发放或重复退款；反过来把幂等键规则套到业务单号上，两笔不同业务会撞号。

### 5.2 业务单号生成

统一由 `mp-common` 的 `BizNoGenerator` 生成，格式：

```
<2位前缀><UUIDv7 的 32 位十六进制，去掉连字符>

示例：BZ019852f3a7b47c9e8d1f2a3b4c5d6e7f
```

| 前缀 | 用于 |
| --- | --- |
| `BZ` | `play_biz_record_no` 业务主单 |
| `FF` | `fulfillment_no` 履约明细 |
| `FR` | `fission_relation_id` 裂变关系（V3） |

**为什么用 UUIDv7 而不是「时间戳 + 随机数」**：

- `yyyyMMddHHmmss + 8位hex` 的随机空间只有 32 bit。按生日悖论，同一秒内约 7.7 万次调用就有 50% 概率撞号 —— 压测（500 VU）与并发重试场景下这不是理论风险
- UUIDv7 前 48 bit 是毫秒时间戳、后续为随机位，**既近似有序**（降低 B+ 树页分裂，与「时间戳前缀」的初衷一致）**又有足够的随机空间**
- 时间信息仍然保留在编码内，需要时可解析出生成时间

JDK 21 无内置 UUIDv7，用 `com.github.f4b6a3:uuid-creator` 或自行实现（48 bit 毫秒 + 74 bit 随机）。

**无论生成器多可靠，唯一索引冲突都必须处理**：`BizNoGenerator` 是概率保证，`uk_biz_no` 是确定性保证。插入时捕获 `DuplicateKeyException` → 重新生成 → 重试，最多 3 次。这是「不能只靠生成器」的一般原则，与《技术方案》§6.4「唯一索引是正确性兜底、其余都是概率优化」一脉相承。

**业务单号不参与任何唯一索引之外的语义判断** —— 不要用它做排序或范围查询的依据，那是 `create_time` 与索引的职责。

### 5.3 幂等键：两条铁律

1. **`UNKNOWN` / 超时重试必须复用原键。** 任务表在建任务时即固化 `op_no`，重试只读取不重新生成。任何代码路径禁止在重试时重新生成幂等键
2. **幂等键的来源必须是外部输入或已落库的稳定值。** 禁止内部自增序列、时间戳、UUID、随机数参与

### 5.4 为什么

唯一索引作为兜底的前提是幂等键**确定性可重算**。若键由 UUID 生成，唯一索引只能拦截网络重传，无法拦截业务重入 —— 同一动作重试两次得到两个不同的键，两条记录都能插入成功。

退款是典型场景：退款序号取上游请求号而非内部计数器。内部计数器在重试时递增，产生新键、绕过唯一索引，这正是「同一订单两个 `refundNo` 退两次」的成因。

### 5.5 生成方式

**确定性字符串拼接，不使用 hash**（避免碰撞，且可读、可对账）。

| 场景 | 键 | 确定性来源 |
| --- | --- | --- |
| 创建订单 | `userId + activityId + skuId + clientReqNo` | `clientReqNo` 由客户端生成，重试保持不变 |
| 履约发奖 | `grantOpNo = bizNo + '_G_' + providerType` | 一次调用 = 一个供应方；供应方类型来自订单快照 |
| 履约查单 | 复用对应 `grantOpNo` | 读操作，直接复用发奖键 |
| 支付回调 | `tradeNo + '_' + notifySeq` | `notifySeq` 由回调携带，重传时不变。**`payStatus` 不入键** |
| 订单关闭 | `closeOpNo = bizNo + '_CLOSE'` | |
| 徒弟发奖 | `followerGrantNo = outFlowNo + '_FL'` | 确权事件流水号 |
| 师傅返奖 | `sponsorFlowNo = outFlowNo + '_SP'` | 与徒弟键同源不同后缀 |
| 退款 | `refundNo = bizNo + '_R_' + refundReqNo` | `refundReqNo` 为上游退款请求号 |
| 权益回收 | `revokeNo = bizNo + '_V_' + refundReqNo` | 与退款同源，一退一收成对，便于审计先后 |
| 人工重试 | 外部工单号 | 禁止用「已有记录数 + 1」 |

**`payStatus` 不入支付回调的幂等键**：入了键之后，`SUCCESS` 与 `CLOSED` 是两个不同的键，「先到 SUCCESS、后到 CLOSED」的乱序通知两条都能插入成功，第二条会把已支付订单关闭、错误释放库存。乱序由主单条件更新拦截，不由幂等键拦截。

### 5.6 `op_seq` 的取值

`play_op_record` 的唯一键是 `uk_biz_op(play_biz_record_no, op_type, op_seq)`。`op_seq` 是 `VARCHAR` 而非自增整数，因为它进了唯一键就必须服从铁律二。

| 操作类型 | `op_seq` | 判据 |
| --- | --- | --- |
| `CREATE_TRADE`、`CLOSE_ORDER`、`GRANT_BENEFIT`、`CREATE_REFUND`、`REVOKE_BENEFIT` | 恒为空串 `''` | 每单**至多发生一次**，第二次即重入，应被拒 |
| `PAY_CALLBACK` | `notifySeq` | 同一订单会收到**多条语义不同**的通知，各自都要留痕 |
| `REFUND_CALLBACK` | 上游通知流水号 | 同上 |
| `MANUAL_REPAIR` | 外部工单号 | 允许多次处置 |

**判据是「同类操作在一单上是否只应发生一次」，不是「这个动作重不重要」。**

`PAY_CALLBACK` 尤其容易归错类。它看起来像「支付回调只有一次」，实际上成功、失败、关单结果是三个不同的业务事件。若 `op_seq` 取空串，第二条通知会在 `uk_biz_op` 上冲突被拒，**根本执行不到条件更新那一步** —— 而乱序通知的正确拦截点恰恰是条件更新。两道闸各管一件事：

| 闸 | 拦什么 |
| --- | --- |
| `uk_biz_op(bizNo, 'PAY_CALLBACK', notifySeq)` | 同一条通知被重传 |
| 主单条件更新 `WHERE pay_status = 'WAIT_PAY'` | 不同通知乱序到达 |

**查单类操作不新建 `op_record`** —— 查单是读操作、无副作用，应更新原记录的 `retry_count` / `downstream_result` / `finish_time`，而不是每查一次插一行。

### 5.7 Review 见到即标 P0

```java
String opNo = UUID.randomUUID().toString();                    // UUID 进幂等键
String opNo = bizNo + "_" + System.currentTimeMillis();        // 时间戳进幂等键
int seq = opRecordMapper.countByBizNo(bizNo) + 1;              // 内部计数器进幂等键
if (result == UNKNOWN) { retry(generateOpNo(order)); }         // 重试时重新生成
String key = tradeNo + notifySeq + payStatus;                  // 状态进幂等键
```

## 6. 四分类结果

### 6.1 枚举

```java
public enum RetStatus { SUCCESS, FAIL, PROCESSING, UNKNOWN }
```

命名与取值以《技术方案》§4.1 为准 —— 是 `FAIL` 不是 `FAILED`，是 `RetStatus` 不是 `DownstreamResult`。四个值一一对应统一响应头的 `RetStatus` 字段，跨服务传递时不做转换。

**从 V1 起就使用此枚举**，即使 V1 的 mock 只返回 `SUCCESS`。其余三个分支写 `throw new UnsupportedOperationException("V2 实现")`，不得退化为 `boolean`。

### 6.2 `UNKNOWN` 不等于 `FAIL`

超时后下游是否已执行，调用方无从判断：

- 判为 `FAIL` → 触发不必要的补偿。若下游实际成功，则出现「已发放又被回收」或「已收款又退款」
- 直接重试 → 若下游实际成功，则重复发放
- **正确处置**：保持中间态，以**原幂等键**发起查单，由下游的幂等能力保证结果一致

**只有 `FAIL` 分支允许走失败处理。** 其余三类均不得判失败。

### 6.3 `PROCESSING` 与 `UNKNOWN` 不得合并

| 结果 | 语义 | 退避 |
| --- | --- | --- |
| `PROCESSING` | 下游已确认受理，正在处理 | 长退避 30s → 2m → 10m |
| `UNKNOWN` | 下游是否收到请求均不可知 | 短退避 1s → 5s → 30s |

二者信息量不同：`PROCESSING` 最终会有通知，高频查单是浪费；`UNKNOWN` 的资金处于悬空状态，必须尽快查证。合并成一类会导致前者被高频轮询或后者慢速收敛，两头劣化。

### 6.4 分开落库

- `op_record.status` — **本地执行态**：`INIT` / `PROCESSING` / `SUCCESS` / `FAILED` / `UNKNOWN`
- `op_record.downstream_result` — **下游四分类原值**：`SUCCESS` / `FAIL` / `PROCESSING` / `UNKNOWN`

两者分列，不合并成一个字段。排查问题时需要区分「我方对这次操作的判断」与「对方的回报」。

**注意两列的失败值拼写不同**：本地态用 `FAILED`，下游四分类用 `FAIL`。这不是笔误 —— 下游四分类必须与统一响应头 `RetStatus` 的取值逐字一致（跨服务传递时不做转换），而本地态是我方自定义的枚举。落库时不要互相套用。

### 6.5 项目内共存的五个「结果类」枚举

同类语义在不同层级用不同枚举，**取值刻意不同以防串用**。写代码前先确认自己在哪一层：

```java
public enum RetStatus    { SUCCESS, FAIL, PROCESSING, UNKNOWN }           // 跨服务四分类
public enum OpStatus     { INIT, PROCESSING, SUCCESS, FAILED, UNKNOWN }   // op_record 本地执行态
public enum GrantStatus  { NOT_START, GRANTING,                           // 主单汇总态
                           GRANT_SUCCESS, GRANT_FAILED, GRANT_UNKNOWN }
public enum ItemGrantStatus { NOT_START, GRANTING,                        // 履约明细单项态
                              SUCCESS, FAILED, UNKNOWN }
public enum PayStatus    { WAIT_PAY, CLOSING, PAY_SUCCESS, PAY_FAILED, CLOSED }
```

| 落库位置 | 枚举 | 失败值 |
| --- | --- | --- |
| `*_op_record.downstream_result` | `RetStatus` | `FAIL` |
| `*_op_record.status` | `OpStatus` | `FAILED` |
| `play_biz_record.grant_status` | `GrantStatus` | `GRANT_FAILED` |
| `benefit_fulfillment_record.grant_status` | `ItemGrantStatus` | `FAILED` |
| `play_biz_record.pay_status` | `PayStatus` | `PAY_FAILED` |

**最容易串的两处**：

1. `downstream_result` 写 `FAIL`、`status` 写 `FAILED` —— 前者必须与统一响应头逐字一致（跨服务不转换），后者是我方自定义
2. **两张表都有 `grant_status` 字段但取值不同** —— 主单的终态带 `GRANT_` 前缀（`GRANT_SUCCESS`），明细的不带（`SUCCESS`）。二者是不同层级：主单是「这一单整体发放到哪一步」，明细是「这一个权益项发放到哪一步」。用两个 Java 枚举类型隔开，让串用变成编译错误而不是运行时脏数据

### 6.5 扇出调用禁止 fail-fast

多权益项并行发放时，禁止使用「任一失败即取消其余」的语义（如 `StructuredTaskScope.ShutdownOnFailure`）。被取消的调用可能已经到达下游并执行成功，但本地既没拿到结果也没写入终态，形成「已发放却无记录」。

正确做法：`Executors.newVirtualThreadPerTaskExecutor()` + 带超时的 `invokeAll`，**所有子任务都跑完**，失败项各自落 `UNKNOWN` 并挂查单任务。

## 7. 状态变更与事务

### 7.1 一律条件更新

```sql
UPDATE play_biz_record SET pay_status = 'PAY_SUCCESS', ...
WHERE play_biz_record_no = ? AND pay_status = 'WAIT_PAY';
```

`affected_rows = 0` 即拒绝本次变更，不抛异常、不重试。这是幂等三道闸的第三道，也是乱序回调的拦截点。

**禁止**先 `SELECT` 判断状态再 `UPDATE` —— 两条语句之间存在并发窗口。

### 7.2 三子状态不合并

`pay_status` / `grant_status` / `refund_status` 三条线独立推进。展示用的 `biz_status` 由三者派生，**不落库**。

理由：「支付成功且退款中」这类组合无法由单一枚举表达；派生态落库会与三子状态不一致；三条线各自的条件更新互不干扰并发。

### 7.3 唯一索引冲突不是错误

命中 `DuplicateKeyException` 表示重复请求已被拦截，属于设计生效。处置方式：捕获后查询已有记录并返回原结果，**不打 `ERROR` 日志、不告警**。

### 7.4 事务边界硬约束

**操作记录、可靠任务的写入必须与业务状态变更处于同一本地事务。**

这是本地消息表模式的前提。破坏它就会出现「状态已变更但任务未落库」的缺口 —— 订单永远不会被履约，且没有任何机制能发现。

事务内禁止：RPC 调用、发消息、大批量库存扣减、`sleep`。

标准写法：

```
前置校验（事务外）
  ↓
@Transactional：条件更新主单 + 写 op_record + 写 task
  ↓
事务提交后：调用 RPC（由任务调度器驱动）
```

### 7.5 时间来源

**涉及跨实例比较的时间一律取数据库时间**（`NOW(3)`），不取应用服务器时间。

多实例时钟不同步时，用应用时间写入 `next_time` / `lease_expire`，会导致任务被提前领取或永不到期。

不涉及跨实例比较的时间（如日志时间戳）可用应用时间。

## 8. 日志与错误码

### 8.1 日志

| 项 | 约定 |
| --- | --- |
| 门面 | SLF4J，禁止 `System.out.println` |
| 必带字段 | `traceId` + 业务单号 |
| 脱敏 | 手机号、身份证、支付账号脱敏后打印 |
| `ERROR` | 仅用于需要人工介入的异常。唯一索引冲突、`affected_rows = 0` **不属于** |
| `WARN` | 降级、重试、下游返回 `UNKNOWN` |
| `INFO` | 关键状态迁移，必须含 from/to |

**`traceId` 的产生**：V1/V2 无 SkyWalking，由 gateway 的过滤器生成 UUID 写入 MDC，透传至 Dubbo 隐式参数，各服务从中读取并写回本地 MDC。V3 接入 SkyWalking 后改为使用其 traceId，MDC 键名保持不变。

日志格式在 `logback-spring.xml` 中统一配置，`%X{traceId}` 输出。

### 8.2 错误码

| 段 | 含义 | 处置 |
| --- | --- | --- |
| `1xxx` | 业务规则拒绝（可展示给用户） | 终态失败，不重试 |
| `4xxx` | 入参或凭证非法 | 终态失败，不重试 |
| `5xxx` | 系统异常 | 结果未知，按 `UNKNOWN` 查单收敛 |

关键码以《技术方案》§4.1 为准，本项目不新造码。

**资格决策必须区分 `1xxx` 与 `5xxx`** —— 前者是「不符合条件」，后者是「系统故障」，前端展示与重试策略完全不同。

### 8.3 异常与响应转换

三层结构，各司其职：

| 层 | 异常类型 | 处理 |
| --- | --- | --- |
| service | `BizException(code, msg)` | 业务规则不通过时抛出，携带 `1xxx`/`4xxx` 码 |
| facade | 捕获 `BizException` → 返回 `RetStatus.FAIL` + `retCode`；捕获其余异常 → `RetStatus.UNKNOWN` + `5001` | **未预期的异常一律映射为 `UNKNOWN`，不映射为 `FAIL`** |
| gateway | `@RestControllerAdvice` 统一转 `{code, message, data, traceId}` | 对外不暴露 `RetStatus` 的四分类语义 |

facade 层的映射规则是防资损的一部分：一个未捕获的 `NullPointerException` 若被映射成 `FAIL`，调用方会走补偿路径，而下游可能已经执行成功。

## 9. 测试

### 9.1 分层与命名

surefire 与 failsafe 按文件名区分，命名不对会导致集成测试在 `mvn test` 阶段被执行（此时容器尚未就绪）或根本不被执行。

| 类型 | 命名 | 执行阶段 | 依赖 |
| --- | --- | --- | --- |
| 单元测试 | `*Test.java` | `mvn test`（surefire） | 无外部依赖，纯内存 |
| 集成测试 | `*IT.java` | `mvn verify`（failsafe） | Testcontainers 起真实 MySQL |

### 9.2 必须用真实 MySQL 的场景

| 场景 | 不能用 H2 的原因 |
| --- | --- |
| 唯一索引拦截 | H2 与 MySQL 的 NULL 去重行为不一致 |
| 条件更新 `affected_rows` | mock 无法验证并发语义 |
| `SKIP LOCKED` 抢占（V2 起） | H2 不支持 `SKIP LOCKED`，无法验证抢占语义 |
| Flyway 迁移 | 必须在真实 MySQL 验证 DDL 可执行 |
| 库存原子扣减（V2 起） | 并发正确性只能在真实数据库验证 |

### 9.3 底线

- 每条阶段退出标准对应至少一个集成测试
- 幂等键与业务单号生成逻辑必须有单测
- 集成测试之间不共享数据 —— 每个测试用独立的业务单号，不依赖执行顺序

## 10. 性能相关约定

### 10.1 虚拟线程

`spring.threads.virtual.enabled=true` **从 V1 起就开启**，不留到 V3。理由：开启后需要同步调整连接池，越晚开启改动面越大。

开启后必须显式设定 HikariCP 连接数 —— 虚拟线程可创建数万个，若沿用默认连接池配置，全部去抢连接会打爆数据库。

### 10.2 避免 pin 住载体线程

临界区使用 `ReentrantLock`，不使用 `synchronized`。虚拟线程在 `synchronized` 块内阻塞会 pin 住载体线程，抵消虚拟线程的收益。

### 10.3 批量与分页

- 批量查询单次不超过 200 条，超出分批
- 分页查询必须有上界，禁止无 `LIMIT` 的全表扫描
- 循环内禁止发起 RPC 或 SQL（N+1）；需要批量时下推为单条 `IN` 查询

### 11.1 规则

- 实现者本人不做最终 review
- 使用 AI review 时**必须开新会话**，只提供 diff 与当阶段方案，不提供实现过程与自查结论
- **只写 LGTM 不算通过**，结论必须落成条目

### 11.2 Review 结论格式

写进 PR 评论：

```markdown
## Review 结论

### P0（阻塞合入）
- 无 / 或逐条列出

### P1
- ...

### 已检查未发现问题
- 重复发放：已确认 grantOpNo 由 bizNo 确定性派生，重试路径复用原键
- 超卖：本次变更未涉及库存
- ...
```

### 11.3 对抗式提示词

```
你是资深支付/营销系统架构师，正在做上线前评审。
目标不是评价代码质量，而是找出这段代码在生产环境会导致资金损失或数据错误的具体路径。

[粘贴 diff 与当阶段方案]

逐项检查，每项明确回答「有」或「无」。回答「有」时必须给出具体执行序列
（第一步发生什么、第二步发生什么、数据库最终处于什么状态）：

1. 重复发放：是否存在路径使同一业务的奖励发放两次？重试是否复用原幂等键？
2. 重复退款/回收：是否只依赖「同一退款号不重复」，而缺少「每单至多一笔退款」的约束？
3. UNKNOWN 被当作 FAIL：是否有任何一处把超时或未知结果直接按失败处理？
4. 超卖/超限购：扣减是否为数据库原子操作？是否存在「先查再扣」的并发窗口？
5. 事务边界：状态变更、操作记录、可靠任务是否处于同一事务？事务内是否有 RPC、发消息、sleep？
6. 幂等键违规：是否有 UUID、时间戳、内部计数器参与？是否有路径在重试时重新生成？
7. 状态机：是否使用条件更新？乱序到达的回调会把状态推向何处？
8. 唯一索引失效：参与唯一索引的字段是否可能为 NULL？
9. 收敛缺口：调用超时后，是否有已落库的机制保证最终收敛？还是依赖内存重试或消息必达？
10. 异常映射：未预期的异常被映射为哪一类结果？是否有被映射为 FAIL 的路径？

输出格式：级别（P0/P1/P2）、位置（文件:行号）、失败序列、最终错误状态、修复方向。
最后必须列出「已检查但未发现问题的项」及判断依据，不允许省略此节。

不要评论代码风格、命名、注释 —— 这些由 Spotless 与阿里手册插件负责。
如果找不到 P0，明确说明「未发现 P0」并列出重点排查了哪几条路径。
```
