## 1. 总体架构

### 1.1 设计原则

| 原则 | 说明 |
| --- | --- |
| 分层依赖单向 | 上层可调用下层，下层不得调用上层，同层不互调 |
| 按领域边界切分 | 服务切分依据为领域职责与依赖关系，而非数据量。当前数据规模不触发**为扩容而做的水平分片（分库分表）**、检索引擎等门槛。此处的「分库分表」指按数据量水平拆分单表，与 §3.1 按服务边界的库隔离是两个不同维度，不矛盾 |
| 公共能力下沉 | 两个玩法共用的能力（活动配置、资格决策、统一发奖）下沉为独立服务，玩法层不重复实现 |
| 事务边界内聚 | 操作记录与可靠任务必须与业务状态变更处于同一本地事务，不得跨服务拆分 |
| 开发与交付解耦 | 开发期以模块化单体形态并行推进，交付期切换为分布式部署 |

### 1.2 分层结构

系统分为四层，依赖严格自上而下。

```
┌─────────────────────────────────────────────┐
│  接入层      Gateway                          │  鉴权、限流、路由
├─────────────────────────────────────────────┤
│  玩法层      fission        benefit-order     │  各玩法私有逻辑
├─────────────────────────────────────────────┤
│  公共能力层  marketing-activity   reward       │  两玩法共用
├─────────────────────────────────────────────┤
│  下游        mock 支付      mock 供应方         │  外部系统（本期 mock）
└─────────────────────────────────────────────┘
```

请求路径始终自上而下：Gateway 接收请求并路由至某个玩法服务；玩法服务在处理过程中向下调用公共能力（判定资格调用 `marketing-activity`，发放奖励调用 `reward`）；公共能力向下调用下游系统。

该结构与《PRD》§1.2 界定的两玩法范围一致：两个玩法首尾同构——活动配置与资格决策为链路前段的公共能力，统一发奖为链路后段的公共能力，玩法私有逻辑居于两者之间。

> 说明：本图仅表达调用依赖，不表达请求时序。一次请求内「先判资格、后发奖」的顺序属于时序范畴，见第 5 章时序图。

### 1.3 服务清单与切分依据

| 层 | 服务 | 职责 | 独立切分依据 |
| --- | --- | --- | --- |
| 接入层 | gateway | 鉴权、限流、路由、统一响应 | 请求唯一入口 |
| 玩法层 | fission | 裂变组、裂变关系、好友过滤、双向发奖编排 | 裂变关系数据无自然上界，需独立存储与治理，避免膨胀特征传染其他域 |
| 玩法层 | benefit-order | 订单、支付对接、履约编排、退款、权益回收 | 资金链路，事务与逆向最复杂，独立收口 |
| 公共能力层 | marketing-activity | 活动配置、配置版本与快照、资格决策 | 两玩法共用，读多写少可缓存，独立避免重复实现 |
| 公共能力层 | reward | 统一发奖、供应方路由、查单、回收 | 两玩法共用且为唯一对接奖励供应方的出口，落地「玩法层不直接对接供应方」 |

**操作记录与可靠任务不独立成服务**：二者必须与业务状态变更处于同一本地事务，是本地消息表模式的硬约束。因此 `fission` 与 `benefit-order` 各自内置操作记录表与任务表，不抽取为公共服务。此为职责内聚要求，非重复建设。

### 1.4 并行开发策略：模块化单体 → 分布式拆分

开发期与交付期采用不同形态，代码一致，仅切换调用方式。

```
开发期（模块化单体）          交付期（分布式）
────────────────────         ────────────────────
单一 Maven 多模块工程          各 module 独立打包部署
module 间 injvm 本地调用   →   @DubboReference 经 Nacos 远程调用
单进程全链路联调              5 服务分布式启动
```

一个 Maven 多模块工程，每个 module 对应一个未来服务。模块间通过接口调用，开发期以 `injvm` 协议在同一进程内以本地方法调用执行，交付期改为 Dubbo 远程调用。该策略同时满足：接口先冻结、三人并行开发互不阻塞；联调无需启动多机；交付形态为真实分布式部署。

**分工与依赖顺序**

| 开发者 | 负责模块 | 顺序约束 |
| --- | --- | --- |
| A | marketing-activity、reward、gateway、中间件与工程骨架 | 公共底座，必须最先交付接口，另两人依赖 |
| B | fission 全链路 | 依赖 A 的公共能力接口 |
| C | benefit-order 全链路 | 依赖 A 的公共能力接口 |

公共底座由单人主导且最先产出，避免玩法层各自实现发奖与操作记录导致能力分裂。

### 1.5 消息队列定位

**一致性只用一套机制：可靠任务表。** 全局仅两类通路，职责不重叠。

| 通路 | 示例 | 机制 |
| --- | --- | --- |
| 状态变更 + 必达后续（含跨服务调用的结果收敛） | 支付回调内更新支付状态并写入履约任务；发奖 UNKNOWN 后查单收敛 | 可靠任务表（与业务状态同本地事务） |
| 跨层事件广播 | reward 收到供应方发放结果后广播，玩法层订阅更新履约态 | RocketMQ 普通消息 |

**为何跨服务一致性也用任务表而非事务消息**：事务消息保证的是「本地写库与消息投递的原子性」，即**我的消息一定送达**；但本方案的核心难题是「调用下游后**结果不确定**」——超时后下游到底执行没有，只能凭 `opNo` 主动查单。这需要一张可轮询的持久任务表，而该表天然也能充当 outbox。既然任务表无论如何都必须存在，再叠事务消息即同一职责的两套实现。故跨服务一致性 = **调用方可靠任务表 + 被调方 `opNo` 幂等 + 调用方查单收敛**（详见 §6.7）。

**RocketMQ 的职责是架构约束下的必需，而非解耦偏好**：供应方异步回调打到 `reward`（公共能力层），若由 `reward` 同步 RPC 回调玩法层，即构成**下层调上层**，违反 §1.1 单向依赖；事件是唯一不破坏依赖方向的做法。且 `reward` 被两个玩法共用，事件只需发一次，扇出天然是 pub/sub 形状。事件负责**加速**收敛，查单任务负责**保证**收敛——事件丢失不产生资损，只让收敛时间退化到查单周期。

### 1.6 部署拓扑

开发期与交付期的部署形态对应 1.4 的两种代码形态。

**初版：单机（开发与联调）**

```
┌──────────────── 机器 A ────────────────┐
│ 应用：gateway + fission + benefit-order │
│       + marketing-activity + reward     │
│       （模块化单体，injvm 本地调用）      │
│ 中间件：MySQL · Redis · RocketMQ · Nacos│
│ 下游：mock 支付 · mock 供应方            │
└─────────────────────────────────────────┘
```

服务间为本地方法调用，单进程即可全链路联调，满足业务演示，不体现分布式特性。

**终版：三机（交付、压测、演示）**

```
┌──── 机器 A：基础设施 ────┐     ┌──── 机器 B：接入 + 玩法层 ────┐
│ MySQL · Redis            │     │ gateway                       │
│ RocketMQ · Nacos         │◄────┤ fission · benefit-order       │
│ 监控：SkyWalking         │     └───────────────┬───────────────┘
│      Prometheus+Grafana  │                     │ 跨机器 RPC
│                          │     ┌───────────────▼───────────────┐
│                          │◄────┤ 机器 C：公共能力层             │
│                          │     │ marketing-activity · reward   │
└──────────────────────────┘     │ mock 支付 · mock 供应方        │
                                 └───────────────────────────────┘
```

| 机器 | 部署内容 | 依据 |
| --- | --- | --- |
| A | 全部中间件与监控 | 基础设施集中，应用无状态便于扩缩 |
| B | gateway、fission、benefit-order | 请求入口与业务编排 |
| C | marketing-activity、reward、mock 下游 | 被 B 跨机器调用，体现真实 RPC |

玩法层（B）调用公共能力层（C）为跨机器 RPC，用于验证服务发现与分布式调用。

**从单机到三机的变更范围**

```
injvm 本地调用   →  @DubboReference 经 Nacos 服务发现
localhost 中间件 →  指向机器 A 内网地址
单进程           →  5 服务独立打包，按上表分布启动
```

变更集中于配置与注解，业务代码不改，与 1.4 的模块化单体策略一致。

### 2.2 选型抉择


**① 服务化：Dubbo 3，不用 Spring Cloud**

| | 选 Dubbo | 备选 Spring Cloud |
| --- | --- | --- |
| 服务调用 | RPC，支持 injvm 本地协议 | OpenFeign（HTTP） |
| 关键能力 | **injvm → remote 改配置即切** | HTTP 调用，无本地协议 |

**决策依据**：Dubbo 把「本地调用 / 远程调用」抽象在同一套服务治理与协议层之下——`injvm`（同进程）与 `tri`（远程）**只改一个配置就能切换**，且切换后超时、重试、负载均衡等治理策略保持一致。这正是 §1.4「模块化单体 → 分布式，业务代码零改动」的实现地基。Spring Cloud 也能用「双 Profile（本地 bean / Feign 客户端）」模拟出类似效果，但那是应用层自己搭的脚手架：两套实现要各自维护，治理能力也不统一。Dubbo 的优势在于**这层抽象是框架原生提供的**，成本近乎为零。

**② 持久层：MyBatis-Plus，不用 JPA/Hibernate**

| | 选 MyBatis-Plus | 备选 JPA/Hibernate |
| --- | --- | --- |
| SQL 可见性 | SQL 即代码，可直接 review 与调优 | ORM 生成为主，native query 为逃生口 |
| 适配场景 | 复杂动态 SQL、批量下推 | 以对象为中心的 CRUD |

**决策依据**：本方案有大量**动态拼装且需精确控制执行计划**的 SQL——好友过滤的 `follower_id IN (候选页)` 批量下推（§7.1）、任务领取的 `FOR UPDATE SKIP LOCKED`（§7.3）、库存与限购的条件更新、对账的多条件扫描。JPA 当然支持 native query，但一旦主力语句都要写 native，ORM 的对象映射优势就所剩无几，反而要同时维护实体映射与手写 SQL 两套心智。选 MyBatis 是让**SQL 成为一等公民**：动态拼装用 XML/注解表达自然，`EXPLAIN` 对照实验（§7.1）也能直接落到具体语句上。

**③ 数据库：MySQL 8，测试也用真 MySQL（Testcontainers），不用 H2**

| | 选 MySQL 8 | 备选 H2/嵌入式 |
| --- | --- | --- |
| `SELECT ... FOR UPDATE SKIP LOCKED` | 支持 | **不支持** |
| 行锁/事务语义 | 生产一致 | 近似，不可信 |

**决策依据**：§7.3 可靠任务调度依赖 `SKIP LOCKED` 做多实例抢占，§6/§7.4 依赖真实行锁做库存原子扣减。H2 没有 `SKIP LOCKED`、行锁语义也不一致，用它测等于没测。因此集成测试用 **Testcontainers 起真实 MySQL 8**，验证的才是生产语义。

**④ Web 层：Spring MVC + 虚拟线程，不用 WebFlux**

| | 选 MVC + 虚拟线程 | 备选 WebFlux |
| --- | --- | --- |
| 编程模型 | 阻塞式，代码直观 | 响应式，Reactor 心智负担 |
| 高并发承接 | 虚拟线程扛住（Boot 3.2+ 官方推荐组合） | 事件循环 |

**决策依据**：§7.2 用 JDK 21 虚拟线程承接 IO 扇出。Spring Boot 3.2+ 官方推荐的高并发方案正是 **MVC（阻塞式）+ 虚拟线程**（`spring.threads.virtual.enabled=true`），既扛住并发又保持阻塞式代码的可读性，避免 WebFlux 的响应式心智负担。虚拟线程让「简单代码 + 高并发」不再二选一。

**⑤ 一致性机制：可靠任务表（本地消息表），不用分布式事务框架**

| | 选可靠任务表 | 备选 Seata AT / TCC | 备选 MQ 事务消息 |
| --- | --- | --- | --- |
| 解决的问题 | 结果不确定 → 查单收敛 | 多库事务原子回滚 | 写库与投递原子 |
| 契合度 | **匹配**——本方案的难点正是下游结果未知 | 过重，且下游是外部系统无法回滚 | 解决不了「下游到底执行没有」 |

**决策依据**：本方案的核心难题不是「消息会不会丢」，而是「调下游超时后，**它到底执行没有**」。这类不确定只能靠**原幂等号主动查单**收敛，因此必须有一张可被轮询的持久任务表；而该表与业务状态同事务提交后，天然也就是 outbox。既然任务表无论如何都要存在，再引入 Seata 或事务消息就是同一职责的两套实现——**做减法而非堆栈**。且下游供应方是外部系统，不支持全局事务回滚，AT 模式在此根本不适用。这个「不选什么以及为什么」的判断，比多接一个中间件更能说明设计取向（详见 §6.7）。

## 3. 数据库设计（DDL）

> 表结构参考行业通用的营销中台单据模型设计：以「业务单据 + 操作记录 + 可靠任务」三件套为骨架，身份统一抽象为平台 `user_id`。

### 3.1 设计约定

| 约定 | 内容 |
| --- | --- |
| 分库 | 按服务分库：`db_activity`（活动）、`db_fission`（裂变）、`db_benefit`（权益）、`db_reward`（发奖）。本期单实例多库，不分表 |
| 主键 | 业务主键用业务号（字符串），物理主键用自增 `id`，业务号加唯一索引 |
| 金额 | `bigint`，单位分 |
| 时间 | `datetime(3)` 毫秒精度；`create_time` / `update_time` 每表必备。**例外**：`activity_config_version`、`benefit_package`、`benefit_item` 是发布即冻结的**不可变版本快照**，只有 `create_time`——它们靠新增版本行而非原地修改来演进，若带 `update_time` 反而暗示可改，与「历史单据据快照履约」的语义冲突 |
| 乐观锁 | 需 CAS 更新的表带 `version int`；**以条件更新（`WHERE` 带前置状态/下界）为主，`version` 仅用于无自然条件可写的场景** |
| 幂等键 | 见 §4.1《幂等键生成规约》：一律确定性拼接，重试复用不重生成 |
| 唯一约束 | 每个「至多发生一次」的业务动作必须有对应唯一索引承载（L3 防线），见 §6.4 |
| 软删除 | **仅配置类表**（`marketing_activity`、`benefit_sku`、`benefit_package`）提供 `deleted TINYINT`；流水/单据/操作记录类表只增不删，靠终态标记 |
| 字符集 | `utf8mb4` |
| 版本管理 | Flyway 管理 DDL，三人库表变更不冲突 |

> **按服务划分独立 schema**：同一 MySQL 实例内每个服务建独立 schema，约束「禁止跨库 JOIN、禁止跨库本地事务」。成本仅为建库命名，价值是把服务边界前置到开发期，使 §1.4 的「模块化单体 → 分布式，业务代码零改动」成立。
>
> **本期不做水平分片**，因为离门槛还很远：关系表（最大表）按 1 万师傅 × 每轮 200 徒弟 × 3 轮估算约 600 万行、单行约 300B、约 2GB；单据表百万级。InnoDB 单表的经验拐点在千万行/单表数十 GB，且当前主链路查询全部走 `group_id` / 业务号等高选择性索引，无全表扫描。分片的实际触发条件是「单表持续写入压力或单表体积逼近上述量级」，本期数据量距此有一到两个数量级余量，提前分片只会引入路由与聚合成本。

**操作记录与可靠任务不集中建库**：二者必须与业务状态变更同事务，因此在 `db_fission` 与 `db_benefit` 中各建一套（`*_op_record`、`*_task`），不放入公共库。


> **`idx_expire` 为 V3 PR-5 补入**，与 `fission_relation.idx_expire` 同构。原设计只为关系表安排了过期治理（FR-F09 的字面范围就是关系），而轮次治理是 PR-2 修正唯一键时连带确定的语义——已过期但未被治理的轮次仍占着 `uk_activity_sponsor_active`，该师傅永远开不了下一轮。**两张表的过期治理必须一起做**：只做关系那一半时，师傅的下一轮开不出来，且报的是业务提示「已存在未终结的轮次」，看起来像正常拒绝。
>
> 没有该索引时，轮次治理只能退回 `idx_activity_sponsor`——其首列为 `activity_id`，而治理语句不带活动维度，等于全表扫描。`fission_group` 的行数远小于 `fission_relation`，全表扫描一时不会显形，正因如此更要在此时建好：等它显形时，加索引是在一张持续写入的表上做 DDL。

> **两道唯一键各挡一类，缺一不可**（V3 PR-2 实测修正）。原设计只有 `uk_activity_sponsor_round`，并把「并发进场不创建重复轮次」的兜底职责记在它上面 —— **该职责它承担不了**：轮次号由「读 `MAX(round_no)` 再 +1」算出，线程 A 建轮 1 提交后线程 B 读到 1 并算出轮 2，两条记录的 `round_no` 不同，唯一键根本不冲突。它实际挡的是「同一个轮次号被建两次」，而那在这套算法下本就不会发生。
>
> 挡住「同时两轮进行中」的是 `active_flag` 那道部分唯一键，机制与 `fission_relation.active_flag` 完全相同 —— **同构的不变量用同构的手段**：两张表的「进行中至多一条」是同一类约束，分别设计时容易只在其中一张上想到部分唯一键。三条终态路径（`DONE`/`EXPIRED`/`CANCEL`）必须全部释放，漏一条则该师傅永远开不了下一轮。
>
> 仅靠 Redis 锁（L2）不足以保证——锁一旦失效即破防，必须有唯一索引托底。`config_version` + `target_count` 固化配置快照，使活动改配置后存量轮次仍按进场时的规则结算（BR-C-05、BR-C-02）。

**裂变关系 `fission_relation`**（师徒关系单据）

```sql

  KEY idx_group_follower_status (group_id, follower_id, status) COMMENT '好友过滤下推：follower_id IN(...) 转 index seek（§7.1）',
  KEY idx_group_status_id (group_id, status, id) COMMENT '关系列表游标分页，避免 filesort（BR-F-22）',

) ENGINE=InnoDB COMMENT='裂变关系，膨胀表，需过期治理';
```

> **唯一键为何不含 `out_biz_no`**：NFR-C-05 的不变量是「同组同师徒**进行中**关系 ≤ 1」。`out_biz_no` 由上游传入，若编入唯一键，上游用两个不同业务号并发调用即可插出两条 JOINED 关系，同一徒弟触发两次双向发奖；且分享建 `INVITED` 时徒弟尚未加入、根本没有 `out_biz_no`。故 `out_biz_no` 降为普通列（默认空串），在 `INVITED → CONNECTED/JOINED` 时条件回填：

> ```sql
> UPDATE fission_relation SET out_biz_no = ?, status = 'JOINED'
>  WHERE group_id = ? AND follower_id = ? AND status = 'INVITED' AND out_biz_no = '';
> ```
>
> **`active_flag` 做「部分唯一」**：MySQL 无 partial index，而业务允许同一对师徒在上一轮终结后重新建立关系。故约定非终态时 `active_flag='ACTIVE'`（受唯一键约束，至多一条），进入 `DONE/EXPIRED/CANCEL` 时置为该行的 `relation_id`（天然唯一，等于把这行移出唯一性约束）。这样「进行中至多一条」由数据库保证，同时不阻塞下一轮。
>
> **三条终态路径必须全部释放，漏一条即静默失败**。若过期治理只置 `status='EXPIRED'` 而不改 `active_flag`，该行仍占着 `(group_id, follower_id, 'ACTIVE')`；该师徒下一轮分享插入时唯一键冲突，而「先插后判」模式会把冲突当**幂等命中**，静默返回那条已过期的关系——用户点了分享看似成功，实际什么也没发生，裂变复购场景全断且最难排查。
>
> 工程约束：**终态释放必须收敛到 Repository 的单一方法**（如 `terminate(relationId, targetStatus)`），禁止在各业务分支散写 `UPDATE status=...`——散落的写法迟早漏掉 `active_flag`。

**关系状态迁移表**（每个枚举值都有明确的入边与出边，无死状态）

| 状态 | 入边（触发者） | 出边（触发者） | 前置条件 |
| --- | --- | --- | --- |
| `INVITED` | 师傅分享（FissionShareInvite） | → `CONNECTED`/`JOINED`/`EXPIRED` | — |
| `CONNECTED` | 徒弟点击建联（`FissionFollowerConnect`） | → `JOINED`/`EXPIRED` | 上一状态为 `INVITED` |
| `JOINED` | 徒弟加入（FissionFollowerJoin） | → `DONE`/`EXPIRED`/`CANCEL` | 回填 `out_biz_no` |
| `DONE` | 双向发奖成功（FissionFollowerDone） | 终态 | 发奖 `op_record=SUCCESS`；**置 `active_flag=relation_id`** |
| `EXPIRED` | 过期治理任务（FR-F09） | 终态 | `expire_time < now` 且（`granting_until IS NULL OR granting_until < now`）；**置 `active_flag=relation_id`** |
| `CANCEL` | 风控 / 人工处置接口（FR-C07） | 终态 | 由 `manualRepair` 提供触发入口；**置 `active_flag=relation_id`** |

**FR-F09 过期治理批量语句**（分片 + 排除在途 + 释放唯一性，三者缺一不可）：

```sql
UPDATE fission_relation
   SET status = 'EXPIRED',
       active_flag = relation_id            -- 列到列赋值，释放唯一键
 WHERE status IN ('INVITED','CONNECTED','JOINED')
   AND expire_time < NOW(3)
   AND (granting_until IS NULL OR granting_until < NOW(3))   -- BR-F-26 + 超时兜底
   AND id BETWEEN ? AND ?                    -- 分片区间，走索引
 LIMIT 500;
-- 循环执行至 affected_rows < 500
```

**为何不用游标**：`UPDATE` 不返回被更新行的 `id`，游标无从推进；而且更新后这些行的 `status` 已变为 `EXPIRED`，**自动离开 `WHERE` 集合**，直接循环 `LIMIT 500` 到 `affected_rows < 500` 即可，天然不会重复扫描。

**分片用区间而非取模**：`id % shardTotal = shardIndex` 是函数运算，无法走索引，会退化为全表扫描。改为各实例认领 `id BETWEEN` 的连续区间（按 `MIN(id)/MAX(id)` 均分），既走索引又互不重叠。同理不加 `ORDER BY`——`expire_time <` 是范围条件，其后的 `id` 已无法用于索引排序，加了只会引入 filesort，而批量过期本就不需要有序。

**分片的身份写进任务的 `biz_no`（形如 `EXPIRE_SHARD_0_OF_1`），不由执行侧读配置**（V3 PR-5 实施时定下）。两种做法在单进程下不可区分（只有一个分片），差别在多实例：任务表的领取不分片，任一实例都可能领到任一分片的任务——执行侧若按自己的配置算区间，领到 1 号分片的实例会去扫 0 号分片的范围，两个分片的差集永远无人扫描。把区间的身份放进任务键，领取与分片即解耦。

**区间的并集必须是整个 `id` 空间**：首片下界取 `0`、末片上界取 `Long.MAX_VALUE`，而非 `MIN(id)` / `MAX(id)` 本身——后者会让「算完区间之后才插入的行」落在所有分片之外。那些行此刻尚未到期，下一轮重算区间即被覆盖，但把覆盖建立在「它们还不到期」这个时序假设上，不如让区间本身无缝。

**轮次过期治理的批量语句与上面同构**，两者必须一起做：

```sql
UPDATE fission_group
   SET status = 'EXPIRED',
       active_flag = group_id                -- 列到列赋值，释放唯一键
 WHERE status = 'RUNNING'
   AND expire_time < NOW(3)
   AND id BETWEEN ? AND ?
 LIMIT 500;
```

**它没有 `granting_until` 那一维**：发奖在途豁免是关系维度的概念（一条关系对应一次双向发奖），轮次不直接参与发奖。轮次到期即可终结——其下若有发奖在途的关系，那条关系自身被 `granting_until` 豁免，不受轮次终结影响；关系的四写也不读轮次状态，只有 `incrementProgress` 带 `status='RUNNING'` 谓词，轮次已终结时进度不再累加，而那正是正确的：过期轮次的进度没有意义。

```sql
  UNIQUE KEY uk_biz_type_op (biz_no, task_type, op_no) COMMENT '按操作单号去重，允许同业务多操作各自建任务',
```

> **`op_no` 为何 `NOT NULL DEFAULT ''`**：MySQL 唯一索引**不对 NULL 去重**，若允许为空，无下游单号的任务（如 `RELATION_EXPIRE`）可无限重复插入，唯一键不起作用。无下游单的任务用确定性本地键填充（如 `biz_no + '_EXPIRE'`）。
>
> **唯一键为何加第三维**：原 `uk_biz_type (biz_no, task_type)` 过紧——组合发放时多个权益项各自 UNKNOWN，需要多条 `QUERY_GRANT` 任务，会被唯一键拒绝；且任务进 `DONE` 后仍占用唯一键，导致对账「补建任务」被静默吞掉。以 `op_no` 作第三维后，幂等由 `op_no` 保证而非靠任务表唯一键强行收紧。
>
> `idx_sched` + `SELECT ... FOR UPDATE SKIP LOCKED` 实现多实例抢任务不重复（BR-C-22），`lease_expire` 负责跨轮次僵尸回收——**二者不可互相替代**：SKIP LOCKED 只解决同一轮扫描的并发互斥，实例宕机后遗留的 `DOING` 行必须靠租约拉回（详见 §7.3）。这也是选 MySQL 8 而非 H2 测试的原因——H2 无 `SKIP LOCKED`。

>
> **`pay_status` 的枚举调整**（对 PRD §4.3 的偏离，在此显式声明）：
>
> - **删除 `INIT`**：无任何迁移入边（下单直接建为 `WAIT_PAY`），是死枚举。不可达枚举会误导实现者写出永不执行的分支。
> - **用 `CLOSING` 而非 PRD 的 `PAYING`**：本方案未引入「支付中」回报，`PAYING` 无入边；但**关单链路确实需要一个中间态**——`closeOrder` 要先调支付方关单，这次 RPC 同样可能返回 `UNKNOWN`：此时既不能置 `CLOSED`（对方可能正在支付成功），也不能置之不理（库存一直被占）。故取一个语义准确的中间态 `CLOSING`，入边是「关单 RPC 返回 UNKNOWN」，出边是查单收敛到 `CLOSED` 或 `PAY_SUCCESS`。
>
> 超时关闭不走 `expire_time` 全表扫描，而是在 `createTrade` 事务内落一条 `CLOSE_ORDER` 可靠任务（`next_time = expire_time`）：复用同一套调度器，且与建单同事务，无「消息没发出去导致订单永不关闭」的缺口。
>
> **主单状态迁移表**（三条子状态线各自的迁移边与触发者）
>
> | 子状态 | 值 | 入边（触发者） | 出边 |
> | --- | --- | --- | --- |
> | pay | `WAIT_PAY` | createTrade | → `PAY_SUCCESS` / `PAY_FAILED` / `CLOSING` / `CLOSED` |
> | pay | `CLOSING` | 关单 RPC 返回 UNKNOWN | → `CLOSED` / `PAY_SUCCESS`（查单收敛） |
> | pay | `PAY_SUCCESS` | payCallback（金额校验通过） | 终态 |

> **`uk_biz_op` 是重复退款的真正拦截点**。仅靠 `refundNo` 唯一是不够的——它只能挡住「同一个 `refundNo` 发两次」，挡不住「同一订单用两个不同 `refundNo` 发两次」：客服在后台连点两次、各自生成一个退款号，L2 分布式锁抢不到的一方按约定「快速失败交由任务重试」，重试时再次进入，两笔退款全部受理成功。有了 `uk_biz_op`，第二笔在 `(biz_no, 'CREATE_REFUND', '')` 上冲突被拒。
>
> **`op_seq` 为何是字符串而非自增整数**：它进了唯一键，就必须服从 §4.1 铁律「禁止内部自增序列参与幂等键」。若按「已有记录数 + 1」计算，同一次操作重试两遍会得到两个不同 `op_seq`，唯一键完全不去重。故：**至多一次的操作**（`CREATE_REFUND`、`GRANT_BENEFIT`、`CLOSE_ORDER`）恒为空串；**同类可发生多次的操作**取**外部单号**——`MANUAL_REPAIR` 取工单号、`PAY_CALLBACK` 取 `notify_seq`、退款取上游 `refund_req_no`，都是同一个道理。
>
> **`PAY_CALLBACK` 为何不是「至多一次」**：同一订单会收到多条**语义不同**的支付通知（成功、失败、关单结果），它们是不同的业务事件，不是同一动作的重入，各自都要留痕。若 `op_seq` 取空串，第二条通知会在 `uk_biz_op` 上冲突被拒，**执行不到条件更新那一步**——而乱序通知的正确拦截点正是是条件更新（§5.3 ③）。故 `op_seq = notify_seq`：同一通知重传被 `uk_biz_op` 挡住（`notify_seq` 重传时不变），不同通知各留一条记录，再由条件更新裁决谁能推进状态。两道闸分工明确，不互相顶替。
>
> **查单类操作不新建 `op_record`**：`QUERY_GRANT_RESULT` 是**读操作、无副作用**，应当更新原发奖记录的 `retry_count` / `downstream_result` / `finish_time`，而不是每查一次插一行。FR-C04 要求留痕的是「有副作用的动作」；把读操作也做成单据，既撑爆表又逼出内部序列。
>
> 配合主单条件更新做第二道闸（完整谓词见 §6.4，含「先回收后退款」的 DB 强制），`affected_rows=0` 即拒绝。
>
> `update_time` 由 `ON UPDATE CURRENT_TIMESTAMP(3)` 自动维护，`idx_status_recover` 依赖它扫描「非终态且长期未更新」的记录。

**营销库存 `marketing_stock`**（平台保证 0 超卖）

```sql
CREATE TABLE marketing_stock (
  id           BIGINT      NOT NULL AUTO_INCREMENT,
  stock_key    VARCHAR(96) NOT NULL COMMENT '维度键：activity/sku/city，热点时可加 bucket 后缀分桶',
  total        BIGINT      NOT NULL,
  locked       BIGINT      NOT NULL DEFAULT 0 COMMENT '预占',
  consumed     BIGINT      NOT NULL DEFAULT 0 COMMENT '消耗',
  create_time  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  update_time  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_stock_key (stock_key)
) ENGINE=InnoDB COMMENT='营销库存';
```

> **三个动作的原子 SQL**（`affected_rows=0` 一律视为失败，杜绝负库存）：
>
> ```sql
> -- 预占（下单）
> UPDATE marketing_stock SET locked = locked + ?
>  WHERE stock_key = ? AND total - locked - consumed >= ?;
> -- 转消耗（支付成功）
> UPDATE marketing_stock SET locked = locked - ?, consumed = consumed + ?
>  WHERE stock_key = ? AND locked >= ?;
> -- 释放（关单/支付失败）
> UPDATE marketing_stock SET locked = locked - ?
>  WHERE stock_key = ? AND locked >= ?;
> ```
>
> **转消耗与释放的互斥不靠库存行本身，靠主单状态机**：两者都以「主单条件更新 `affected_rows=1`」为前提（`WAIT_PAY→PAY_SUCCESS` 与 `WAIT_PAY→CLOSED` 只有一方能赢），赢的一方才在同事务落库存任务。否则「支付回调与超时释放并发」会双双执行，产生 `locked` 为负或超卖。
>
> 此处不使用 `version` 乐观锁——余量条件 `total-locked-consumed>=?` 与下界 `locked>=?` 本身就是更强的约束，且避免了 CAS 失败重试放大热点。这也是 §3.1 中「以条件更新为主」的由来。

> 扣减：`UPDATE user_purchase_quota SET used_qty = used_qty + ? WHERE user_id=? AND activity_id=? AND sku_id=? AND period_key=? AND used_qty + ? <= limit_qty`。与库存预占在**同一本地事务**内完成，二者任一失败即整体回滚（PRD FR-B02 ⑤「原子预占营销库存与用户购买额度」）。
>
> **退款/关单后的口径必须定死，否则对账第 6 项在任何含退款的压测里都会报差异**：
>
> | 场景 | 库存 | 限购额度 |
> | --- | --- | --- |
> | 关单 / 支付失败（未成交） | `locked` 释放（`STOCK_RELEASE`） | **返还**（`QUOTA_RELEASE`）——交易未成立 |
> | 退款（已成交后反悔） | `consumed` 回补至可售 | **不返还** |
>
> 退款不返还额度的理由：限购的目的是防止单用户过度占用营销资源，若「买了再退」能刷回额度，限购即被绕过。库存则回补——商品本身可以再卖给别人。该不对称为有意设计。

**可靠任务 `benefit_task`**：结构同 `fission_task`（含 `op_no NOT NULL DEFAULT ''`、`lease_owner`、`lease_expire`、`uk_biz_type_op`、`idx_sched`），`task_type` 取 `GRANT/QUERY_GRANT/REFUND/QUERY_REFUND/REVOKE/CLOSE_ORDER/QUERY_CLOSE/STOCK_CONSUME/STOCK_RELEASE/QUOTA_RELEASE`，此处省略重复 DDL。其中 `CLOSE_ORDER` 在建单事务内落库、`next_time = expire_time`，承接订单超时关闭；`STOCK_CONSUME`/`STOCK_RELEASE` 承接从支付回调事务中移出的库存变更（见 §7.4）。

## 4. 接口设计

> 接口结构参考行业通用的营销中台契约风格：统一响应头 `RetStatus/RetCode/RetMsg`、通用子结构 `ReqUserInfo/ReqTerminalInfo/RiskInfo`、幂等字段 `OutBizNo/OutFlowNo`。裂变接口保留 `FissionFollowerDone` 等语义化命名作为调用链坐标。身份统一抽象为 `userId`。

### 4.1 统一约定

**统一响应头**

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `RetStatus` | string | `SUCCESS` / `FAIL` / `PROCESSING` / `UNKNOWN`，与 PRD 四分类一一对应 |
| `RetCode` | string | 业务响应码，见 PRD 附录 C |
| `RetMsg` | string | 内部描述，不直接展示用户 |
| `Exts` | map | 扩展，不依赖未形成契约的键 |

> **四值必须各自独立，禁止合并**（PRD §4.5、BR-C-10）。四者处置策略两两不同：
>
> | 值 | 含义 | 处置 |
> | --- | --- | --- |
> | `SUCCESS` | 下游确认成功 | 推进终态 |
> | `FAIL` | 下游确认失败 | 可安全走失败分支（补偿/退款）；**只有这一类允许判失败** |
> | `PROCESSING` | 下游已受理、处理中 | **等下游通知为主 + 长退避查单兜底**，收敛窗口长，告警阈值宽 |
> | `UNKNOWN` | 结果不确定（超时/网络异常） | **立即主动查单**，短退避、高频；**严禁按失败处理**——误判即重复发奖或重复退款 |
>
> `PROCESSING` 与 `UNKNOWN` 的区别在于「下游是否已确认收到」：前者下游明确在处理，重复调用有意义的概率低；后者连是否到达都不知道，必须用原幂等号查证。二者合并会让「等通知」的单被高频查单，或让「结果未知」的单被慢速收敛，均劣化 §6.6 的收敛表现。

**《幂等键生成规约》**（L3 唯一索引成立的前提）

唯一索引作为兜底的前提是**幂等键确定性可重算**：若键由 UUID/雪花生成，唯一索引挡住的只是网络重传，挡不住业务重入。故所有幂等键一律**确定性字符串拼接**（不用 hash，避碰撞且可读可对账），且每个键必须有一个**重试时不变的来源**：

| 操作 | 幂等键 | 确定性来源 |
| --- | --- | --- |
| 创建订单 | `user_id + activity_id + sku_id + client_req_no` | `client_req_no` 客户端生成，重试保持不变 |
| 履约发奖 | `grantOpNo = bizNo + '_G_' + providerType` | **一次 `grantReward` 调用 = 一个供应方 = 一个 opNo**；供应方类型来自订单快照 |
| 履约查单 | 复用对应 `grantOpNo` | 读操作，直接复用发奖键 |
| 徒弟发奖 | `followerGrantNo = outFlowNo + '_FL'` | 确权事件流水号 |
| 师傅返奖 | `sponsorFlowNo = outFlowNo + '_SP'` | 与徒弟键**同源不同后缀**，一次确权派生两把键 |
| 退款 | `refundNo = bizNo + '_R_' + refundReqNo` | `refund_req_no` 为**上游退款请求号**（外部输入） |
| 权益回收 | `revokeNo = bizNo + '_V_' + refundReqNo` | 与退款同源，一退一收成对，便于审计先后 |

**`grantOpNo` 的粒度定死为「一次调用 = 一个供应方」**，这决定了三处结构必须对齐：一次 `grantReward` 调用只面向单一供应方、`reward_grant_record` 一个 `opNo` 一行、明细按项挂在 `reward_grant_item`。组合权益若跨多个供应方，则**天然拆成 N 次调用、N 个幂等键、N 条查单任务**，与 `benefit_task.uk_biz_type_op` 的第三维 `op_no` 正好对上。`grantBenefit` 是订单级**编排入口**，它按供应方分组后逐组调用，本身不占 `grantOpNo`——其幂等由 `uk_biz_op(bizNo,'GRANT_BENEFIT','')` 保证。

**两条铁律**：

1. `UNKNOWN` / 超时重试**必须复用原键**；任何代码路径禁止在重试时重新生成幂等键。可靠任务表在建任务时即固化 `op_no`，重试只读不生成。
2. 幂等键的来源必须是**外部输入或已落库的稳定值**——禁止内部自增序列、时间戳、UUID 参与幂等键。特别地，退款序号取上游请求号而非内部计数器：内部计数器在重试时会递增，产生新键、绕过唯一索引，正是「同一订单两个 `refundNo` 退两次」的成因。这条铁律同样约束 `op_seq`（§3.4）——它进了唯一键，就不能是内部序列。

> **本期一单至多一笔退款**，由 `uk_biz_op(bizNo,'CREATE_REFUND','')` 强制。PRD §1.4 已将「按核销进度部分退款」划为范围外；若未来要支持，需把 `op_seq` 改为上游工单号维度并同步放开该唯一键——**属范围外，本期不做**。此处显式声明而非含糊暗示支持。

**通用请求子结构**

| 结构 | 字段 | 说明 |
| --- | --- | --- |
| `ReqUserInfo` | `userId`, `appId` | 平台统一身份（已脱敏，多身份统一由领域层完成） |
| `ReqTerminalInfo` | `appVersion`, `platform`, `deviceType`, `did`, `ip` | 终端契约，风控/规则/监控 |
| `RiskInfo` | map | 风控透传，至少含设备维度 |

**幂等字段约定**

| 字段 | 语义 |
| --- | --- |
| `OutBizNo` | 上游业务对象（一次分享/一次购买），标识业务关系 |
| `OutFlowNo` | 本次操作，写操作幂等键，落 `*_op_record.idempotent_key` |

> 二者不天然相等：一次业务关系（`OutBizNo`）下可发生多次操作（各有 `OutFlowNo`）。`UNKNOWN` 重试必须复用原 `OutFlowNo`，不得生成新流水。
>
> **对外 HTTP 与对内 Dubbo 的响应结构不同**：对外网关按 PRD §2.2 输出 `{code, message, data, traceId}`，对内 Dubbo 使用上表的 `RetStatus/RetCode/RetMsg/Exts`，由网关层做转换。`RetStatus` 的四分类语义只在服务间传递，不暴露给端。

**错误码分区与关键码**（对齐 PRD 附录 C，本方案不新造码）

| 区间 | 含义 | 处置 |
| --- | --- | --- |
| 1xxx | 业务规则拒绝 | 终态失败，不重试 |
| 4xxx | 入参/凭证非法 | 终态失败，不重试 |
| 5xxx | 系统异常 | 结果未知，按 UNKNOWN 查单收敛 |

| 码 | 场景 | 出现位置 |
| --- | --- | --- |
| `1711` | 价格不一致（凭证成交价 ≠ 服务端重算价） | `createTrade` §5.2 ④.5 |
| `1712` | 库存不足 | `createTrade` 预占失败 |
| `1713` | 超出限购额度 | `createTrade` 额度扣减失败 |
| `1731` | 支付金额/币种/商户不一致 | `payCallback` §5.3 ①.5，触发 P0 告警 |
| `1751` | 发放结果未定，暂不受理退款 | `revokeAndAdmit` §7.5，对应 `GRANTING`/`GRANT_UNKNOWN` |
| `1752` | 权益已核销/已过期，不可回收 | 供应方原子判定后回传，`revokeAndAdmit` |
| `1753` | 回收未完成，不得推进退款 | `revokeAndAdmit`、`createRefund` |
| `1754` | **实付金额未知，无法确定退款金额** | `revokeAndAdmit` 与 `createRefund` 各拦一道，见下 |
| `4732` | **供应方通知验签失败** | `providerCallback`，与支付通知的 `4731` 分开 |
| `4001` | 必填参数缺失或取值非法 | 各接口入参校验 |
| `4003` | 凭证签名非法或已过期 | `createTrade`、`FissionFollowerJoin` |
| `5001` | 下游超时/未知 | 各 RPC 调用点，映射为 `RetStatus=UNKNOWN` |

> **`1754` 归 1xxx 而非 5xxx，且必须拦在两处**（PR-7/8 review 补）。`pay_amount` 可空是 §5.6 有意留下的：`applyPaidAfterClosing` 手上没有支付通知，支付方只回答了「这笔已收款」，没说收了多少——留空等回填，因为「金额未知」是可表达的状态，而一个猜来的数不是。
>
> 退款侧**必须显式拒绝它，不能以 `order_amount` 代入**：实付 ≠ 应付时按应付退是多退或少退，而多退一笔钱要走人工追讨。归 1xxx 是因为它确定——金额补齐前重试多少次都是同一答案；判 5xxx 会让退款任务一路重试到死信。
>
> **两处各拦一道，缺一不可**：`revokeAndAdmit` 那道保证「回收不会白做」——回收不可逆，若只在退款时拒绝，权益已被收走而钱退不出去，用户既没权益也没钱；`createRefund` 那道是因为它是公开接口，不强制经过准入，且它才是真正解引用金额的地方。
>
> **不拦的后果不是报错而是静默**：直接拆箱抛 NPE 会被「异常一律映射 `UNKNOWN`」捕获，主单进 `REFUNDING`、落查单任务、回报「结果未定」，与支付方超时不可区分；而查单每轮问同一个 `refundNo`，支付方查无恒答 `UNKNOWN`，重试至死信后该单永停 `REFUNDING`。

**RPC 载体**：Dubbo 3，开发期 injvm、交付期 tri（gRPC over HTTP/2），见 §1.4。

| 方法 | 入参 | 出参 | 幂等键 |

### 4.4 fission 接口（玩法·裂变）

共 13 个接口，本期全部实现（主链路 8 个 + 分享/建联/轮次/查询 5 个）。

**`createTrade` 事务边界**（对应 PRD FR-B02、BR-B-07/B-08）：

```
前置校验：验咨询凭证签名与时效 → 校验 token 的 user/sku/activity 与请求一致
         → 服务端重算价格，assert token.dealPrice == recalcPrice，不等则 1711 拒绝且不建单
事务一：原子预占库存 + 原子扣减限购额度 + 建 play_biz_record + op_record(CREATE_TRADE)
        + benefit_task(CLOSE_ORDER, next_time=expire_time)   ← 与建单同事务，无投递缺口
事务外：调用支付下单 RPC          ← 绝不放事务内
事务二：保存 trade_no
超时：查支付结果，禁止创建第二笔支付单（BR-B-09）
```

**`payCallback` 校验与写入**（对应 FR-B03、BR-B-11/B-14/B-15）：

```
① 验签 → 定位主单
①.5 业务校验：amount == order_amount && currency && merchantId
     任一不符 → 不改任何状态 + 写 RECONCILE 记录 + P0 告警(1731)
② 幂等：tradeNo + '_' + notifySeq（status 不入幂等键）
③ 同一本地事务：
     条件更新 pay_status（WHERE pay_status='WAIT_PAY'）← 乱序通知在此被拒
   + op_record(PAY_CALLBACK)=SUCCESS + 落 pay_amount
   + benefit_task(GRANT)        ← 已收款必履约
   + benefit_task(STOCK_CONSUME) ← 库存变更移出主事务，避开单行热点
返回确认前，本地状态与可靠任务必须已落库
```

**`closeOrder` 关闭规则**（对应 FR-B04、BR-B-16/17/18）：关闭前先查支付 / 关支付单，按**四分类**分支处理——关单本身是外部 RPC，同样会返回未知：

```
调支付方关单：
  SUCCESS（确认未支付，已关闭）
      → WAIT_PAY→CLOSED，同事务落 STOCK_RELEASE + QUOTA_RELEASE
  FAILED（对方回报已支付成功）
      → 拒绝关闭，转由 payCallback / 查单推进 PAY_SUCCESS（BR-B-16）
  UNKNOWN / 超时（关单结果未定）
      → WAIT_PAY→CLOSING，同事务落 QUERY_CLOSE 任务
      → 【关键】此阶段不得释放库存与额度：结果未定就释放，
         等于把额度让给别人，而钱可能已经收了
  QUERY_CLOSE 查单收敛：
      确认未支付 → CLOSING→CLOSED，此时才落 STOCK_RELEASE + QUOTA_RELEASE
      确认已支付 → CLOSING→PAY_SUCCESS，转入正常履约（补建 GRANT 任务）
```

条件更新的三条谓词见 §6.4；`CLOSING` 长期未收敛由对账第 14 项兜底。

**`revokeAndAdmit` 回收语义**（对应 FR-B08、BR-B-30）：回收请求携带「仅当未使用时回收」，由供应方原子判定并返回实际使用态；前置查询仅作准入初筛，不作最终依据。回收成功后方可进入 `createRefund`。

## 5. 核心流程时序

> 参与方按 §1.2 四层标注：`GW` 接入层 / `FIS` `BEN` 玩法层 / `ACT` `RWD` 公共能力层 / `PAY` `PROV` 下游 mock（支付/供应方）。时序只画请求走向，依赖方向恒为上层调下层。

### 5.0 两玩法的收敛点

`FissionFollowerDone`（徒弟完成）与 `payCallback`（支付成功）占据**同一架构位置**：一个「已确认的凭证事件」触发「公共能力层发奖/履约」。二者上游不同（社交行为 vs 付款），下游收敛到 `reward.grantReward` + 可靠任务收敛，这是四层架构能让两玩法复用后段的根因。下文 5.1 与 5.3 刻意用同一套「操作记录→PROCESSING→下游→四分类收敛」骨架呈现这一点。

### 5.1 裂变·徒弟完成双向发奖（主链路）

**触发**：徒弟侧完成动作回调 `FissionFollowerDone(OutBizNo, OutFlowNo, ...)`。

```
GW        FIS(fission)                         RWD(reward)     PROV
 |  Done请求  |                                     |            |
 |----------->|                                     |            |
 |            |①凭证/签名校验(平台层)                 |            |
 |            |②分布式锁 lock:fis:rel:{group}:{follower}         |
 |            |  ← 业务键，入参即可构造                |            |
 |            |③查关系:定位唯一进行中关系               |            |
 |            |  group_id+follower_id (uk前缀)       |            |
 |            |④事务A(进入临界区即落任务):             |            |
 |            |   op_record(FOLLOWER_DONE)          |            |
 |            |   幂等键=outFlowNo, status=PROCESSING |            |
 |            |   命中uk_idempotent→直接返回原结果     |            |
 |            | + granting_until=now+收敛窗口(豁免过期) |            |
 |            | + fission_task(QUERY_GRANT, opNo)    |            |
 |            |   next_time=now+RPC超时              |            |
 |            |   ←── 此后任何时刻宕机，任务都在        |            |
 |            |⑤ grantReward(opNo=OutFlowNo+'_FL',徒弟)|            |
 |            |------------------------------------->|发奖         |
 |            |                                     |----------->|
 |            |            四分类结果 <---------------|<-----------|
 |            |⑥事务B(单事务, 四写):                   |            |
 |            |   op_record=SUCCESS                  |            |
 |            | + UPDATE relation status='DONE'      |            |
 |            |     WHERE status='JOINED'            |            |
 |            |     granting_until=NULL, active_flag=id|            |
 |            | + QUERY_GRANT 任务置 DONE             |            |
 |            | + fission_task(SPONSOR_REWARD)       |            |
 |            |     幂等键=outFlowNo+'_SP'            |            |
 |  返回SUCCESS|  ←── 四写同事务，绝无「徒弟已发师傅漏发」 |            |
 |<-----------|                                     |            |
 |            |⑦ 异步消费task → FissionSponsorDone    |            |
 |            |   grantReward(opNo=派生流水,师傅)      |            |
 |            |------------------------------------->|            |
```

**关键点**
- 组件序：关系预处理 → 徒弟发奖 → 关系后处理 → 师傅返奖（异步）。
- **④ 的任务前置是收敛率 100% 的基础**：查单任务与 `op=PROCESSING` 同事务落库，而非等发奖成功后再建。否则 RPC 发出后宕机，记录停在 `PROCESSING`、无任务、对账若只扫 `UNKNOWN` 就永久悬挂——徒弟究竟收没收到奖，无人查证。
- **⑥ 的四写必须在同一本地事务**：若「op=SUCCESS」与「关系 DONE + 师傅返奖任务」分属两个事务，中间宕机将导致徒弟已发奖、而师傅返奖任务根本不存在，师傅奖永久漏发且无重试载体（BR-F-20）。
- ⑥ 用 `WHERE status='JOINED'` 作条件更新，重复回调时 `affected_rows=0`，天然幂等（BR-F-17）；同时置 `active_flag=relation_id` 释放唯一键，允许该师徒下一轮重新建立关系。
- 徒弟发奖与师傅返奖用**不同幂等键但同源派生**：`followerGrantNo = outFlowNo + '_FL'`、`sponsorFlowNo = outFlowNo + '_SP'`，一次确权派生两把确定性键，重试时可重算（§4.1）。
- 师傅返奖走**本地消息表异步**（⑦），主链路只保证徒弟发奖同步完成，师傅返奖最终一致——避免一次请求串两次外部发奖拉长 RT。

**异常分支**
- ⑤ 返回 `UNKNOWN` → op_record 置 `UNKNOWN`，**不推进关系到 DONE**，保留 ④ 已建的查单任务，由 5.4 收敛；返回给上游 `PROCESSING`。
- ⑤ 返回 `PROCESSING` → 同上但用长退避（§6.6）。
- ⑤ 返回 `FAILED` → op_record=FAILED，`granting_until=NULL`，关系保持 JOINED，可人工/重试重入。
- **对账补位**：若 `FOLLOWER_DONE=SUCCESS` 但长时间无对应 `SPONSOR_DONE` 记录，对账第 7 项补建 `SPONSOR_REWARD` 任务（§6.8）。

### 5.2 权益·创建订单（下单预占库存）

**触发**：`createTrade(userId, activityId, skuId, quantity, clientReqNo, consultToken)`。

```
GW        BEN(benefit-order)      ACT(activity)   PAY
 |  下单请求 |                          |           |
 |--------->|①验凭证: 签名+时效           |           |
 |          |  校验 token 的 user/sku/  |           |
 |          |  activity 与请求一致       |           |
 |          |  不符→4003 拒绝，不建单     |           |
 |          |②幂等键查重                 |           |
 |          | user+activity+sku+       |           |
 |          | clientReqNo 命中→返原单    |           |
 |          |③资格决策 decideQualif.     |           |
 |          |------------------------->|           |
 |          |<-------------------------|           |
 |          |④价格/权益快照(配置版本)     |           |
 |          |④.5 价格比对:              |           |
 |          |  token.dealPrice ==      |           |
 |          |  recalcPrice ?           |           |
 |          |  不等→1711 拒绝，不建单     |           |
 |          |⑤事务A(单本地事务):         |           |
 |          |  原子预占 marketing_stock  |           |
 |          |  WHERE total-locked      |           |
 |          |       -consumed>=n       |           |
 |          |  + 扣减 user_purchase_quota|          |
 |          |    WHERE used+n<=limit   |           |
 |          |  任一 affected=0→回滚返回   |           |
 |          |  + 建 play_biz_record     |           |
 |          |    pay=WAIT_PAY, quantity |          |
 |          |  + op_record(CREATE_TRADE)|          |
 |          |  + benefit_task(CLOSE_ORDER)         |
 |          |    next_time=expire_time |           |
 |          |⑥事务外调支付下单           |           |
 |          |------------------------------------->|
 |          |            trade_no <----------------|
 |          |⑦事务B: 保存trade_no        |           |
 |  返回收银台|                          |           |
 |<---------|                          |           |
```

**关键点**
- **① 验凭证 + ④.5 价格比对缺一不可**（FR-B02 ①④、BR-B-08）：服务端重算价格后必须与凭证中的成交价**比对**，不一致一律拒绝（错误码 1711），**既不取较低价也不静默使用新价**。若只重算不比对，用户看到 9.9 元下单却成了 19.9 元，是明确的产品事故（AC-02）。
- **预占库存、扣减限购、建单同一本地事务**（事务A），是「500 并发抢 100 库存恰好成 100 单」(AC-03) 的实现：`UPDATE ... WHERE 余量>=n` 靠行锁串行化，`affected_rows` 判定成败，不用分布式锁。限购同理用 `WHERE used_qty+n<=limit_qty` 原子扣减，二者任一失败则整体回滚（FR-B02 ⑤「原子预占营销库存与用户购买额度」）。
- **`CLOSE_ORDER` 任务在建单事务内落库**，`next_time = expire_time`：与订单状态同事务提交，无「消息没发出去导致订单永不关闭、库存永不释放」的缺口。远期任务不拖慢调度——`idx_sched(status, next_time)` 的 range scan 扫到 `next_time > now()` 即停。
- ⑥ 支付下单 RPC **严禁放事务内**——外部调用可能秒级超时，占着库存行锁会雪崩。
- 超时/未拿到 `trade_no`：查支付结果，绝不创建第二笔支付单（BR-B-09）；`play_biz_record.uk_trade_no` 兜底防重复绑定。

### 5.3 权益·支付回调履约（本地消息表保证已收款必履约）

**触发**：`payCallback(tradeNo, notifySeq, status, amount, currency, merchantId)`，与 5.1 同骨架。

```
PAY       BEN(benefit-order)                    RWD/PROV
 | 支付通知 |                                        |
 |-------->|①验签+查trade_no定位主单                   |
 |         |①.5 业务校验(缺一不可):                    |
 |         |   amount == order_amount ?              |
 |         |   currency == 主单币种 ?                 |
 |         |   merchantId == 预期商户 ?               |
 |         |   任一不符→不改任何状态                    |
 |         |            +写RECONCILE记录              |
 |         |            +P0告警(1731)                |
 |         |②幂等: op_record(PAY_CALLBACK)            |
 |         |   幂等键=tradeNo+'_'+notifySeq               |
 |         |   (status 不入幂等键)                     |
 |         |③事务A(单本地事务, 条件更新+三写):          |
 |         |   UPDATE pay_status='PAY_SUCCESS'       |
 |         |    WHERE pay_status IN                  |
 |         |      ('WAIT_PAY','CLOSING')  ←状态机     |
 |         |   affected=0 → 乱序/重复，直接ACK不处理     |
 |         | + op_record=SUCCESS, pay_amount 落库      |
 |         | + benefit_task(GRANT) 落库(本地消息表)     |
 |         | + benefit_task(STOCK_CONSUME) 落库        |
 | ACK返回  |                                         |
 |<--------|  ← 本地状态+任务已落库才ACK                |
 |         |④异步消费task → grantBenefit(opNo)        |
 |         |   事务C(同一事务): op=PROCESSING          |
 |         |     + grant_status=GRANTING              |
 |         |     + QUERY_GRANT任务                    |
 |         |   提交后才事务外发RPC                      |
 |         |   逐权益项 benefit_fulfillment_record     |
 |         |--------------------------------------->|发放
 |         |          四分类结果 <-------------------|
 |         |⑤SUCCESS→grant=GRANT_SUCCESS,查单任务DONE  |
 |         |  UNKNOWN/PROCESSING→保留查单任务(见5.4)    |
```

**关键点**
- **①.5 的三项校验是不可省略的资损防线**（FR-B03 ③、BR-B-11/12）。仅验签不够：验签只证明「消息来自支付方」，不证明「金额与本单应付一致」。校验失败时**不推进任何状态**，只写对账记录并告警——绝不自动改单（AC-04）。
- **商户号校验无条件做，金额校验只对收款通知做**（V3 PR-10 后置补入实现）。两者的判据不同，位置也因此不同：
  - 金额只在收款通知里有内容可校验。`FAILED` / `CLOSED` 说的是「这笔没收成」，支付方在这两类通知里不带金额或带 0 是常态——一律要求等于应付额，会把线上所有关闭通知判成 `1731`，订单永远停在 `WAIT_PAY`，而告警里全是不存在的资损。
  - 「这笔属不属于本商户」对每一类通知都成立。**把商户校验一并写进 `PAY_SUCCESS` 分支是最自然的写法，而那样只拦收款通知**：一条来自他人商户的 `CLOSED` 通知照样能把本单关掉，库存与额度随之释放。
  - 商户校验与验签挡的也不是一回事：验签证明「消息来自持密钥方」，商户校验证明「这笔属于本商户」。**支付方多商户共用一把通知密钥、或密钥泄露后照着别家商户的单伪造，验签都会通过**，只有商户校验拦得住。期望商户号从配置读且不设代码内默认值——与 `mp.pay-notify.secret` 同一条约定（§6.2）。
- **重复通知与乱序通知是两个不同问题，必须分开治理**：
  - 重复 → 幂等键 `tradeNo + '_' + notifySeq` 拦截（`notifySeq` 由回调携带、重传时保持不变）；对应地 `play_op_record.op_seq = notify_seq`（§3.4），使 `uk_biz_op` 与幂等键同口径——**不同通知各留一条记录，同一通知重传被挡**；
  - 乱序 → **主单条件更新**拦截。反例：若把 `status` 编进幂等键（`tradeNo + '_' + status`），不同 `status` 即不同键，「先到 SUCCESS、后到 CLOSED」的乱序通知两条都能插入成功，第二条会把已支付订单关闭、错误释放库存，而履约任务仍在跑——已收款、订单显示关闭、权益照发，典型钱货不一致。用条件更新后，`WHERE pay_status='WAIT_PAY'` 使迟到的 CLOSED 通知 `affected_rows=0`，直接 ACK 丢弃。
- 「收款」与「发起履约」用**本地消息表**绑同一事务（③）：ACK 支付前，`benefit_task` 已落库，宕机重启后调度器续跑，保证已收款必履约（NFR-C-01 已收款未发奖=0 的根）。
- **库存转消耗改由 `STOCK_CONSUME` 任务异步执行**，不在回调事务内直接改库存行——500 QPS 的支付通知与 300 QPS 的下单预占争抢同一 `stock_key` 行会击穿 P99 目标（详见 §7.4）。
- ④ 的关键顺序：**`op=PROCESSING` + `grant_status=GRANTING` + 查单任务三者同一事务提交，提交后才发 RPC**。若把任务建在成功分支，RPC 发出后宕机将导致记录永久悬挂（详见 §6.5）；若 `grant_status` 与任务不同事务，则会出现「状态已 GRANTING 但无任务」的悬挂。
- ⑤ 收敛时必须**同时推进 `grant_status` 与履约明细**，而非只更新 `op_record`——查单任务收敛后调用与主流程相同的幂等后处理方法（§5.4）。
- 与 5.1 对比：`payCallback`≈`FollowerDone`，`grantBenefit`≈`grantReward` 触发——同一后段骨架，印证 §5.0 收敛点。

### 5.4 通用·UNKNOWN 收敛（可靠任务查单）

**触发**：任一下游返回 `UNKNOWN`（发奖/履约/退款皆适用）。这是防资损的通用兜底。

```
调度器(多实例)          业务服务                下游
 |①事务内领取(拆两条SQL,避免OR触发index merge):   |
 | SELECT id FROM *_task                       |
 |  WHERE status='PENDING' AND next_time<=now  |
 |  FOR UPDATE SKIP LOCKED   ← 走 idx_sched    |
 | SELECT id FROM *_task      (僵尸回收,低频)   |
 |  WHERE status='DOING' AND lease_expire<now  |
 |  FOR UPDATE SKIP LOCKED   ← 走 idx_lease    |
 | UPDATE ... SET status='DOING',              |
 |   lease_owner=?, lease_expire=now+LEASE     |
 |------------------------>|                    |
 |②按任务固化的 op_no 查单  |                    |
 |                         |------------------->|
 |                         |  真实终态 <---------|
 |③收敛:                    |                    |
 |  SUCCESS→advanceAfterGrantConfirmed(opNo)     |
 |          重放业务后处理, 任务DONE               |
 |  FAILED →op=FAILED,补偿(退款/回滚)             |
 |  PROCESSING→retry++,长退避                     |
 |  仍UNKNOWN→retry++,短退避,超阈→DEAD告警         |
```

**关键点**
- **查单收敛后必须重放业务后处理，而不是只更新操作记录**。这是个极易踩空的死角：若查单只把 `op=SUCCESS`、任务置 `DONE`，则「RPC 返回后、后处理事务提交前宕机」的单会停在——关系仍 `JOINED`、`granting_until` 未清（被过期治理豁免）、`active_flag='ACTIVE'`（唯一键被占死，该师徒下一轮永远建不了关系）、`SPONSOR_REWARD` 任务不存在（师傅奖漏发）。三个各自正确的机制叠加出一个永生的悬挂行。
  故把后处理抽成**幂等方法** `advanceAfterGrantConfirmed(opNo)`，主流程与查单任务**调同一个**，靠 `WHERE status='JOINED'` 天然幂等：

  ```java
  @Transactional
  public void advanceAfterGrantConfirmed(String opNo) {
      // 关系 DONE + granting_until=NULL + active_flag=relation_id + op SUCCESS
      // + SPONSOR_REWARD 任务；WHERE status='JOINED' 保证重复调用无副作用
  }
  ```
  权益侧同理：`queryGrantResult` 收敛后必须推进 `grant_status` 与履约明细，而非只推 `op_record`。
- **豁免过期的标志必须自带超时，且只用一个字段**：`granting_until DATETIME NULL` —— `NULL` 表示不在途，非空且未过期表示豁免，超时即允许治理接管并告警。**不设独立的 `granting_flag`**：两个字段必须同步维护，任一处漏改即失效；单字段无从不同步——与「终态释放收敛到单一方法」是同一条工程判断。
- **`SKIP LOCKED` 管同轮互斥，租约管跨轮僵尸回收，二者不可互替**（BR-C-22）：实例宕机后遗留的 `DOING` 行既不在 `PENDING` 集合、也无人持锁，只能靠 `lease_expire` 过期拉回。
- **查单用任务建立时固化的 `op_no`/`OutFlowNo`**，绝不生成新流水——否则下游视作新请求造成重复发放（资损）。
- **`PROCESSING` 与 `UNKNOWN` 退避策略不同**（§6.6）：前者下游已受理、等通知为主，用长退避；后者结果未知、需尽快查证，用短退避。
- 退避重试 + `DEAD` 死信告警：超最大重试进死信并触发 NFR-A 告警，人工介入 `MANUAL_REPAIR`，不静默丢弃。
- **对账扫描的是全部非终态**（`INIT/PROCESSING/UNKNOWN`）而非仅 `UNKNOWN`——任务与操作记录是两条独立的兜底路径，任务负责主动收敛，对账负责发现「连任务都没有」的悬挂记录（§6.8 第 4 项）。

### 5.5 裂变·好友过滤下推（性能优化对照）

**触发**：`FissionGetFriends` → `FissionFilterFriends`。这是唯一「性能实验」链路，用于 NFR-P-08~10 对照数据。

```
优化前(逐用户查):                     优化后(整页批量+下推):
 for page in 好友分页:                for page in 好友分页:
   for f in 过滤器:                     for f in 过滤器:
     for u in 当前页(N人):                if 关系过滤:
       查该用户的关系  ← 病根                SELECT follower_id
       (扫师傅全量关系)                       WHERE group_id=?
 SQL次数 = page×N                             AND follower_id IN(整页N人)
 扫描行数 = page×N×R                          AND status IN(...)
                                          # 走(group_id,follower_id,status)
                                          # N次index seek, 只扫命中行
                                      SQL次数 = page×1   (降N倍≈200×)
                                      扫描行数 = page×h  (h=命中数)
```

**收益拆成两笔**：批量化使 SQL 次数**降 N 倍（≈200×）**；下推 + 正确索引使单次扫描行数从 O(师傅全量关系 R) 降到 O(命中数 h)。

> **SQL 次数并不与 `page` 解耦**——候选集本身是分页拉取的，每页仍要执行一次下推查询；收益来自消除「页内逐用户查询」。索引必须是 `(group_id, follower_id, status)`；若用 `(group_id, status)`，`follower_id` 只能回表逐行过滤，扫描行数不降，下推就白做了。

压测在 `fission_relation` 灌百万行、单师傅千级关系下用 k6 跑对照，出 before/after 的 QPS、P99、慢查询日志与 `EXPLAIN` 的 `key`/`rows` 对照作为面试证据，NFR-P-08~10 按实测值填写。

- 退款走 `UNKNOWN` 收敛（5.4）：退款回调未达则查单，保证「重复退款=0」且「该退必退」。

## 6. 数据一致性实现

> 目标（PRD NFR-C）：资损=0、超卖=0、重复发奖=0、重复退款=0、收敛率=100%。本章把这些目标落到「四层防线 + 四分类收敛 + 对账兜底」的可实现细节，每层解决一类具体失效。

### 6.1 四层防线总览

四层不是冗余，是**各挡一类失效**，从外到内逐层收窄：

| 层 | 防线 | 挡住的失效 | 落地物 |
| --- | --- | --- | --- |
| L1 | 凭证签名校验 | 伪造/篡改请求、越权触发发奖 | Token 签名 + 时效 |
| L2 | 分布式锁 | 同一业务并发进入临界区 | Redisson 按业务键加锁 |
| L3 | 业务唯一键 + 唯一索引 | 锁失效/跨实例/重试导致的重复落单 | DB 唯一约束（最终兜底） |
| L4 | 操作记录 + 可靠任务 | 中途宕机、下游 UNKNOWN、结果丢失 | `*_op_record` + `*_task` 同事务 |

**关键认知**：L2 是「性能优化」（减少走到 L3 冲突），L3 才是**正确性兜底**。锁可能因超时/宕机/时钟失效，唯一索引不会。因此任何写操作都必须有 L3，不能只靠 L2。

### 6.2 L1 凭证签名

- 师傅 Token / 咨询凭证由平台层签发，含 `activityId + subjectId + 裂变组/SKU + 签发时间 + 过期`，HMAC 签名。
- 消费侧（`FissionFollowerJoin`/`createTrade`）先验签验时效再进业务，防止跳过资格直接触发后段发奖。
- 批量解密由公共签名 SDK 提供；密钥仅存服务端配置，不入库、不入日志。

**验签只是第一步，之后必须逐字段比对。** 签名证明的是「这张凭证由平台签发、未被篡改」，不是「它是发给当前这个请求的」——用户 A 的合法凭证放进用户 B 的请求里，验签这一关**完全通过**。两者容易被当成一件事，而少比一个字段就漏一类越权：

| 不比的字段 | 漏掉的越权 |
| --- | --- |
| `userId` | 拿他人凭证下单 |
| `activityId` / `skuId` | 拿低价商品的凭证买高价商品，且**比价照样过**——凭证价与它自己那件商品的重算价本来就相等 |
| `packageVersion` | 按旧承诺付钱、拿新内容，且**比价同样照样过**——见下 |

**`packageVersion` 必须进签名并比对，这一条最容易漏。** 权益包的内容由 `benefit_snapshot` 决定，而快照取自 `sku.benefitPackageId + sku.packageVersion`，**与活动版本无关**。换版时价格可以一分不动：

```
用户按「月卡 + 券」咨询，看到 99 元
  → 运营把 SKU 改指向新版权益包，只剩券，价格仍是 99 元
  → 用户下单：验签过（user/activity/sku 全对）、比价过（99 == 99）
  → 建单时快照读的是新版本
  → 用户按月卡+券付了钱，只拿到券
```

比价拦不住它，因为**价格没变不代表承诺没变**。判 `4003` 而非 `1711`：后者的语义是「价格不一致」（§4.1），而此处价格可能完全没变；不为此新造码，端上的处置与 `4003` 相同——重新咨询。

`configVersion` 则**不作为拒绝依据**：它是活动级版本，与权益内容无关（后者由 `packageVersion` 决定）。活动改版而价格与权益包都未变时，用户看到的承诺没有变化，据此拒绝会无故打断下单。它入签名是为了让「签发时活动是哪个版本」可审计、不可篡改。

**过期时刻必须在签名覆盖范围内，且由签发侧算定**——放在签名之外（如另作一个查询参数）等于让持有者自行决定有效期。

**载荷字段以控制字符分隔，且签发时拒绝含分隔符的值。** 用普通字符拼接时，`userId="ab" + activityId="c"` 与 `userId="a" + activityId="bc"` 会拼出同一个串、算出同一个签名，攻击者可据此挪走字段边界。

算法、有效期与密钥来源的取值见《分阶段方案》§5.6 ⑧。

### 6.3 L2 分布式锁（Redisson）

**加锁键**按业务对象最小粒度，不锁大范围：

| 场景 | 锁键 | 粒度 |
| --- | --- | --- |
| 徒弟完成 | `lock:fis:rel:{group_id}:{follower_id}` | 单关系（**业务键，非物理主键**） |
| 师傅进场开轮 | `lock:fis:sponsor:{userId}:{scene}` | 用户+场景 |
| 支付回调 | `lock:ben:trade:{tradeNo}` | 单支付单 |
| 退款回收 | `lock:ben:refund:{bizNo}` | 单主单 |

> 锁键必须用**入参就能构造出来的业务键**。若用 `relation_id`，而 `relation_id` 要先查库才知道，加锁时手上只有 `groupId/followerId`，锁键根本构造不出来——加锁就必须发生在查询之前。

```java
RLock lock = redisson.getLock(key);
if (!lock.tryLock(0, LEASE, TimeUnit.SECONDS)) {   // 不等待，快速失败
    throw new BizException(CODE_CONCURRENT);         // 上游按 PROCESSING 重试
}
try { /* 临界区: 查状态 → 判幂等 → 写库 */ }
finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();  // 锁已过期被他人持有时不可解锁
}
```

**约定**：
- `tryLock` 不阻塞等待，抢不到直接返回「处理中」，交由上游/任务重试——避免锁等待放大 RT。
- **显式传 `leaseTime` 即禁用看门狗自动续租**（Redisson 仅在不传 `leaseTime` 时启用看门狗）。发钱场景不应依赖无限续租——实例假死时锁若永不释放，业务将永久阻塞。因此这里取「可重入 + 固定租约兜底」，并要求**临界区必须显著短于 `LEASE`**。
- `unlock` 前判 `isHeldByCurrentThread()`：锁若已因超时被他人获取，直接 `unlock` 会抛 `IllegalMonitorStateException`，把业务本已成功的请求变成失败响应。
- 锁只是加速，**过期或重入的正确性由 L3+L4 保证**，绝不假设锁一定不失效。

### 6.4 L3 业务唯一键 + 唯一索引

L3 由**两类唯一索引 + 一道条件更新**共同构成，缺任何一类都会漏。

**第一类：幂等键唯一**——挡「同一个键发两次」（网络重传、任务重试）

| 操作 | 幂等键 | 唯一索引 |
| --- | --- | --- |
| 权益下单 | user+activity+sku+clientReqNo | `play_biz_record.uk_idempotent` |
| 裂变操作 | OutFlowNo | `fission_op_record.uk_idempotent` |
| 权益操作 | opNo | `play_op_record.uk_idempotent` |
| 发奖 | opNo | `reward_grant_record.uk_op_no` |
| **回收** | **revokeNo** | **`reward_revoke_record.uk_revoke_no`** |
| 任务入队 | biz_no+task_type+op_no | `*_task.uk_biz_type_op` |

**第二类：单据级唯一**——挡「同一业务语义生成了两个不同的键」

| 不变量 | 唯一索引 |
| --- | --- |
| 同组同师徒进行中关系 ≤ 1（NFR-C-05） | `fission_relation.uk_group_follower_active` |
| 同活动同师傅同轮次 ≤ 1（BR-F-02） | `fission_group.uk_activity_sponsor_round` |
| 每单每类操作至多一次（重复退款/重复履约） | `play_op_record.uk_biz_op` / `fission_op_record.uk_biz_op` |
| 同单同权益项履约明细 ≤ 1 | `benefit_fulfillment_record.uk_biz_item` |

> **这是幂等设计中最容易漏的一层**。唯一索引保护的是**幂等键的唯一性**，不是**业务动作的唯一性**——客服连点两次退款、各自生成一个 `refundNo`，第一类索引全部放行。必须用第二类索引把「每单至多一笔退款」这个业务不变量本身写进数据库。

**第三道闸：主单条件更新**——挡乱序与非法迁移，`affected_rows=0` 即拒绝

```sql
-- 退款准入（BR-B-29 未知态不退款 + BR-B-30 先回收后退款，两条都由 DB 强制）
UPDATE play_biz_record SET refund_status='REFUNDING'
 WHERE play_biz_record_no=?
   AND grant_status NOT IN ('GRANTING','GRANT_UNKNOWN')      -- 结果未定，一律拒绝
   AND ( -- 自动路径：严格
         (grant_status IN ('NOT_START','GRANT_FAILED') AND refund_status='NONE')
      OR (grant_status='GRANT_SUCCESS'                 AND refund_status='REVOKING')
      -- 人工路径：显式开口，必须带 operator，且只允许从失败态重入
      OR (refund_status='REFUND_FAILED' AND :byOperator = 1) );
--     ↑ 无权益在外从 NONE 进  ↑ 有权益在外须已 REVOKING  ↑ 人工重试留审计
-- 支付成功（拒绝乱序覆盖；CLOSING 必须放行，见下）
UPDATE play_biz_record SET pay_status='PAY_SUCCESS'
 WHERE play_biz_record_no=? AND pay_status IN ('WAIT_PAY','CLOSING');
-- 关单受理（关单 RPC 结果未定 → 中间态，此时不得释放库存）
UPDATE play_biz_record SET pay_status='CLOSING'
 WHERE play_biz_record_no=? AND pay_status='WAIT_PAY';
-- 关单确认（已支付不可关：BR-B-14）
UPDATE play_biz_record SET pay_status='CLOSED'
 WHERE play_biz_record_no=? AND pay_status IN ('WAIT_PAY','CLOSING');
```

> **`CLOSING` 必须出现在「支付成功」的准入集合里**，否则引入它反而制造资损：订单到期 → 关单 RPC 超时 → 置 `CLOSING` → 用户最后一秒付款成功 → 支付通知验签与金额校验都通过 → 条件更新命中 0 行 → 被当作乱序通知 ACK 丢弃。结果是**已收款、订单永停 `CLOSING`、履约任务不建、库存不转消耗**，且 §6.8 前十三项对账无一覆盖（第 1 项扫 `PAY_SUCCESS`、第 9 项扫 `CLOSED`）—— 第 14 项即为此缺口而设。
>
> 语义上：`CLOSING` 表示「关单结果未定」，而**支付成功通知是比查单更强的证据**，必须放行。这也是「UNKNOWN 不等于失败」在状态机层面的体现——中间态不能吞掉后到的确定结果。
>
> **通用约束：任何中间态都必须同时具备「准入谓词的入边」与「对账的一行」**，否则它就是个只进不出的黑洞。

> **「先回收后退款」必须写进 DB 谓词，不能只靠应用层调用顺序**。若准入条件写成 `refund_status IN ('NONE','REVOKING') AND grant_status NOT IN (...)`，则 `grant=GRANT_SUCCESS` 且 `refund=NONE` 的单可以直接置 `REFUNDING`，完全跳过 `REVOKING`——客服工单直接调 `createRefund`、或任何自动退款路径漏调 `revokeAndAdmit`，都会「退了钱、权益还在用户手里」。这正是本节自己立的规矩：**业务不变量要写进数据库，而不是只活在文档里**。
>
> 进入 `REFUNDING` 前还需二次校验 `benefit_fulfillment_record` 各项 `revoke_status='SUCCESS'`（或该项 `rollback_supported=0` 已按规则豁免），确保回收真的完成而非只是状态标记。
>
> **谓词写进 DB 只挡住了外部绕过，挡不住内部把状态「送」到 `REVOKING`**（PR-7/8 review 补）。`REVOKING` 是「准入已通过且回收已完成」的凭据，故**凡是能把主单置于该状态的代码路径，都必须真的确认过回收发生了**——而这样的路径不止同步链路一条：`reconcileRevoke` 是第二条。
>
> 实测的失效：主单 `grant_status='GRANT_SUCCESS'` 而履约明细里一条成功项都没有（数据不一致）时，同步链路 `revokeGranted` 判得对（打 ERROR、置未定、交人工，理由是「不静默当作无需回收，那会退掉一笔可能已发放的单」），而收敛通路的循环一次都不执行，直接落到「回收成功」——**一次回收都没发生，主单却进入「回收已完成」**，`createRefund` 的谓词随即放行。DB 那道谓词一字未改，却被从内部绕过，三道闸一道都不会响。
>
> **推论**：「结果未定」有出口的地方，那个出口就是同一条规则的第二份实现。两份必须对同一个输入给出同一个答案，且**各自都要有用例**——只验同步那条时，收敛通路可以任意宽松而不被发现。
>
> **自动路径严格、人工路径显式开口且留审计**：`REFUND_FAILED` / `REVOKE_FAILED` 是状态迁移表里标注的人工重试边，若准入谓词不给例外分支，这两条边永远 `affected_rows=0`，它们又会退化成死状态。做法不是悄悄放宽谓词，而是**用 `:byOperator` 参数把人工通道显式化**——调用方必须来自 `manualRepair` 并带 `operator`，同时写入 `play_op_record` 的 `operator/reason`（BR-C-27）。回收失败的重试同理（`REVOKE_FAILED → REVOKING`）。
>
> **人工重试禁止派生新的 `refundNo`**（BR-B-38）：`manualRepair` 只新增一条 `MANUAL_REPAIR` 审计记录（其 `op_seq` 取外部工单号，故多次重试各留一条痕），而 **`refundNo` 一律从原 `CREATE_REFUND` 记录读取**，不重新生成。否则两次人工重试就是两个退款单号，等于对支付系统发起两笔退款——这正是「幂等键重试必须复用」铁律在人工链路上的落地。

**先插后判**幂等模式（比先查后插更抗并发）：

```java
try {
    opRecordMapper.insert(op);              // status=PROCESSING
} catch (DuplicateKeyException e) {
    OpRecord exist = opRecordMapper.getByKey(idempotentKey);
    return toResult(exist);                 // 命中→回放原结果，不重复执行
}
```

唯一索引由 DB 保证原子，跨实例、锁失效、并发重试全都挡住——这是「重复发奖/重复退款=0」的最终防线。

### 6.5 L4 操作记录 + 可靠任务

**铁律：操作记录、可靠任务必须与业务状态变更在同一本地事务**。这也是 §1.3 论证「操作记录不能独立成服务」的根因——跨服务就没有本地事务，只能退化为分布式事务。

**任务必须建在副作用之前，而不是成功之后**——这是本地消息表最容易用反的地方：

```java
// 事务一：进入临界区即落任务，保护的是「失败分支」
@Transactional
public void beforeGrant(...) {
    opRecordMapper.insert(op);                   // status=PROCESSING
    taskMapper.insert(queryGrantTask);           // next_time = now + RPC超时
}                                                // ← 此后任何时刻宕机，任务都在

grantResult = rewardService.grantReward(opNo);   // 事务外 RPC

// 事务二：拿到确定结果才推进终态
@Transactional
public void onFollowerDone(...) {
    relation.setStatus(DONE);                    // 业务状态
    relationMapper.updateByJoined(relation);     // WHERE status='JOINED'
    opRecordMapper.updateSuccess(op);            // 操作记录
    taskMapper.markDone(queryGrantTask);         // 查单任务功成身退
    taskMapper.insert(sponsorRewardTask);        // 师傅返奖任务，与关系状态同事务
}
```

> **为何不能把任务建在成功分支**：若 `op_record=PROCESSING` 写入后、RPC 返回前进程被 kill，此时既没有任务、对账又只扫 `UNKNOWN`，这条记录永远不会被任何人处理——徒弟可能已收到奖、也可能没有，无人查证，收敛率 100% 直接破防。任务前置后，宕机重启即由调度器凭 `op_no` 查单收敛。
>
> **事务二的三写必须同事务**：`relation DONE` + `op SUCCESS` + `SPONSOR_REWARD 任务` 若拆成两个事务，中间崩溃则「徒弟已发奖、师傅返奖任务不存在」，师傅奖永久漏发且无任何对账项覆盖。

- **操作记录**：全生命周期留痕（INIT→PROCESSING→终态），存 `req_digest/resp_digest/downstream_no`，是查单、对账、人工修复的依据。
- **可靠任务**：本地消息表，承接异步动作（师傅返奖、履约、查单、退款、释放库存、关系过期）。调度器 `SKIP LOCKED` 抢任务 + 租约回收僵尸，退避重试，超阈进 `DEAD` 告警。

### 6.6 四分类收敛（防资损内核）

下游返回统一归四类，**`UNKNOWN` 独立于 `FAILED` 是整个方案最关键的一条**：

| 分类 | 语义 | 处置 | 退避策略 | 反例（错误做法） |
| --- | --- | --- | --- | --- |
| SUCCESS | 确定成功 | 推进终态 | — | — |
| FAILED | 确定失败，可原单重试 | 回滚/补偿/重入 | — | — |
| PROCESSING | 下游**已受理**、处理中 | 等下游通知为主，查单兜底 | **长退避**（30s→2m→10m），收敛窗口长 | 当成失败去补偿 → 重复 |
| UNKNOWN | **结果未知**（连是否到达都不知） | 保持中间态 + 原号主动查单 | **短退避**（1s→5s→30s），高频 | **当成 FAILED 退款/重发 → 资损** |

```java
// 四分类各自独立处置，禁止合并
switch (rpcResult.getRetStatus()) {
    case SUCCESS   -> { op.status = SUCCESS; advanceToTerminal(); }
    case FAIL      -> { op.status = FAILED;  compensate(); }        // 仅此分支可判失败
    case PROCESSING -> {
        op.status = PROCESSING;                  // 本地态
        op.downstreamResult = PROCESSING;        // 下游态，两者分列
        task.insert(QUERY_GRANT, opNo, LONG_BACKOFF);
    }
    case UNKNOWN   -> {
        op.status = UNKNOWN;
        op.downstreamResult = UNKNOWN;
        task.insert(QUERY_GRANT, opNo, SHORT_BACKOFF);   // 用原 opNo 查单
    }
}
return PROCESSING_TO_CALLER;   // 后两类都不给上游"失败"
```

**为什么这是内核**：把「未知」误判成「失败」→ 触发退款/重发 → 而下游实际成功 → 一笔钱赔两次 / 一个奖发两次。UNKNOWN 只能靠**原幂等号查单**收敛到真实终态，永不主观臆断。

**PROCESSING 与 UNKNOWN 为何不能合并**：二者的信息量不同——`PROCESSING` 意味着下游已确认收到并在处理，最终会有通知，高频查单只是浪费；`UNKNOWN` 意味着请求可能根本没到达、也可能已执行完，必须尽快查证。合并成一类，要么让前者被高频轮询、要么让后者慢速收敛，两头都劣化。故 `op_record` 用 `status`（本地执行态）与 `downstream_result`（下游四分类）两列分别承载，告警阈值也分开设置（§8.4）。

### 6.7 跨服务消息选型

**一致性只用一套机制：可靠任务表。** 全局仅两类消息通路：

| 通路 | 机制 | 一致性保证 |
| --- | --- | --- |
| 服务内异步 + 跨服务调用兜底（履约、师傅返奖、查单、退款、回收、关单、库存） | **可靠任务表**（`*_task`，与业务状态同事务） | 业务提交则任务必存，宕机重启续跑；跨服务调用的结果不确定由**原号查单**收敛 |
| 跨层事件广播（reward 发奖结果 → 玩法层更新履约态） | **RocketMQ 普通消息** | 至少一次投递 + 消费侧 `opNo` 幂等 + 任务兜底 |

**为何不用事务消息**：事务消息解决的是「本地写库与消息投递要么都成要么都不成」，即保证**我的消息送达**。但本方案的核心难题不是投递，而是「**调用下游后，结果不确定**」——超时后下游到底执行没有，只能凭 `opNo` 查单查证。这需要一张可被轮询的持久任务表，而任务表天然也能做 outbox。既然任务表无论如何都必须存在，再叠一层事务消息就是同一职责的两套实现。反过来若只有事务消息、没有任务表，`UNKNOWN` 将永久悬挂 → 资损。因此：**跨服务一致性 = 调用方可靠任务表 + 被调方 `opNo` 幂等 + 调用方查单收敛**，不存在需要两个服务本地事务原子提交的场景。

> **V3 的传输是进程内事件总线，发布侧只认 `GrantResultPublisher` 接口**（PR-9 实施时定下，详见《分阶段方案》§6.4 ⑤a）。V3 为单进程，V4 拆分布式后换成 RocketMQ 普通消息，`reward` 的发布代码一行不动。
>
> **这一层要验的东西与传输无关**：「事件加速、查单保证」这条分工由**消费侧的幂等与查单任务并存**决定，进程内还是跨进程都一样。真实 MQ 的语义（至少一次投递、broker 停机）属 V4 退出标准第 5 条。
>
> **消费侧的通知幂等是两道闸，不是一道**：`uk_notify(op_no, notify_seq)` 挡「同一条通知重复投递」，`result NOT IN ('SUCCESS','FAIL')` 挡「后到的结果覆盖先到的」。前者若只取 `op_no` 一维，供应方补发的第二条真实通知会被当成重传丢弃；后者若缺失，一笔已确认成功的发放会被迟到的失败通知翻掉。

**RocketMQ 承担的唯一职责是跨层事件广播**，理由是架构约束而非解耦偏好：供应方异步回调（FR-B06）打到 `reward`（公共能力层），若 `reward` 同步 RPC 回调 `benefit-order`/`fission`（玩法层），就是**下层调上层**，直接违反 §1.1 的单向依赖原则；事件是唯一不破坏依赖方向的做法。且 `reward` 被两个玩法共用，改用轮询则每个上游各写一套查单，而事件只需发一次，扇出天然是 pub/sub 形状。

> **事件负责加速收敛，查单负责保证收敛。** `QUERY_GRANT` 查单任务是 lower bound（保证最终一致，不依赖投递可靠性）；`RewardGrantResultEvent` 是 upper bound 的优化（把 P99 收敛时间从查单退避周期压到秒级）。**事件丢失不产生资损，只让收敛时间退化到查单周期**——这与「不用事务消息」是同一套逻辑：投递不可靠没关系，因为收敛不依赖投递。

**可扩展方向（本期不做）**：真实流量下裂变高峰的发奖可入队削峰，本期量级（百万行、压测目标 ≤1000 QPS、mock 下游）不触发；死信队列与 `*_task.status='DEAD'` 功能重叠，不重复建设。

### 6.8 对账兜底

防线再密也可能有漏网（下游 bug、消息丢失、人为误操作），**T+0/T+1 对账**是收口：

| # | 对账项 | 扫描条件（走索引） | 差异处置 | 幂等依据 |
| --- | --- | --- | --- | --- |
| 1 | 已收款未履约 | `pay=PAY_SUCCESS AND grant_status IN ('NOT_START','GRANTING','GRANT_UNKNOWN') AND refund_status='NONE'` 超阈（`idx_pay_grant`） | 补建 GRANT 任务 | `grantOpNo` |
| 2 | 已退款权益未回收 | `refund=REFUND_SUCCESS AND grant_status='GRANT_SUCCESS' AND 履约 revoke≠SUCCESS` | 补回收 + 告警 | `revokeNo` |
| 3 | 发奖单下游无记录 | `op=SUCCESS` 但 reward 侧查无（走 `batchQueryByOpNos`，**不跨库 JOIN**） | 告警人工核 | `opNo` |
| 4 | **非终态长期未收敛** | `op.status IN ('INIT','PROCESSING','UNKNOWN') && update_time` 超阈（`idx_status_recover`） | 强制查单，超阈进死信 | `opNo` |
| 5 | **金额一致性** | `pay_amount ≠ order_amount` 或与支付系统流水不符 | P0 告警，禁止自动改单 | — |
| 6 | **库存与单据数一致** | `consumed` vs `count(pay=PAY_SUCCESS AND refund_status<>'REFUND_SUCCESS')`；`locked` vs `count(pay='WAIT_PAY')`；以及 `locked+consumed>total` | 告警 + 产出 `stock_oversold_total` | — |
| 7 | **徒弟已发师傅未返** | `FOLLOWER_DONE=SUCCESS` 但无对应 `SPONSOR_DONE` 子记录且超阈 | 补建 SPONSOR_REWARD 任务 | `sponsorFlowNo` |
| 8 | **支付成功本地无单** | 拉取支付方对账文件（`listPaidTrades`），逐笔反查本地 `play_biz_record_no` | **P0 告警 + 人工核，禁止自动补单** | `outTradeNo` |
| 9 | **已关闭单仍占库存** | `pay=CLOSED` 但未见 `STOCK_RELEASE` 完成 | 补建释放任务 | 任务 `op_no` |
| 10 | **关系完成但轮次进度未推进** | `relation=DONE` 但 `group.progress` 未含该关系 | 重放关系后处理 | `relation_id` |
| 11 | **重复发奖检出** | 同 `biz_order_no + receiver_id + 奖励项` 存在两条 SUCCESS（`idx_receiver_activity`） | P0 告警 + 产出 `reward_duplicate_total` | — |
| 12 | **发奖成功但关系未推进** | `op_type='FOLLOWER_DONE' AND status='SUCCESS'` 但对应关系 `status<>'DONE'` 超阈 | 重放 `advanceAfterGrantConfirmed(opNo)` | `opNo`（方法幂等） |
| 13 | **发奖在途标志超时** | `granting_until IS NOT NULL AND granting_until < NOW(3)` | 强制查单收敛，仍未定则告警并允许治理接管 | `opNo` |
| 14 | **关单中间态未收敛** | `pay_status='CLOSING' AND update_time` 超阈 | 强制 QUERY_CLOSE 查单 | 任务 `op_no` |
| 15 | **限购额度与单据数一致** | 按 `(user, activity, sku, period)` 比对 `used_qty` 与 `count(quota_status='LOCKED')` | 告警 + 人工核，禁止自动改 `used_qty` | — |

> **第 1 项的谓词必须同时排除三类单**，只排除 `GRANT_SUCCESS` 会制造资损：
>
> - 排除 `GRANT_FAILED`：履约确定失败的单会走退款流程，若对账把它当「未履约」补建 GRANT 任务，就是给**已全额退款的用户再发一次权益**——钱退了、货也给了。
> - 排除 `refund_status<>'NONE'`：一旦进入退款流程（含回收中、退款中、已退款），该单不再是「待履约」。
> - 因此谓词是**白名单**（`NOT_START/GRANTING/GRANT_UNKNOWN`）而非黑名单，新增枚举时不会误放行。
>
> **「可重试」与「该重试」是两回事**（补充 §6.6 约束）：`FAILED` 允许用原幂等号重试，但**只能由业务显式发起**（用户重新下单、运营人工触发）；**对账与调度器一律不得自动重发 `FAILED`**——自动重发的前提是「结果未定」，而 `FAILED` 是已定结果。
>
> **第 2 项须限定 `grant_status='GRANT_SUCCESS'`**：`NOT_START`/`GRANT_FAILED` 的单权益从未发出，`revoke_status` 恒为 `NONE`，而这类单是自动退款的主力——不加限定会让告警全为假阳性，资损哨兵随之失效。
>
> **第 2 项还要求回收留痕的粒度与回收动作一致**（PR-7/8 review 补）：回收按 `grantOpNo` 逐供应方发起，留痕就要按 `grantOpNo` 逐笔落。写成「一单一次」时，一单跨两个供应方而其中一件已核销的情形下整笔汇总为失败，于是一条留痕都不落——**而另一件确实已经被收走了**，本项会把它判成差异并补一次回收。下游按 `revokeNo` 幂等挡得住二次回收，但**告警是假的，而本项正是资损哨兵**；人工据此处置时也会以为一件都没收回来。**留痕的判据是「这一项收没收走」，与整笔的汇总结果无关**——故回收的三个出口（成功、失败、未定）都要留痕。
>
> **第 4 项是收敛率 100% 的关键**：扫描范围必须覆盖全部非终态，而非只扫 `UNKNOWN`——`PROCESSING`/`INIT` 同样可能因宕机悬挂。凡「非终态 + 超时未更新」一律强制查单。
>
> **跨库对账不做 JOIN**：`db_benefit` 与 `db_reward` 的比对由对账任务分批拉取 `reward.batchQueryByOpNos` 在内存比对，遵守 §3.1「禁止跨库 JOIN」。
>
> **第 3 项的扫描集合是「已发放成功」的单，不是「未发完」的单**（V3 PR-10 review 修）：本项的判据是「平台记着已发成功、下游却查无」，若复用第 1 项的扫描（`grant_status IN ('NOT_START','GRANTING','GRANT_UNKNOWN')`），两个集合几乎不相交——它只会在单子还没发完时去比对下游，而那种单本就没有发奖记录，查无是正常的，于是**该项近乎空转**。
>
> **第 8 项的处置由「补记主单 + 建履约任务」降级为只告警**（V3 PR-10 后置实施）：支付对账文件只有 `outTradeNo` / `tradeNo` / 金额三个字段——**支付方不知道这笔钱对应哪个活动、哪个 SKU、买了几份**。补记主单需要 `activity_id` / `sku_id` / `price_snapshot` / `benefit_snapshot` 一整套业务数据，全都只能填占位值，而**凭占位值造出来的单会被后续履约当成真单发奖**：那是一笔查不到来源的发放，比「本地无单」本身更糟——后者只是一笔待人工核对的收款。判断与第 3 项「不自动补发」、第 5 项「禁止自动改单」同源：**正确值取决于历史，猜不出来就只告警**。
>
> **第 8 项是十五项里唯一「从支付方往平台看」的一项**，其余全是拿本地的单去比对下游。方向反过来才能发现**平台自身没有任何记录的那笔单**——建单事务提交后、支付通知到达前进程崩溃，或通知永久丢失，本地没有任何线索可查，前七项一条都覆盖不到它。
>
> **第 5 项补时间下界**（V3 PR-10 后置）：它曾是十五项里唯一不带下界的扫描。下界不只是省开销，它是判据的一部分——`pay_amount` 由支付通知回填，一笔刚走完关单收敛的单在通知到达前 `pay_amount` 与 `order_amount` 本就可能不等，没有下界时这个正常的中间态每轮都会被报成金额差异。**假告警会让资损哨兵失效**，与本节其余条目同理。
>
> **第 5、9、14 项走 `idx_pay_update(pay_status, update_time)`**（V3 PR-10 后置补）：三者的谓词都是 `pay_status + update_time`，而 `idx_pay_grant` 的第二列是 `grant_status`——只有最左列用得上，`update_time` 落到回表后逐行过滤。**「走了索引」与「走对了索引」是两回事**：删掉新索引后 `EXPLAIN` 的 `type` 从 `RANGE` 退化为 `REF` 而非 `ALL`，只断言「不是全表扫」的用例照样全绿（实测确认，故用例改为断言 `type = RANGE`）。第 15 项无需新建索引——已有 `uk_idempotent(user_id, activity_id, sku_id, client_req_no)` 覆盖其前三列，**唯一键的最左前缀本就是一个可用的普通索引**。
>
> **第 6、15 项比对的是份数，不是单数**（V3 PR-10 review 修）：`consumed` 与 `used_qty` 均按份数累加（`consumed = consumed + qty`），拿它们与 `COUNT(*)` 比会让一笔 `quantity=3` 的正常单每轮报一次假差异。**假告警会让资损哨兵失效**，与本节其余条目的用意相同。
>
> **第 5/6/11 项是资损哨兵指标的数据来源**（§8.2）——这些指标**由对账任务产出，不是请求路径埋点**。
>
> **第 15 项与第 6 项是同一类兜底的两个计数器**（V2 PR-8 补）：第 6 项管库存，这一项管额度。V2 之前只有前者，理由曾是「额度由库存那道闸一并保证」——而该假设不成立：两者「是否占用过」不同步，详见 §7.4。**凡是有一个共享计数器、又要按单增减的地方，就要有一条对账项**。
>
> **第 10 项的处置在 V3 PR-10 实施时改为只告警**：原写「重放关系后处理」，而重放入口 `settleDone` 的关系推进是条件更新 `WHERE status='JOINED'`，对已 `DONE` 的关系命中 0 行，进度加不上去。且 `progress` 与 `locked`、`used_qty` 同为共享计数器，直接改数会把错误固化成新基线。**第 13 项是唯一直接改字段的**（清 `granting_until`）——清的是豁免标志不是业务结果，清完关系回到治理的扫描范围内。
>
> **差异一律不自动改 `used_qty`**：它与 `locked` 不同——库存差异可由「补建释放任务」自愈（任务本身带幂等闸），而额度的正确值取决于历史上哪些单占用过，直接改数会把一次错误固化成新的基线。

对账扫描走 §3.4 的 `idx_pay_grant` 等索引，不全表扫；差异先告警（NFR-A）再自动/人工修复，闭环回 `MANUAL_REPAIR` 操作记录。

## 7. 关键技术方案


### 7.1 好友过滤下推（SQL 放大治理）

**问题**：好友过滤的朴素实现按「分页 × 过滤器 × 页内用户」三重遍历，关系过滤对每个用户各查一次、每次都扫师傅全量关系再内存判断，SQL 次数与扫描行数双重放大，师傅关系上千后 P99 劣化明显。

**基线（优化前）的确切形态**——必须先写死，收益口径才站得住：

```java
// 优化前：关系过滤对候选页内【每个用户各查一次】
for (Page page : friendPages) {              // 分页拉好友，每页 N=200 人
    for (Filter f : filters) {               // 8 个过滤器
        for (User u : page.users()) {        // ← 病根在这一层
            if (f == RELATION_FILTER)
                selectRelation(groupId, u.id());   // 单人一次 SQL
        }
    }
}
// SQL 次数 = page × N，且每次都按 (group_id,status) 扫该师傅全量关系
```

**方案**：两步改造，收益来自两笔不同的账。
1. **批量化（换轴）**：关系过滤从「逐用户查」改为「整页一次 `IN` 查询」，SQL 次数从 `page × N` 降到 `page × 1`，即**降 N 倍（≈200×）**。
2. **关系过滤下推 DB**：把内存 join 改为 `follower_id IN (当前候选页)` 下推，配合正确索引使**扫描行数从 O(师傅全量关系) 降到 O(命中数)**：

```sql
SELECT follower_id FROM fission_relation
WHERE group_id = ? AND follower_id IN (?, ?, ...)   -- 仅当前页 N 人，非师傅全量关系
  AND status IN ('INVITED','CONNECTED','JOINED');
```

**索引必须是 `(group_id, follower_id, status)`**（即 `idx_group_follower_status`，与 `uk_group_follower_active` 同前缀）。若用 `(group_id, status)`，`follower_id` 只能在回表后逐行过滤，扫描行数仍等于该师傅当前轮次的全部进行中关系（千级），下推就白做了。换索引后 `IN` 列表转为 N 次 index seek，**扫描行数 = 命中行数**。

**收益口径（拆成两笔，各自可验证）**：

| | SQL 次数 | 单次扫描行数 | 总扫描行数 |
| --- | --- | --- | --- |
| 基线 | `page × N`（N=每页人数≈200） | O(师傅全量关系 R) | `page × N × R` |
| 优化后 | `page × 1` | O(命中数 h) | `page × h` |

- **SQL 次数降 N 倍（≈200×）** —— 来自批量化；
- **单次扫描行数降 `R/h` 倍** —— 来自下推 + 正确索引；
- 两者相乘，总扫描行数降幅在千级师傅关系下可达三个数量级。

> 注意 SQL 次数**不与 `page` 解耦**——候选集本身是分页拉取的，每页仍要执行一次下推查询。收益来自消除「页内逐用户查询」，而非消除分页。NFR-P-08/09 的目标按实测值填写，不写够不着的数字。

**取舍**：`IN` 列表长度受候选页大小约束（N≤200），不会退化为大 `IN`；过滤器可降级（`DegradedRules` 标记），非关键过滤器超时则跳过并标注，保证主链路可用。

**验证**：`fission_relation` 灌百万行、单师傅千级关系，k6 对照压测，产出 before/after 的 QPS、P99、慢查询日志，以及 `EXPLAIN` 的 `key` / `rows` 对照（重点展示 `idx_group_status` 与 `idx_group_follower_status` 两种索引下 `rows` 的差异）。这是全项目**唯一带量化对照**的性能实验，是「有指标不是 demo」的直接答卷。

### 7.2 虚拟线程承接 IO 扇出（JDK 21）

**问题**：发奖/履约链路是典型 IO 密集——一次 `grantBenefit` 要串多个权益项、每项调外部供应方；平台配置刷新、批量查单也大量等 IO。平台线程池扇出受限于线程数，阻塞等待浪费资源。

**方案**：
- 外部调用密集的编排（多权益项发放、批量查单、对账扫描修复）跑在**虚拟线程**上并行 fan-out。
- Web/RPC 入口用虚拟线程承接高并发短连接（支付回调 ≥500 QPS）。

```java
// 发奖扇出：全部 join，绝不取消
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 带超时的 invokeAll：到点未完成的子任务被 cancel，但每一项都有 Future 可读
    List<Future<GrantResult>> futures = executor.invokeAll(
        items.stream().map(it -> (Callable<GrantResult>) () -> grantOne(it)).toList(),
        RPC_TIMEOUT_SECONDS, TimeUnit.SECONDS);
    for (int i = 0; i < futures.size(); i++) {
        try {
            record(items.get(i), futures.get(i).get());         // 各项独立落四分类
        } catch (CancellationException | ExecutionException e) {
            markUnknown(items.get(i));                          // 超时或异常 → UNKNOWN
            taskMapper.insert(queryGrantTask(items.get(i)));    // 各自挂查单任务
        }
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();       // 恢复中断标志，任务表已兜底
    throw new BizException(CODE_INTERRUPTED);
}
```

> 超时项被 `cancel` 后 `get()` 抛 `CancellationException`——它与「确定失败」不同，同样归入 `UNKNOWN` 并挂查单任务，因为供应方可能已经执行成功。`invokeAll` 必须带超时参数，否则一个卡死的供应方会让整个扇出无限期挂起。

> **发奖扇出禁止使用 fail-fast 取消语义**。`StructuredTaskScope.ShutdownOnFailure` 的语义是「任一 fork 失败即取消其余所有 fork」——用在发奖上意味着券发放失败时，正在飞行中的月卡、折扣 RPC 被 interrupt。这些调用可能已经到达供应方并成功执行，但本地既没拿到结果、也没写入终态，正是本方案反复强调要避免的「已发放却无记录」。后续按「核心权益失败 → 回收附加权益后退款」处理时，回收清单里没有月卡 → 退了钱、月卡还在用户手里，直接资损。
>
> 因此用 `newVirtualThreadPerTaskExecutor` + `invokeAll`：**所有子任务都跑完**，失败项各自落 `UNKNOWN` 并挂查单任务，由收敛机制查明真实结果。附带收益是不依赖 `StructuredTaskScope`——它在 JDK 21 仍是 preview（JEP 453，需 `--enable-preview`），交付物不应依赖预览 API。

**取舍**：虚拟线程**不适合 CPU 密集**（无收益还增调度），本项目 CPU 密集极少；注意**避免 `synchronized` 锁 pin 住载体线程**，临界区用 `ReentrantLock`；DB 连接池仍是瓶颈边界，虚拟线程不改变连接数上限，需按池容量限流。

**验证**：同压测下对比平台线程池 vs 虚拟线程的吞吐/RT/资源占用，说明 IO 扇出场景的收益边界。

### 7.3 可靠任务调度（SKIP LOCKED 抢占）

**问题**：多实例部署时，多个调度器扫同一张 `*_task` 表，如何做到不重复消费、不互相阻塞、故障实例的任务能被接管。

**方案**：`SELECT ... FOR UPDATE SKIP LOCKED` 抢占式领取：

**领取必须是同一事务内的两条语句**：

```sql
BEGIN;
-- ① 直接对目标表持锁挑一批（拆两条 SQL，避免 OR 导致 index merge + filesort）
--   主路径：待执行任务，走 idx_sched(status, next_time)
SELECT id FROM benefit_task
 WHERE status='PENDING' AND next_time <= NOW(3)
 ORDER BY next_time LIMIT 50
 FOR UPDATE SKIP LOCKED;              -- 已被别的实例锁住的行直接跳过
--   兜底路径：僵尸任务回收，走 idx_lease(status, lease_expire)，频率可低于主路径
SELECT id FROM benefit_task
 WHERE status='DOING' AND lease_expire < NOW(3)
 ORDER BY lease_expire LIMIT 50
 FOR UPDATE SKIP LOCKED;
-- ② 按 id 更新，打上租约
UPDATE benefit_task
   SET status='DOING', lease_owner=?, lease_expire=NOW(3) + INTERVAL ? SECOND
 WHERE id IN (:ids);
COMMIT;
```

> 两条路径**拆开而非用 `OR` 合并**：`WHERE (status='PENDING' AND next_time<=?) OR (status='DOING' AND lease_expire<?)` 配合 `ORDER BY` 会退化为 index merge + filesort。拆开后各自命中 `idx_sched(status, next_time)` 与 `idx_lease(status, lease_expire)`，且僵尸回收的扫描频率可以低于主路径（如每 10 轮一次），进一步降低开销。

> **陷阱：不要把锁子句塞进派生表**。为绕开 MySQL 错误 1093（不能 UPDATE 又在子查询引用同表），很容易写成
> `UPDATE benefit_task ... WHERE id IN (SELECT id FROM (SELECT id ... FOR UPDATE SKIP LOCKED) t)`。
> 必须拆成上面两条语句，让 `SELECT ... FOR UPDATE SKIP LOCKED` 直接作用于目标表。
>
> **实测修正（V2 PR-2，MySQL 8.4.11）**：本条原记「内层派生表被物化，锁子句随之失效，多个实例领到同一批任务」。实测该写法**不重复领取，而是退化为互相阻塞**——会话 A 持有前两行时，B 不是跳过而是等锁，直至 `Lock wait timeout`。`EXPLAIN` 确认派生表确被物化，但锁仍施加于基表。
>
> 结论不变、理由需换：**阻塞形态比重复领取更难发现**——并发用例只会表现为变慢，「每条任务仅一个 owner」的断言照常通过（已实测确认）。因此该约束由 `ShapeFreezeTest` 静态拦截，不能指望并发测试兜底。原表述所依据的行为可能来自更早的 MySQL 版本，未在 8.4 上复现。

领取后置 `DOING` 并写入租约；处理完 `DONE`；失败 `retry_count++` 且 `next_time = now + backoff`；超阈 `DEAD` 告警。长耗时任务在执行中定期续租（延长 `lease_expire`）。

**`SKIP LOCKED` 与租约解决的是两个不同问题，不可互相替代**：

| 机制 | 解决 | 失效场景 |
| --- | --- | --- |
| `FOR UPDATE SKIP LOCKED` | **同一轮扫描**的多实例并发互斥 | 实例宕机后遗留的 `DOING` 行——它不在 `PENDING` 集合里，也没有任何人持有它的行锁 |
| `lease_expire` 租约 | **跨轮次**的僵尸任务回收 | 无法阻止同一轮内两个实例同时挑中同一行 |

缺租约字段时，被 kill 实例持有的 `DOING` 任务将永久卡死——`GRANT` 任务丢失即「已收款未发奖」，直接资损。

**取舍**：
- 选 **MySQL 8** 而非 H2 测试的直接原因——H2 无 `SKIP LOCKED`，用 Testcontainers 起真实 MySQL 才能验证抢占语义。
- 调度事务显式声明 **`READ COMMITTED`**：RR 隔离级别下范围扫描会加间隙锁，而 `SKIP LOCKED` 跳过的是行锁不是间隙锁，仍可能阻塞新任务插入。
- `uk_biz_type_op(biz_no, task_type, op_no)` 保证同一操作不重复入队，同时允许同业务的多个操作各自建任务。
- 退避 + 死信，避免坏任务无限重试拖垮调度。

**验证**：多实例并发跑，断言每个任务仅被一个实例领取；`kill -9` 一个实例后，其在途 `DOING` 任务在租约到期后被其他实例接管续跑（对应 §8.6 混沌测试）。

### 7.4 库存 0 超卖（DB 原子扣减 vs Redis 预扣）

**问题**：500 并发抢 100 库存，要求恰好成 100 单、0 超卖，且不能因预扣与落单不一致产生「扣了没下单」的漏。

**方案**：本期用 **DB 原子扣减**，扣减与建单同一本地事务：

```sql
-- 预占：与建单、限购扣减同一本地事务
UPDATE marketing_stock SET locked = locked + ?
WHERE stock_key = ? AND total - locked - consumed >= ?;
-- affected_rows = 0 → 库存不足，事务回滚
```

行锁天然串行化，`affected_rows` 即判定成败，无需分布式锁。

**转消耗与释放的竞态治理**（这是 0 超卖真正的难点）：订单到期释放库存与「用户最后一秒付款成功」天然并发，两者若各自直接改库存，会产生 `locked` 为负或额度被突破。解法是**互斥不由库存行承担，而由主单状态机承担**：

```
支付回调:  SET pay_status='PAY_SUCCESS' WHERE pay_status IN ('WAIT_PAY','CLOSING')
关单受理:  SET pay_status='CLOSING'     WHERE pay_status='WAIT_PAY'   ← 不落库存任务
关单确认:  SET pay_status='CLOSED'      WHERE pay_status IN ('WAIT_PAY','CLOSING')
   ↓ 条件更新 affected_rows=1 的一方，才在同事务落库存任务
STOCK_CONSUME / STOCK_RELEASE / QUOTA_RELEASE → 异步执行带下界保护的库存 UPDATE
```

**每一层各防什么，必须分清**——这三层不是「堆三道保险」，而是各挡一类失效：

| 层 | 防的失效 | 防不了的 |
| --- | --- | --- |
| 支付态条件更新 | 「支付成功」与「关单」并发时**双双推进** | 同一分支被重复执行 |
| `*_task.uk_biz_type_op` | 同一单同一类库存动作重复**入队** | 同一条任务被重复**执行** |
| **库存态条件更新 `WHERE stock_status='LOCKED'`** | **同一单的库存被处置两次**（每单幂等的真正承重点） | 跨单的总量越界 |
| **额度态条件更新 `WHERE quota_status='LOCKED'`** | **同一单的额度被返还两次，或未占用过的单去返还** | 同上，且它管的是另一个计数器 |
| SQL 下界 `WHERE locked >= ?` / `used_qty >= ?` | 总数被减成**负值** | 「某一单重复释放」 |

> **下界保护不提供每单幂等**：`locked` 是该 `stock_key` 下所有订单共享的计数器，A 单重复释放两次时，`locked` 因别的订单占用仍大于 0，下界不拦截——结果是 A 释放了别人的预占，可售余量多出一份，构成超卖。
>
> **任务表唯一键同样不提供每单幂等**（V2 PR-5 实施时修正，原文此处标注有误）：它挡的是重复**入队**，挡不住同一条任务被重复**执行**——租约过期被接管、调度器重跑都会走到执行体，而那时唯一键早已生效过、不再参与。
>
> 故须在主单上落 `stock_status`（`NONE/LOCKED/CONSUMED/RELEASED`），执行体先做条件更新 `WHERE stock_status='LOCKED'`，`affected_rows=0` 即跳过实际的库存 UPDATE。这道闸是**按单的**，与共享计数器无关，前两者都替代不了。
>
> **限购额度的返还与库存释放由一个任务承接**（`STOCK_RELEASE`）：「交易未成立」本就是一个事件，库存与额度同进同退；拆成两条任务则同一件事要在两处各判一次状态，且中间崩溃会只还一半。`QUOTA_RELEASE` 保留在任务类型清单里但 V2 不注册处理器。
>
> **但两者各带一道闸，不共用**（V2 PR-8 修正，此前的写法是共用）：额度行按 `(user, activity, sku, period)` 聚合，与 `locked` 完全同构——同一用户的另一笔单占着额度时重复返还会吃掉那一笔的，下界 `used_qty >= qty` 拦不住。故主单再落一列 `quota_status`（`NONE/LOCKED/RELEASED`），与 `stock_status` 分列。
>
> **不能共用 `stock_status` 那一道**，因为「有没有占用过」两者并不同步：库存对每一单都预占，额度只在 SKU 配了限购（`purchase_limit_qty > 0`）时才扣。共用则不限购的单同样以 `LOCKED` 进入释放分支，把不属于它的额度还掉。
>
> **该错误只在限额中途变过时显形**，这也是它到 PR-8 才被发现的原因：既有用例里限额恒定，每一单都占额度，「无条件返还」与「按本单是否占用返还」表现完全相同。触发序列是——限额置 0 时下 A 单（不占额度）→ 运营调高限额 → 同用户下 B 单（`used_qty=1`）→ A 单释放 → B 的额度被 A 还掉。运营调限额是常规动作，不是边缘场景。
>
> **额度没有 `CONSUMED`**：支付成功时额度不动，`quota_status` 停在 `LOCKED`——买了就算用掉。这与库存的不对称即 §3.4 口径表所记：退款回补库存（商品可以再卖给别人），但不返还额度（否则「买了再退」可刷回额度，限购被绕过）。
>
> 此外**库存类任务的 `op_no` 必须写死取值约定**：`op_no = biz_no + '_' + task_type`（如 `B20260802001_STOCK_RELEASE`）。若留空串，同一单可插入多条释放任务，唯一键不起作用——即 §3.3 所述 `NOT NULL DEFAULT ''` 的问题，库存任务同样适用。
>
> **这个错误只有一种用例能暴露**：重复释放时必须**另有一笔单占着库存**。单笔单场景下释放后 `locked` 归零，第二次释放被下界拦下，验证的是「下界生效」而非「不动其他订单的预占」。
>
> 状态机层面：`CLOSING` 阶段**不落任何库存任务**（结果未定不释放），待 `QUERY_CLOSE` 收敛到 `CLOSED` 或 `PAY_SUCCESS` 后，由确定的那一方落对应任务。

**库存变更为何移出支付回调事务**：支付通知目标 500 QPS，而同一活动/SKU 的 `stock_key` 是单行；若在回调事务内更新，500 QPS 的通知加上 300 QPS 的下单预占全部争抢这一行，持锁时间还会把事务内其余三写一起拖长，P99 ≤ 100ms（NFR-P-03）无法达成。移出后回调事务只写 `op_record + pay_status + benefit_task`，热点行不在同步路径上；库存的最终一致由任务保证，对账（§6.8 第 6 项）校验 `locked+consumed` 与单据数一致。

**取舍**：
- DB 原子扣减在百万级数据量下足够，实现简单且强一致；不引入 Redis 预扣的「缓存与 DB 一致性」复杂度。
- 若单 SKU 成为极端热点，先做**分桶**：`stock_key` 拆为 N 个桶（`sku:S1:bucket3`），预占随机选桶、余量不足时轮询其他桶，对账按前缀汇总——比引入 Redis 预扣代价小得多。
- 再往后才是 **Redis 预扣 + 异步落库 + 对账补偿**，作为「可扩展方向」留白，不过度设计。

**验证**：k6 500 并发压 100 库存，断言成功单数 = 100、库存终值 = 0、无负库存（AC-03）；另跑「支付回调与超时关单并发」用例，断言两者恰有一个生效、库存不出现负值。

### 7.5 三子状态机与展示态派生

**问题**：权益订单同时有支付、发放、退款三条推进线，若用单一 `biz_status` 枚举，状态爆炸且并发更新互相覆盖。

**方案**：`play_biz_record` 落 **pay/grant/refund 三个独立子状态**，各自独立推进、独立幂等；对用户展示的 `biz_status` **由三者派生、不落库**：

```
派生规则(优先级从高到低，与 PRD §4.3 逐行对齐):
  refund=REFUND_SUCCESS           → 已退款
  refund in (REVOKING,REFUNDING)  → 退款中
  refund in (REVOKE_FAILED,REFUND_FAILED) → 异常(待人工处置)
  grant=GRANT_FAILED              → 异常(发放失败)
  grant=GRANT_SUCCESS && refund=NONE → 已完成
  grant in (GRANTING,GRANT_UNKNOWN)  → 发放中
  pay=PAY_FAILED                  → 异常(支付失败)
  pay=PAY_SUCCESS                 → 发放中(待履约)
  pay=WAIT_PAY                    → 待支付
  pay=CLOSED                      → 已关闭
```

> 必须保留 `GRANT_FAILED` / `PAY_FAILED` / `REVOKE_FAILED` / `REFUND_FAILED` 四个**异常展示态**。若缺失，一个 `grant=GRANT_FAILED` 的单会沿优先级链落到 `pay=PAY_SUCCESS` 分支，把**异常单显示成正常单**，运营看不见需要处置的单。

**退款准入规则**（直接影响收敛率）：

| grant 状态 | 能否进入退款 | 依据 |
| --- | --- | --- |
| `NOT_START` | ✅ 可直接退款，无需回收 | FR-B08「权益从未发放 → 直接退款」 |
| `GRANT_FAILED` | ✅ 可直接退款，无需回收 | 发放已确定失败，无权益在外 |
| `GRANT_SUCCESS` | ✅ **须先回收再退款** | BR-B-30 先回收后退款 |
| `GRANTING` | ❌ 拒绝 | 结果未定，回收对象不明 |
| `GRANT_UNKNOWN` | ❌ 拒绝，等查单收敛后再判 | **BR-B-29 未知态不退款** |

> **不能写成「grant 未成功就不允许退款」**——那会把 `NOT_START`（从未履约）和 `GRANT_FAILED`（履约失败）这两类**最需要退款**的单永久锁死，而「已支付未履约」正是对账要自动补偿的头号场景，一旦退不了款，收敛率必然破防。正确的分界线是「**结果是否确定**」：确定成功→先回收后退款，确定失败或从未开始→直接退款，**只有不确定（GRANTING/UNKNOWN）才拒绝**。

**取舍**：三子状态避免「支付成功且退款中」这类组合无法用单枚举表达的问题；派生态不落库避免与三子状态不一致；每条子线各自的条件更新/幂等键互不干扰并发。

**验证**：状态机单测覆盖各子状态合法迁移 + 非法迁移拒绝（重点覆盖上表五种 grant 状态下的退款准入判定），派生规则表驱动测试。

### 7.6 模块化单体 → 分布式拆分

**问题**：三人并行开发要低耦合、易联调，交付要能演示分布式；又不想为切换重写业务代码。

**方案**：单 Maven 多模块工程，服务间只通过 **Dubbo 接口 + DTO** 交互，实现类不互相 import。
- **开发期**：`@DubboService`/`@DubboReference(scope="local")` 走 **injvm**，本地方法调用，无需起注册中心，联调快。
- **交付期**：改为 `scope="remote"` + `protocol=tri`，接 Nacos 注册中心，拆成独立进程部署到 3 台机器。

**只改配置/注解，不改业务代码**——这是模块化单体的核心收益。

**取舍**：代价是前期要严守分层与接口纪律（§1.3 上层调下层、同层不互调、不 import 实现），换来的是并行开发 + 平滑演进；对小团队/短周期是最优解，避免一上来就分布式带来的联调地狱。

**验证**：injvm 与 remote 两套 profile 各跑一遍全链路 e2e，证明业务代码零改动切换形态。

### 7.7 活动配置读多写少（本地缓存 + 版本快照）

**问题**：`queryActivityConf`/`decideQualification` 是每次进场/下单都调的读热点（预咨询 ≥1000 QPS），直接查库压力大；但配置又会发布变更，不能读到脏配置。

**方案**：
- 配置**本地缓存 + 定时刷新 + 发布失效**：进程内缓存活动与当前版本，秒级 TTL 刷新，发布时主动失效。
- 历史单据**认版本快照**：下单时把 `config_version + price_snapshot + benefit_snapshot` 冻结进 `play_biz_record`，后续履约/退款一律读快照，配置变更不影响存量单。

**取舍**：读走本地缓存扛 QPS，一致性用「秒级最终一致 + 快照冻结」——营销配置容忍秒级延迟，但**存量单必须用下单时的配置**，快照解决了「配置改了老单怎么算」的经典问题。

**验证**：压测 `queryActivityConf` 达 1000 QPS/P99≤100ms；改配置后老单履约金额仍等于下单快照。

## 8. 监控与压测方案

> 本章是「有指标不是 demo」的直接落地：把 PRD 的性能/正确性/告警目标（NFR-P/C/A）转成可采集的指标、可触发的告警、可复现的压测脚本。三支柱各司其职，业务指标与技术指标分层。

### 8.1 可观测三支柱

| 支柱 | 工具 | 回答的问题 | 采集点 |
| --- | --- | --- | --- |
| Metrics | Prometheus + Grafana | 系统健康吗？指标达标吗？ | Micrometer 埋点 → `/actuator/prometheus` |
| Tracing | SkyWalking | 慢/错在哪一跳？ | Agent 自动埋 Dubbo/MySQL/Redis span |
| Logging | 结构化日志 + traceId | 这一笔具体发生了什么？ | 操作记录 + 日志关联 traceId |

**串联主线**：一次请求的 `traceId` 贯穿三支柱——Grafana 看板发现 P99 毛刺 → SkyWalking 按 traceId 定位慢在哪跳 → 日志/操作记录按 traceId 还原这笔业务，形成「发现→定位→还原」闭环。

### 8.2 业务指标

技术指标各处都有，**业务指标才是这个项目的差异化**。埋点用 Micrometer `Counter`/`Timer`。

**一、经营指标（PRD §9.5 要求「本期实现口径与看板」）**

| 指标 | 类型 | 口径 |
| --- | --- | --- |
| `fission_k_factor` | Gauge | K 因子 = 有效徒弟数 / 参与师傅数，按活动维度日聚合 |
| `fission_funnel_total{stage}` | Counter | 转化漏斗：`SHARE→INVITED→CONNECTED→JOINED→DONE` 各阶段计数，相邻比值即转化率 |
| `benefit_pay_conversion` | Gauge | 支付转化率 = `PAY_SUCCESS` 单数 / 创建订单数 |
| `benefit_order_amount` | Summary | 客单价分布（分位数），`sum/count` 即均值 |
| `benefit_refund_rate` | Gauge | 退款率 = `REFUND_SUCCESS` 单数 / `PAY_SUCCESS` 单数 |
| `cost_per_user` | Gauge | 单用户成本 = 发奖总金额 / 获取用户数（裂变 DONE 数） |
| `pay_to_grant_seconds` | Timer | 履约时效：支付成功 → 权益到账 |
| `friend_filter_total{result}` | Counter | 好友过滤候选数 / 通过数 / 拒绝数，`result` 含拒绝原因（AC-09） |

> 漏斗与 K 因子由 `fission_funnel_total` 一个 Counter 的不同 `stage` 标签算出，无需额外埋点；看板上是一张漏斗图 + 一条 K 因子趋势线。`friend_filter_total` 的 `result` 标签直接对答 AC-09 的「拒绝原因分布」。

**二、一致性与资损指标**：

| 指标 | 类型 | 口径 | 目标（NFR） |
| --- | --- | --- | --- |
| `reward_grant_total{result}` | Counter | 发奖四分类计数 | UNKNOWN 收敛率=100% |
| `idempotent_hit_total{layer}` | Counter | **各层防线拦截次数**（L2 锁冲突 / L3 唯一索引冲突） | 非 0 是好事，证明防线在工作 |
| `reward_duplicate_total` | Counter | **对账检出**的重复发奖（应恒为 0） | =0 |
| `stock_oversold_total` | Gauge | **对账检出**的超卖行数（应恒为 0） | =0 |
| `refund_duplicate_total` | Counter | **对账检出**的重复退款（应恒为 0） | =0 |
| `pay_to_grant_seconds` | Timer | 支付成功→权益到账时延 | P99≤3s |
| `unresolved_pending_gauge{state}` | Gauge | 未收敛的 UNKNOWN / PROCESSING 单量（分列） | 长期趋 0 |
| `task_dead_total` | Counter | 进死信的任务数 | 趋 0，非 0 即告警 |
| `reconcile_diff_total{type}` | Counter | 对账差异条数，按 §6.8 十五项分类 | 趋 0 |
| `manual_repair_total` | Counter | 人工处置次数 | 观察 |
| `sign_verify_fail_total` | Counter | 验签失败量 | 突增即告警 |

> **资损哨兵指标由对账任务产出，不是请求路径埋点**。这一点决定了指标是否可信：
>
> - **唯一索引冲突 ≠ 资损**。冲突表明重复已被拦截，是防线**生效**，应记入 `idempotent_hit_total`（正向指标）。
> - **真正的重复发奖不会产生任何冲突**——它绕过唯一键（用两个不同 `opNo` 发同一笔奖、或供应方侧重复入账）。若把 `reward_duplicate_total` 埋在唯一索引冲突处，指标会恒为 0，但那是**因为测不到，不是因为系统正确**。
> - 故三个「应恒为 0」的指标一律改由 §6.8 的对账项产出：重复发奖来自对账第 11 项（同 `biz_order_no + receiver_id + 奖励项` 存在两条 SUCCESS），超卖来自第 6 项（`SELECT count(*) FROM marketing_stock WHERE locked+consumed > total`），重复退款来自单据级唯一约束的违例检出。
>
> `unresolved_pending_gauge` 按 `state` 分列 UNKNOWN 与 PROCESSING——两者收敛窗口不同（§6.6），合并统计会让长退避的 PROCESSING 单误触告警。

| 时延 | P50/P95/P99（`http_server_requests` / Dubbo Timer） | 预咨询≤100ms / 创建订单≤200ms / 支付通知≤100ms / 好友过滤≤300ms |
| 错误 | 错误率、分区错误码分布（4xxx/5xxx） | 5xxx 系统错误率<0.1% |
| 资源 | CPU/内存/GC 停顿/虚拟线程数/DB 连接池 | GC 无长停顿、连接池不打满 |
| 中间件 | Redis RT、RocketMQ 堆积、慢查询数 | 无消息堆积、慢查询趋 0 |

**PromQL 示例**（P99 时延）：

```promql
histogram_quantile(0.99,
  sum(rate(http_server_requests_seconds_bucket{uri="/preConsult"}[1m])) by (le))
```

### 8.4 告警规则（对齐 NFR-A）

分级告警，资损哨兵最高优先级：

| 级别 | 规则 | 触发 |
| --- | --- | --- |
| P0 资损 | `increase(reward_duplicate_total[5m])>0` 或 `stock_oversold_total>0` 或 `refund_duplicate_total>0` | 立即电话/群 @ |
| P0 金额 | 对账检出 `pay_amount ≠ order_amount`（§6.8 第 5 项） | 立即告警，禁止自动改单 |
| P0 履约缺失 | `pay=PAY_SUCCESS` 但无对应 GRANT 任务/操作记录 | 已收款未发奖前兆 |
| P0 收敛 | `unresolved_pending_gauge{state="UNKNOWN"}` 持续 >阈值 30min | 未知态未收敛，可能资损前兆 |
| P1 收敛 | `unresolved_pending_gauge{state="PROCESSING"}` 持续 >阈值 2h | 阈值宽于 UNKNOWN（等下游通知） |
| P1 验签 | `increase(sign_verify_fail_total[5m])` 突增 | 可能被刷或上游密钥不一致 |
| P1 关系异常 | 关系数与发奖数大规模不一致（对账第 7/10 项） | 裂变链路异常 |
| P1 时延 | 关键接口 P99 连续 5min 超目标 2 倍 | 群告警 |
| P1 死信 | `increase(task_dead_total[10m])>0` | 任务进死信需人工修复 |
| P2 容量 | 连接池使用率>80% / MQ 堆积>阈值 | 观察 |

告警经 Alertmanager 分级路由；每条告警附 traceId/看板链接，直达定位。

### 8.5 压测方案（k6）

**压测目标**：不是「跑个高 QPS」，而是**验证 PRD 每条量化目标 + 正确性在压力下不破**。

**场景清单**：

| 场景 | 模型 | 断言 |
| --- | --- | --- |
| 预咨询读热点 | 恒定 1000 QPS/5min | P99≤100ms、错误率<0.1% |
| 创建订单 | 阶梯加压至 300 QPS | P99≤200ms、无超卖 |
| 支付通知 | 尖峰 500 QPS | P99≤100ms、无重复发奖 |
| 师傅进场 | 500 QPS | P99≤150ms |
| **秒杀抢库存** | 500 VU 瞬时抢 100 库存 | **成功=100、库存终值=0、无负库存**（AC-03） |
| **好友过滤对照** | before/after 各压一轮 | SQL 次数/扫描行数/P99 达优化目标（NFR-P-08~10） |

**k6 秒杀断言示例**：

```javascript
export const options = { scenarios: { seckill: {
  executor: 'shared-iterations', vus: 500, iterations: 500 } } };
export default function () {
  const r = http.post(`${BASE}/createTrade`, payload);
  check(r, { 'no oversell': (res) =>
    res.status === 200 || res.json('code') === '1712' });   // 1712=库存不足，对齐 PRD 附录 C
}
// 压测后校验：SELECT total-locked-consumed FROM marketing_stock → 必 >=0
// 成功单数断言（口径精确到活动+SKU，且只算「占着库存」的单）：
//   SELECT count(*) FROM play_biz_record
//    WHERE activity_id=? AND sku_id=? AND pay_status IN ('WAIT_PAY','PAY_SUCCESS') → 必 =100
//   另断言 marketing_stock: total - locked - consumed = 0 且 locked >= 0
```

## 9. 任务拆分与排期

> 三人团队并行开发。核心约束：公共底座（A）先出接口，B/C 才能开工。排期围绕「接口先冻结 → 主链路 → 一致性 → 压测 → 分布式交付」的依赖顺序展开。周次为相对周，示意粒度。

### 9.1 分工与职责边界

| 开发者 | 负责模块 | 核心职责 | 依赖 |
| --- | --- | --- | --- |
| A | gateway、marketing-activity、reward、工程骨架、中间件、监控 | 公共底座 + 基础设施，最先冻结接口供 B/C 依赖 | 无（被依赖方） |
| B | fission 全链路 | 裂变组/关系、好友过滤下推、双向发奖编排、关系治理 | A 的 activity/reward 接口 |
| C | benefit-order 全链路 | 订单、支付对接、履约编排、退款、权益回收 | A 的 activity/reward 接口 |

**边界原则**：三人只通过 Dubbo 接口 + DTO 交互，不 import 彼此实现（§1.3）；各自的库表由 Flyway 独立管理，互不冲突（§3.1）。

### 9.2 里程碑与退出标准

| 里程碑 | 周次 | 目标 | 退出标准 |
| --- | --- | --- | --- |
| M0 接口冻结 | W1 | 全部 Dubbo 接口与 DTO、**DDL 全量（含唯一约束与索引）**、错误码分区、**《幂等键生成规约》** | 接口/DTO 编译通过；Flyway 脚本可建库；**幂等键规则逐接口落表**，B/C 可对空实现联调 |
| M1 工程骨架 | W2 | 多模块工程、injvm 打通、中间件（含 RocketMQ）起本地、Flyway 建库、**公共可靠任务框架**、gateway | 单进程跑通一次空链路调用；**任务调度器（SKIP LOCKED + 租约）可独立跑通并有单测** |
| M2 主链路（**内建一致性**） | W3–W4 | 两玩法主链路打通，**写路径自带幂等与可靠任务**；随开发埋点 | 主链路端到端跑通；**每个写接口都有唯一约束 + 操作记录 + 任务落库**；重复请求幂等；核心指标已上报 |
| M3 异常与收敛 | W5–W6 | 四分类收敛、对账补偿、退款回收、人工处置、关系治理 | **注入 UNKNOWN/超时/kill 实例不产生资损**；对账 15 项跑通；收敛率 100% |
| M4 压测与调优 | W7 | k6 六场景、好友过滤 before/after 对照、看板与告警定稿 | 关键接口达 PRD 目标；秒杀 0 超卖；对照实验出数 |
| M5 分布式交付 | W8 | injvm→remote 切换、三机部署、演示 | 三机跑通全链路，业务代码零改动 |

**排期调整的两条依据**（相对初版）：

1. **一致性从 M3 前移进 M2**。四层防线是主链路的**骨架而非补丁**：若 M2 先写 happy path、M3 再补幂等与可靠任务，等于把「写路径的事务边界」推倒重来——`op_record` 与 `task` 必须与业务状态同事务，这决定了每个写方法的结构。因此 M2 定义为「带着幂等和任务写主链路」，M3 专注**异常路径与收敛**（对账、补偿、人工处置）。
2. **埋点随 M2/M3 开发同步进行，不集中到 M4**。若把「埋点 + 三块看板 + 告警 + 6 个压测场景 + before/after 对照实验」压进 M4 一周并不现实——尤其对照实验需要两套代码路径各压一轮。故埋点随功能开发落地，M4 只做**压测与调优**。

### 9.3 阶段任务分解

| 阶段 | A（公共底座） | B（裂变） | C（权益） |
| --- | --- | --- | --- |
| M0 | 定 activity/reward 接口、统一响应（**RetStatus 四值**）、错误码、公共 DTO、**幂等键规约** | 评审并锁定所依赖接口；定 fission 接口与 DDL（唯一约束） | 评审并锁定所依赖接口；定 benefit 接口与 DDL（唯一约束） |
| M1 | 多模块骨架、injvm 配置、中间件（含 RocketMQ）、Flyway、gateway、**可靠任务框架（SKIP LOCKED + 租约 + 退避 + 死信）**、监控栈骨架 | fission 模块骨架 + 库表 | benefit 模块骨架 + 库表 |
| M2 | activity 配置/资格/发布、reward 发奖 + **查单** + 事件发布 | 进场/分享/加入/完成主链路，**自带幂等键、操作记录、任务前置** + 埋点 | 下单（验凭证+比价+库存限购）/支付回调（金额校验）/履约主链路，**自带三闸幂等** + 埋点 |
| M3 | reward 回收 + 供应方回调、公共对账框架、人工处置接口 | 四分类收敛、关系过期治理（排除在途）、好友过滤下推 | 三子状态机、关单/超时、退款先回收后退、对账补偿 |
| M4 | 资损大盘定稿、告警规则、混沌注入脚本 | 好友过滤 before/after 对照实验出数 | 秒杀压测、UNKNOWN 注入与 kill 实例验证 |
| M5 | Nacos 接入、三机部署编排、演示脚本 | fission 切 remote + 联调 | benefit 切 remote + 联调 |

> **M1 的可靠任务框架是全队卡点**：B/C 在 M2 就要用它落任务，因此 A 必须在 M1 交付可跑通的调度器（含租约回收单测），不能拖到 M3。这是本次排期调整中 A 的最大变化。

### 9.4 依赖关系与关键路径

```
A: M0接口+幂等规约 ─> M1骨架+任务框架 ─> M2公共能力 ─> M3对账/回收 ─> M4大盘 ─> M5部署
      │                    │                  │
      ▼                    ▼                  ▼    (B/C 每阶段依赖 A 同阶段产出)
B: ─────────────────> 骨架 ──> 主链路(内建一致性) ──> 收敛与治理 ──> 对照实验 ──> 切remote
C: ─────────────────> 骨架 ──> 主链路(内建一致性) ──> 收敛与补偿 ──> 压测 ──────> 切remote
```

**关键路径**：`A.M0 接口+幂等规约 → A.M1 可靠任务框架 → B/C.M2 主链路 → M3 收敛 → M4 压测`。

- A 是**被依赖方**：M0 的接口冻结与幂等键规约、M1 的可靠任务框架是全队卡点，必须最优先交付。**幂等规约必须在 M0 定死**——它决定每个写接口的键构造方式，晚定则 B/C 的写路径要重写。
- B/C 在 M0 后即可用 **A 的接口空实现（mock 返回）** 并行开发骨架与主链路，不必等 A 完成实现——接口冻结解耦了实现进度。
- 好友过滤下推（B）与秒杀压测（C）是各自的技术亮点：功能在 M3 完成，M4 专门用于**出对照数据**，避免与开发抢时间。
- **风险与缓冲**：M2 内建一致性会让主链路开发变慢（预计比纯 happy path 多 20~30%），但省下的是 M3 的重构时间，净收益为正。若 M2 超期，优先保「裂变徒弟完成 + 权益下单支付履约」两条主链路，把关系治理、权益使用状态同步等边缘功能后移到 M3。

### 9.5 并行开发保障机制

| 机制 | 作用 |
| --- | --- |
| 接口先冻结 | M0 锁定 Dubbo 接口/DTO/错误码，三人按契约并行，互不阻塞 |
| injvm 联调 | 单进程即可全链路联调，无需起多机（§1.4） |
| 接口 mock/空实现 | A 未完成实现前，B/C 用 mock 返回先行开发 |
| Flyway 独立管理 | 各服务库表脚本独立，合并不冲突（§3.1） |
| 契约测试 | 对冻结接口做契约测试，防止 A 改接口悄悄破坏 B/C |
| Testcontainers | 各自集成测试起真实中间件，本地可独立验证 |
