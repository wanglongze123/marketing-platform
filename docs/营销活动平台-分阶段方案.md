# 营销活动平台 分阶段方案

## 0. 本文档的定位

三份文档配套使用，职责不重叠：

| 文档 | 回答什么 |
| --- | --- |
| 《技术方案》 | **怎么设计的、为什么这么设计**。表结构、接口签名、时序、四层防线的推导 —— 终态,不随阶段修改 |
| 《环境与依赖》 | **用什么版本、怎么跑起来** |
| 本文档 | **这一阶段从终态里裁哪一块、裁的时候不能裁掉什么、做到什么程度算完** |

本文档大量引用技术方案章节号（如 `§3.4`），写代码时两份对着看：本文档说「V1 建 `play_biz_record`，全量字段」，具体字段去技术方案 §3.4 抄，不在此重复。

**评审节奏**：每阶段开工前评审本文档对应章节，通过后开工。阶段细化直接补写进本文档，不另起文件。

## 1. 阶段划分

| 阶段 | 一句话 | 交付形态 | 演示什么 |
| --- | --- | --- | --- |
| **V0** | 骨架 | 空壳工程 + CI | 提 PR 触发 CI，全绿 |
| **V1** | 跑通 | 单进程模块化单体，下游 mock 固定成功 | 下单 → 支付回调 → 发放 → 查得到 |
| **V2** | 扛住 | 单进程，下游 mock 可注入异常 | 注入超时自动收敛不重复发放；500VU 抢 100 不超卖 |
| **V3** | 铺开 | 单进程，两玩法齐全 + 逆向 + 对账 | 新玩法接入后段零改动；对账检出人为注入的差异 |
| **V4** | 分布式 | 5 服务独立部署，多实例 | kill 实例任务被接管；三机压测与看板 |

### 1.1 为什么这样切

**按「可验证的正确性」切，不按模块切。** 每一刀落在「能不能演示一个现象」上。按模块切需要先冻结全部接口再付集成成本，而接口在实现中大概率还会变。

**先权益、后裂变。** 权益售卖链路短、状态机简单，适合把「主单 + 操作记录 + 可靠任务」这套骨架立起来。裂变的关系状态机（四态 + 两条终止边 + `active_flag` 部分唯一 + `granting_until` 过期豁免）复杂度高，压在骨架不稳时做会返工。

**V2 在 V3 之前。** 先让系统面对「下游不可靠」，再面对「分布式」。次序颠倒则压测暴露的问题无法归因 —— 锁未生效、结果分类判错、RPC 序列化异常三者混杂。

**分布式化放最后。** 拆服务、多实例是把已经正确的系统分布式化，正确性不来自它们。放前面会让每次调试都要起 5 个进程。

**V3 与 V4 分开，同一把刀。** 原 V3 骨架把「第二个玩法接入」与「分布式化」压在一个阶段，二者的验收对象却完全不同：前者验的是**抽象对不对**（裂变接入时公共能力层动了几处），后者验的是**部署形态换了业务代码是否不变**。合在一起时，裂变接入引发的接口改动与拆服务引发的序列化、超时、注册发现问题会混在同一批调试里，与「V2 在 V3 之前」要避免的是同一种归因困难。故 V3 仍为单进程，V4 才拆。

### 1.2 第二个玩法为什么排在 V3

技术方案 §5.0 的核心论断：`FissionFollowerDone` 与 `payCallback` 占据同一架构位置 —— 都是「确权事件 → 触发公共能力层发放」。

这个论断**只有在第二个玩法接入的那一刻才被证明**。裂变接入不是「补一个功能」，而是**对公共能力层抽象的验收**。接入过程中 `reward` 接口的改动量本身就是交付物 —— 改动越小，说明抽象越对。

## 2. V1 形状冻结清单

### 2.1 为什么先讲这个

真正导致返工的从来不是「某功能没做」，而是「某个形状定错了」。功能是**加代码**，形状是**改所有调用方**。

V1 的功能仅为 happy path，无可评之处，**首次评审的重点即这份清单** —— 此时修改成本最低。

### 2.2 八项

| # | 冻结项 | V1 只需做到 | 不冻结的代价 |
| --- | --- | --- | --- |
| 1 | **幂等键进接口 + 唯一索引** | 接口参数带 `clientReqNo` / `opNo`；`uk_idempotent` 系列索引全建 | 改所有调用方签名 + 洗历史数据 |
| 2 | **下游返回四分类枚举** | 定义 `RetStatus{SUCCESS, FAIL, PROCESSING, UNKNOWN}`（命名以技术方案 §4.1 为准）；mock 只返 `SUCCESS`，其余分支 `throw UnsupportedOperationException("V2")` | 若 V1 返 `boolean`，V2 要改每个调用点的分支逻辑 |
| 3 | **状态枚举一次定全** | 三条子状态线按 §3.4 全部写进代码，V1 用不到的也写 | 加枚举值要写 migration，且所有查询条件要重新审查 |
| 4 | **`play_op_record` 建表并写入** | 建表 + 每个写操作插一条 | 后加等于在每条写路径中间插一层，且要与事务边界重新对齐 |
| 5 | **事务边界收成一个方法** | 状态变更用一个 `@Transactional` 方法包住 | 可靠任务表要求「任务写入与状态变更同事务」，边界散了就要重构 |
| 6 | **`reward` 接口通用化** | 入参只有 `playType / activityId / bizOrderNo / opNo / receiverId / rewardItems[]`，**不出现 `orderId` / `tradeNo` 等权益售卖专有概念** | 裂变接入时要改接口，「后段零改动」的论断直接落空 |
| 7 | **Maven 模块按终态切** | 建全部 module，模块间 `injvm` 调用 | V3 拆服务变成重写而非改配置 |
| 8 | **异常映射方向** | facade 层：`BizException` → `FAIL`，**其余未预期异常 → `UNKNOWN`** | 未预期异常若映射为 `FAIL`，调用方会走补偿路径，而下游可能已执行成功 |

**八项加起来，V1 的额外工作量约半天。** 省下它们，V2 起步就是重构。

第 8 项容易被忽略：V1 阶段 mock 固定成功，几乎不会触发异常分支，很容易顺手写成 `catch (Exception e) { return FAIL; }`。这行代码在 V2 引入真实异常后就是资损入口。

### 2.3 第 6 项展开（最容易做错）

V1 只有权益售卖一个调用方，写 `reward` 接口时手会自然地把 `orderId` 塞进去 —— 因为当下只有它。等 V3 接裂变时才发现这是「权益专用发放接口」，不是「通用发放接口」。

**判据**：写完 `grantReward` 签名后，问自己「裂变的师徒双向发奖能不能原样调用这个方法」。答案必须是能。裂变发放的入参是「师傅 userId + 奖励包」，没有订单号 —— 所以 `bizOrderNo` 必须是**通用业务单号**，语义是「调用方的业务标识」，不是「订单号」。

### 2.4 评审时逐项确认的方式

第一次评审的产出应当是这张表填满，而不是「大家觉得没问题」：

| 冻结项 | 确认方式 |
| --- | --- |
| 1 幂等键进接口 | 打开 `CreateTradeReq` / `GrantRewardReq`，确认幂等字段存在；打开 DDL，确认唯一索引存在 |
| 2 四分类枚举 | 打开 `RetStatus.java`，确认四个值；打开调用点，确认是 `switch` 四分支而非 `if (success)` |
| 3 状态枚举定全 | 与技术方案 §3.4 的状态迁移表逐行对照 |
| 4 `play_op_record` | 打开 DDL 与写入代码 |
| 5 事务边界 | 全局搜索 `@Transactional`，确认每处都只包状态变更，且方法内无 RPC |
| 6 `reward` 接口通用化 | 逐字段念一遍 `GrantRewardReq`，任何一个字段说不出「裂变怎么传」即为不通过 |
| 7 模块切分 | `mvn dependency:tree` 看依赖方向 |
| 8 异常映射 | 全局搜索 `catch`，确认没有 `catch (Exception) → FAIL` |

## 3. V0 做什么

V0 不写业务代码，只回答一个问题：**这套工程结构、构建、CI、测试基础设施，是不是真的能跑通。**

产出是一个 **walking skeleton** —— 一条极简但**贯穿全部层次**的链路，把每一样基础设施都实际用一遍。用不上的基础设施不在 V0 引入。

### 3.1 交付清单

| # | 项 | 内容 |
| --- | --- | --- |
| 1 | 仓库 | 建仓、`main` 分支保护、`.gitignore`、`README.md` |
| 2 | 构建骨架 | 根 `pom.xml` + 全部 module 空壳，版本按《环境与依赖》锁定 |
| 3 | 依赖方向 | 各 module 的 `pom.xml` 只声明允许方向的依赖 |
| 4 | 格式化 | Spotless 绑到 `verify` 阶段 |
| 5 | Git 钩子 | `git-build-hook-maven-plugin` + `.githooks/commit-msg` + `.githooks/pre-commit` |
| 6 | 中间件 | `docker-compose.yml`，V0/V1 只需 MySQL |
| 7 | Flyway | 四个库的 `CREATE DATABASE` + 迁移目录骨架；V0 只有一个脚本 `V0201__create_smoke_record.sql`（发奖库） |
| 8 | 冒烟链路 | 见 §3.2 |
| 9 | 集成测试 | Testcontainers 起真实 MySQL，跑通冒烟链路；surefire / failsafe 按 `*Test` / `*IT` 分工 |
| 10 | CI | GitHub Actions，见 §3.4 |
| 11 | 基础设施代码 | traceId 过滤器 + MDC 透传、`@RestControllerAdvice` 全局异常、`logback-spring.xml` |
| 12 | PR 模板 | `.github/PULL_REQUEST_TEMPLATE.md`，内容见《开发规范》§2.1 |

**第 11 项放在 V0 而非 V1**：traceId 与全局异常处理是横切能力，V1 一旦开始写业务代码再补，每个已写的 facade 都要回头改一遍。

### 3.2 冒烟链路的设计

冒烟链路要**贯穿全部层次**，否则验证不到分层是否真的成立。

```
HTTP GET /smoke/{bizNo}
    ↓ gateway
BenefitOrderService.smoke(bizNo)          玩法层
    ↓ Dubbo injvm
RewardService.smoke(bizNo)                公共能力层
    ↓ Dubbo injvm
MockProviderService.smoke(bizNo)          下游 mock
    ↓ 返回
reward 写一行 smoke_record（Flyway 建表）    验证 Flyway + MyBatis-Plus + 事务
    ↓ 返回
gateway 返回 {"code":0,"data":{"bizNo":"...","chain":["gateway","benefit-order","reward","mock"]}}
```

**这条链路验证了七件事**：多模块能编译、Dubbo `injvm` 能通、依赖方向没写反、Flyway 能在真实 MySQL 跑起来、MyBatis-Plus 能写库、Spring Boot 3.5 + JDK 21 组合可用、Testcontainers 能起容器。

**冒烟链路刻意走「逐层向下」**（玩法层 → 公共能力层 → 下游），是为了把四层都串一遍。但这不是唯一合法形状 —— V1 的 `createTrade` 直接调 `mock-downstream` 的支付服务、跨过公共能力层，同样合法（《开发规范》§3.2 规则 1：跨层向下允许）。

**`smoke_record` 建在 `db_reward`**（脚本 `V0201__create_smoke_record.sql`，放 `mp-reward` 模块下），因为链路末端是 reward 写库。表结构极简：`id` + `biz_no` + `create_time`。

**它和全部 `smoke` 方法在 V1 结束时删除**（`V1203__drop_smoke_record.sql`，不修改 V0 的历史脚本）。它是脚手架，不是功能。

### 3.3 依赖方向的验证方式

依赖方向靠 `pom.xml` 编译期强制（见《开发规范》§3.2）。V0 要**实际验证一次它真的会挡住**：

1. 临时在 `mp-reward/pom.xml` 里加一条对 `mp-benefit-order` 的依赖（下层依赖上层）
2. `mvn clean compile`，确认**构建失败**
3. 删掉这条依赖，确认构建恢复
4. 把这次验证的结论写进 PR 描述

省去此步，「依赖方向编译期强制」只是一项未经验证的声明。

### 3.4 CI 必过项

GitHub Actions，触发条件：向 `main` 提 PR、push 到 `main`。

| # | 检查 | 命令 |
| --- | --- | --- |
| 1 | commit message 格式 | 正则校验 Conventional Commits |
| 2 | 代码格式 | `mvn spotless:check` |
| 3 | 编译 | `mvn clean compile` |
| 4 | 单测 | `mvn test` |
| 5 | 集成测试 | `mvn verify`（Testcontainers 起 MySQL） |
| 6 | Flyway 从零执行 | 包含在集成测试内 —— 容器是全新的库，迁移必须从零跑通 |
| 7 | 文档一致性 | `python3 docs/check-docs.py`（V1 补入，见 §4.8） |

任一不过不允许合入。CI 用 JDK 21，与本地一致。第 7 项在 V0 阶段为 6 项，V1 起为 7 项。

**CI 上不要跑 `mvn validate` 装钩子** —— CI 环境不需要 git 钩子，且 `git-build-hook-maven-plugin` 在 detached HEAD 下可能报错。CI 直接从 `spotless:check` 开始。

# V1：跑通

> 预计一周。目标是**一条能演示的正向链路**，以及八项形状冻结全部落地。

## 4. V1 范围

### 4.1 一句话

用户下单 → 支付成功 → 权益发放 → 查得到。下游全部 mock 且固定成功，不考虑任何异常。

### 4.2 链路时序

```
① createTrade                            benefit-order
     校验活动有效（调 activity.queryActivityConf）
     读 benefit_sku → benefit_package → benefit_item，组装 benefit_snapshot
     生成 bizNo（BizNoGenerator）—— 同时作为支付侧的商户订单号
     事务：建 play_biz_record（pay=WAIT_PAY, grant=NOT_START, refund=NONE）
          + 写 play_op_record(CREATE_TRADE, op_seq='', SUCCESS)
     事务外：调 mock 支付下单，传 outTradeNo=bizNo
     第二个短事务：回填 trade_no
                ↓
② payCallback                            benefit-order
     按 outTradeNo（=bizNo）定位主单     ← 不依赖 trade_no 是否已回填
     验金额/币种/商户号，任一不符 → 不改任何状态，返回失败
     事务：按 payStatus 分支做条件更新（见下表）
          + 写 play_op_record(PAY_CALLBACK, op_seq=notifySeq)
     仅当推进到 PAY_SUCCESS 时，事务提交后：
          【V1 同步调用 grantBenefit；V2 改为事务内落 GRANT 任务】
                ↓
③ grantBenefit                           benefit-order
     读 play_biz_record.benefit_snapshot，按 provider_type 分组
     事务 A：条件更新 grant_status NOT_START → GRANTING
            + upsert play_op_record(GRANT_BENEFIT, op_seq='', status=PROCESSING)
            ※ 二者 affected_rows 均为 0 时 → 走重入分支（见下）
     事务外，每组派生 grantOpNo = bizNo + '_G_' + providerType
       → 调 reward.grantReward
       → upsert benefit_fulfillment_record（按 uk_biz_item，一权益项一行）
     事务 B：条件更新 grant_status GRANTING → GRANT_SUCCESS
            + 回写 op_record(GRANT_BENEFIT).status = SUCCESS
                ↓
④ reward.grantReward                     reward
     按 op_no 查 reward_grant_record，命中则直接返回原结果（幂等出口）
     未命中：插入 reward_grant_record(result=PROCESSING)   ← 落库态，非下游返回值
            → 调 mock 供应方（V1 固定返回 SUCCESS）
            → 落 reward_grant_item（一奖励项一行）
            → 回写 reward_grant_record.result = SUCCESS
                ↓
⑤ queryOrder                             benefit-order
     返回主单三子状态 + 履约明细列表
```

#### `payStatus` 的分支处置

`PayCallbackReq.payStatus` 在 V1 只接受两个值，各自的条件更新谓词不同：

| `payStatus` | 条件更新 | 后续 |
| --- | --- | --- |
| `SUCCESS` | `SET pay_status='PAY_SUCCESS' WHERE pay_status='WAIT_PAY'` | `affected_rows=1` 才触发 `grantBenefit` |
| `FAILED` | `SET pay_status='PAY_FAILED' WHERE pay_status='WAIT_PAY'` | 不触发履约，链路终止 |

**`affected_rows=0` 时直接 ACK 返回成功，不抛异常、不重试。** 这是幂等三道闸的第三道生效，不是错误。

**V1 不接受 `CLOSED`**：关单是 V2 的 `closeOrder` 引入的语义，V1 收到该值直接拒绝并返回参数错误。不要为了「以后要支持」提前写分支 —— 提前写的分支没有测试覆盖，而 V2 引入 `CLOSING` 中间态后逻辑还要重写。

#### 关于支付侧的关联号

`bizNo`（`play_biz_record_no`）**同时作为传给支付方的商户订单号**（即微信/支付宝语境下的 `out_trade_no`），回调按它定位主单。

不新增字段的理由：`bizNo` 本身已全局唯一、已有 `uk_biz_no`、且在调用支付方**之前**就已落库。若改为「支付方返回 `tradeNo` 后再按 `tradeNo` 定位」，则在「支付下单成功但 `trade_no` 尚未回填」的窗口内进程崩溃，回调将无法定位业务单 —— 钱收了，订单还是 `WAIT_PAY`。

`trade_no` 仍然回填并保留 `uk_trade_no`，它的作用是反查与对账，不是回调的定位依据。

#### 关于 `quantity`

**V1 冻结为 `quantity = 1`**，`createTrade` 校验不等于 1 时直接拒绝（`4001`）。

字段保留在 `CreateTradeReq` 里（形状冻结，V2 引入库存时才真正生效）。V1 不实现的理由：`quantity > 1` 会牵连三处语义——应付金额如何计算、`RewardItem.qty` 传什么、`benefit_fulfillment_record` 是一项一行还是一份一行。这三处都要在库存与限购一起做时才定得下来，V1 定了大概率要改。

**显式校验而非默默忽略**：如果只是不读这个字段，调用方传 `quantity=3` 会得到一份权益却付了一份的钱，且没有任何报错。

**V3 放开（全量 review 后置）**。当年列的三处牵连，实测后结论如下：

| 当年的问题 | 结论 |
| --- | --- |
| 应付金额如何计算 | `order_amount = salePrice × quantity`。**`salePrice` 是单价**——`preConsult` 不接收 `quantity`，故 `token.dealPrice` 与服务端重算价比的一直是单价，比价那一步不受份数影响 |
| `RewardItem.qty` 传什么 | 传订单份数。`benefit_item` 没有数量列，包内每项恒为 1 份，故「这一项发几份」完全由订单份数决定 |
| 履约明细一项一行还是一份一行 | **一项一行**。回收走履约明细而非快照，粒度与发放调用对齐（一次调用 = 一个供应方 = 一行），份数不进明细也不进快照 |

第三处当年担心的「快照要不要存份数」**实测不需要**：两处读快照的地方（`grantOneProvider`、退款准入的键预检）都能从 `order` 直接拿到 `quantity`，而回收侧根本不读快照。**这是 checklist 上被实测推翻的一项**——列 checklist 时按「份数是权益项的属性」假设，实际它是订单的属性。

**上限取 99**：`quantity` 参与库存预占、限购扣减与金额相乘，三者都按它线性放大。不设上限时一个 `Integer.MAX_VALUE` 会让 `salePrice × qty` 溢出，而 `Math.multiplyExact` 抛的 `ArithmeticException` 落进「异常一律 UNKNOWN」后表现为下单结果未定。

**限购的语义定为「最多买几份」**（非「最多下几单」）：与 `used_qty += qty` 的既有实现一致，也与对账第 15 项的 `SUM(quantity)` 一致。限 2 份时一单买 3 份直接被拒，且不留痕——额度未扣、库存未占。

**两条用例缺一不可**：「买 N 份收 N 份钱」与「买 N 份发 N 份货」必须同时断言。收 1 份钱发 1 份货是自洽的，收 3 份钱发 3 份货也是自洽的，**只有收 3 发 1 才是资损**——单独任一条都会让缺陷看起来「账平了」。而发放份数**只有供应方数得清**：平台侧的履约明细只有状态没有数量，对账十五项也不比对这个维度，故 `ProviderLedger` 本轮补了 `grantedQty` 记账——与「重复发奖 = 0 取下游账本」是同一条理由。

#### 关于 `benefit_snapshot`

在 `createTrade` 时从 `benefit_sku` → `benefit_package` → `benefit_item` 组装并落库，履约时只读快照、不再查配置表。这样即使运营改了权益包，历史订单仍按下单时的配置履约。V1 就要这么做 —— 后改要洗数据。

#### `grantBenefit` 重入怎么处理

V1 虽然是 happy path，但 `grantBenefit` 会被重复调用（重复的支付回调、V2 的任务重试）。**这条路径上有三处会命中约束，都不是错误**：

| 位置 | 现象 | 处置 |
| --- | --- | --- |
| 条件更新 `NOT_START → GRANTING` | `affected_rows = 0` | 读出当前 `grant_status`，按下表分支 |
| 插入 `op_record(GRANT_BENEFIT, '')` | `uk_biz_op` 冲突 | **upsert**：`ON DUPLICATE KEY UPDATE retry_count = retry_count + 1` |
| 插入 `benefit_fulfillment_record` | `uk_biz_item` 冲突 | **upsert**：命中则更新 `provider_order_no` / `grant_status`，不新增行 |

**这三处必须写成 upsert 而非 insert**，否则第二次调用抛 `DuplicateKeyException` 中断链路，而重入的正确行为是正常返回。

按 `grant_status` 的分支：

| 已有 `grant_status` | 处置 |
| --- | --- |
| `NOT_START` | 正常首次执行 |
| `GRANTING` | 继续走发放流程 —— `reward.grantReward` 按 `opNo` 幂等，返回原结果；`benefit_fulfillment_record` 走 upsert 更新为最新结果 |
| `GRANT_SUCCESS` | 直接返回原结果，**不再调用 reward** |

**正确性由 reward 侧的 `uk_op_no` 兜底，不由 benefit 侧的状态判断兜底。** 即使两个线程同时进入 `GRANTING` 分支，`grantOpNo` 是确定性派生的（`bizNo + '_G_' + providerType`），reward 侧只会有一条记录、只发一次奖。状态判断只是避免无谓的 RPC，是优化不是保证。

V2 引入任务调度后，`GRANTING` 分支改为交给查单任务收敛，不再直接重发。

#### `op_record(GRANT_BENEFIT)` 为何跨两个事务

`grantBenefit` 的 `op_record` 先写 `PROCESSING`（事务 A）、调用完成后回写 `SUCCESS`（事务 B），这与 `CREATE_TRADE` / `PAY_CALLBACK` 一次性写 `SUCCESS` 不同。

原因是它包含**跨服务调用**：调用发出前必须先留痕（否则 RPC 发出后崩溃就没有任何记录），调用结果回来后才能判定终态。这正是终态设计中「`op=PROCESSING` + 状态置 `GRANTING` + 查单任务，三者同一事务提交后才发 RPC」的形状（技术方案 §5.3 ④）—— V1 只是暂时缺了查单任务这一项。

**代价**：事务 A 与 B 之间崩溃，`op_record` 永久停在 `PROCESSING`，V1 无机制收敛。这与 §7.3 第 2 条是同一个缺口，V2 的任务表一并补上。

#### 关于 ②→③ 的调用位置

**这是 V1 的临时形态。** V2 改为「payCallback 事务内落 `GRANT` 任务，调度器驱动 `grantBenefit`」，因为任务表在 V2 才引入。冻结项 5（事务边界收成一个方法）保证了这次改动只影响一个方法内部。全部临时形态见 §7.3。

**调用位置必须在事务提交之后**，不在事务内 —— 事务内调 RPC 违反《开发规范》§7.4。V2 改成任务驱动时，正好是在事务内加一行 `insert`、删掉这行同步调用。

**代价要说清楚**：事务提交后、`grantBenefit` 调用前若进程崩溃，订单会停在「已支付未履约」且**没有任何机制能恢复** —— V1 没有任务表。这是 V1 接受的已知缺口，V2 的任务表就是为了补上它。演示时不要刻意制造这个场景。

**`itemSeq` 的口径**：**相对于本次调用的 `rewardItems` 列表，从 0 起连续编号**，不是订单内全局下标。

因为 `grantOpNo` 的粒度是「一次调用 = 一个供应方」，按 `provider_type` 分组后每组是**独立的一次调用、独立的 `opNo`**，各组的 `itemSeq` 都从 0 开始。`reward_grant_item.uk_op_item(op_no, item_seq)` 的第一维已经隔开了不同组，不会冲突。

以 seed 数据为例（项 A 属 `PROVIDER_A`、项 B 属 `PROVIDER_B`）：

| 调用 | `opNo` | `rewardItems` | `itemSeq` |
| --- | --- | --- | --- |
| 第一次 | `BZxxx_G_PROVIDER_A` | [项 A] | 0 |
| 第二次 | `BZxxx_G_PROVIDER_B` | [项 B] | 0 |

**两次调用的 `itemSeq` 都是 0，这是正确的。** 若误写成全局下标（0 和 1），`benefit_fulfillment_record` 与 `reward_grant_item` 的对应关系就要额外维护映射。

**`playType` 在 V1 的取值**：恒为 `BENEFIT_SELL`（`reward_grant_record.play_type` 是 `NOT NULL`，必须传）。它的作用是让 reward 侧能按玩法维度做路由与对账，V3 接裂变时传 `FISSION`。V1 就要传对，不要留空或传 `null`。

**签名自检**：裂变的师徒双向发奖调用它时，`playType` 传 `FISSION`、`bizOrderNo` 传裂变关系号、`opNo` 传 `outFlowNo + '_FL'`、`receiverId` 传徒弟 userId、`rewardItems` 传奖励包展开项。**能原样调用，不需要改签名。**

#### 「V1 只实现 SUCCESS 分支」的准确含义

冻结项 2 说其余三个分支 `throw UnsupportedOperationException`，指的是**处理下游返回值的 `switch` 分支**，不是禁止 `PROCESSING` 这个值出现在数据库里。

| 位置 | V1 是否出现非 SUCCESS |
| --- | --- |
| mock 下游的**返回值** | 否，固定 `SUCCESS` |
| 调用方处理返回值的 `switch` | `FAIL`/`PROCESSING`/`UNKNOWN` 三个 case 抛 `UnsupportedOperationException` |
| `reward_grant_record.result` **落库中间态** | **是** —— 调用下游前先落 `PROCESSING`，返回后回写 `SUCCESS` |
| `play_op_record.status` 落库中间态 | **是** —— 同上，`GRANT_BENEFIT` 先 `PROCESSING` 后 `SUCCESS` |

**「调用前先落中间态」是必须在 V1 就做对的形状**：若省略这一步、等结果回来才插记录，则 RPC 发出后崩溃将没有任何痕迹 —— 这正是 V2 查单收敛所依赖的锚点。V1 缺的只是「查单任务」，不是「中间态」。

**mock 支付不自动回调。** `createPay` 只返回 `tradeNo`，不异步触发 `payCallback`。回调由外部触发：

| 场景 | 触发方式 |
| --- | --- |
| 集成测试 | 测试代码主动调用 `payCallback`，自行构造 `notifySeq` |
| 手工演示 | `curl` 打 gateway 的 `/api/benefit/pay-callback` |

**不做自动回调的理由**：自动回调会让「支付完成」变成一个看不见的异步过程，演示时无法暂停在「已付款未履约」这个中间状态观察，V2 要注入回调乱序、重复投递时也无从下手。真实支付平台的通知本来就是外部事件，mock 保持这个形状是对的。

V1 不做验签 —— 签名校验是 L1 防线，V2 随咨询凭证一起做。

**`/orders`、`/sku/{skuId}`、`/order/{bizNo}/op-records` 三个是只读查询**，为端侧列表与排查而加，见 §4.6 的说明。三者均无副作用：不写状态、不落操作记录、不调下游，故不进 `OrderTxService`、不携带幂等键。`ReadOnlyQueryIT` 对此有断言 —— 查询前后主单状态、操作记录行数、履约行数、发奖记录数均不变。只读接口若意外落了操作记录，会污染幂等键空间与对账口径（对账按操作记录比对，多出来的行会被当成真实业务动作）。

`/api/benefit/orders` 用复数与单查的 `/api/benefit/order/{bizNo}` 区分。状态筛选项取值非法时返回 `4001` 而非当作「查不到」回空列表 —— 后者会让端侧把拼错的枚举名误读成「该状态下没有订单」。`grantStatus` 只接受带 `GRANT_` 前缀的主单取值，传明细态的 `SUCCESS` 会被拒绝。

`RetStatus` → HTTP `code` 的转换规则：

| RetStatus | code | 说明 |
| --- | --- | --- |
| `SUCCESS` | `0` | |
| `FAIL` | 原 `retCode`（`1xxx`/`4xxx`） | 展示给用户 |
| `PROCESSING` / `UNKNOWN` | `0`，`data.status` 标记处理中 | **对端不返回失败** —— 结果未定时告诉用户「失败」，用户会重试，形成重复下单 |

上表是终态规则。V1 下游固定成功，仅 `SUCCESS` 一行被真实走到，`data.status` 字段与其余三行的分支留待 V2 填实现。

**业务拒绝与请求级失败分开处置**：业务拒绝走 HTTP 200 + 业务码，由端侧按 `code` 分支；路由不存在、方法不支持、报文不可读属请求级失败，保留框架给出的 4xx，仅套用统一响应壳。二者不可合并 —— `5xxx` 的语义是「结果未知，按 UNKNOWN 查单收敛」，若把客户端错误记为 `5001`，调用方会为一件未发生的事发起重试与对账。

**`mp-common` 里两个工具类是 V1 必须有的**，把《开发规范》§5 的规则集中在一处，review 只需盯这两个类：

```java
/** 业务单号：全局唯一，每次调用必须不同。UUIDv7 —— 近似有序且随机空间充足 */
public final class BizNoGenerator {
    public static String bizNo()         { return gen("BZ"); }   // play_biz_record_no
    public static String fulfillmentNo() { return gen("FF"); }   // 履约明细号
    private static String gen(String prefix) {
        return prefix + UuidCreator.getTimeOrderedEpoch().toString().replace("-", "");
    }
}

/** 幂等键：确定性可重算，同一操作重试必须得到同一个值 */
public final class IdempotentKeys {
    /** 履约发奖：一次调用 = 一个供应方 */
    public static String grantOpNo(String bizNo, String providerType) {
        return bizNo + "_G_" + providerType;
    }
    /** 支付回调 —— payStatus 不入键 */
    public static String payCallback(String tradeNo, String notifySeq) {
        return tradeNo + "_" + notifySeq;
    }
    // V2 补：closeOrder；V3 补：refundNo、revokeNo、followerGrantNo、sponsorFlowNo
}
```

**两个类的规则相反**，放在一起是为了让这个反差在代码里可见：`BizNoGenerator` 必须用随机源，`IdempotentKeys` 禁止随机源。合并为一个工具类是常见的错误起点。

**不用「时间戳 + 8 位随机」**：32 bit 随机空间在同一秒内约 7.7 万次调用即有 50% 碰撞概率，压测（500 VU）与并发重试下不是理论风险。UUIDv7 前 48 bit 是毫秒时间戳，同样近似有序（降低 B+ 树页分裂），但随机空间足够。理由详见《开发规范》§5.2。

**无论生成器多可靠，插入路径都要处理唯一冲突**：捕获 `DuplicateKeyException` → 重新生成 → 重试，最多 3 次。生成器是概率保证，唯一索引是确定性保证。

#### 缺陷

四处，均由实施期自查与集成测试发现。

**① `@Transactional` 同类内部调用静默失效。** 初版事务方法与编排逻辑同在 `BenefitOrderServiceImpl`，注解不经代理、不生效、不报错，后果是状态已改而操作记录未落库。修正：抽出 `OrderTxService`，五个事务方法各为一个事务单元。

**② 全局异常处理器把请求级失败吞成 `5001`。** `HttpEndpointIT.grantBenefitIsNotExposedOverHttp` 发现：不存在的路由期望 404，实测 500。`@ExceptionHandler(Exception.class)` 捕获了 `NoResourceFoundException`。修正：继承 `ResponseEntityExceptionHandler`，沿用框架的状态码映射，仅覆写响应体包装。

冻结项 8 的表述据此修正为：业务拒绝 → `FAIL`；**业务逻辑内**的未预期异常 → `UNKNOWN`；**未进入业务逻辑**的请求级失败（路由不存在、方法不支持、报文不可读）→ 保留框架 4xx。

**③ 建单时两种唯一冲突被合并处理。** 初版 `catch (DuplicateKeyException)` 一律按幂等命中返回原单。`uk_biz_no`（单号碰撞）应换号重试，`uk_idempotent`（幂等命中）才返回原单，合并的后果是碰撞时返回另一用户的订单。修正：`insertOrder` 以幂等键回查区分，碰撞时换号，上限 3 次。

**④ pre-commit 钩子在非交互 shell 下找不到 `JAVA_HOME`。** git 钩子不读 `.zshrc`，表现为终端 `mvn` 正常、提交即失败。修正：钩子自行解析 JDK 路径，按《环境与依赖》§1.1 的 brew formula 路径兜底。

### 5.3 故障注入控制面

**注入模式必须区分「下游已执行」与「下游未执行」。** 若注入实现为「抛异常且不落库」，则 `UNKNOWN` 收敛时查到「未发放」并重发，结果正确 —— 但该场景下即使把 `UNKNOWN` 误判为 `FAILED` 走补偿，结果同样正确。四分类的价值在此场景不可见。

需要构造的是**下游已执行成功但调用方未收到结果**：mock 先记账，再抛超时。此时误判 `FAILED` 触发补发即为重复发放。

**mock 必须持有独立账本**。`reward_grant_record` 是平台侧记录，且在调用 mock 之前就已落 `PROCESSING`（§4.2 三段式）—— 对它计数只能证明平台幂等，不能证明供应方实际只发了一次。「下游已执行」必须建模在服务边界的另一侧：

- mock 供应方维护自有账本，键为 `opNo`，put-if-absent 语义等价唯一索引。不落四个业务库 —— 外部系统的存储不属于平台 schema，进程内结构即可，重启丢失可接受（mock 无状态重启本就是允许的）
- 契约补 `MockProviderService.queryGrant(opNo)`，返回账本中的结果与 `providerOrderNo`；**查无返回 `UNKNOWN`**，不返回 `FAIL` —— 查无可能是提交在途，判失败会触发误补偿（§7.3 缺陷 9 同源）
- 「无重复发放」的最终断言落在两侧：平台记录计数 1，且 mock 账本中该 `opNo` 的 `providerOrderNo` 与平台侧一致、全程不变

| 模式 | mock 行为 | 期望收敛 |
| --- | --- | --- |
| `SUCCESS` | 正常返回 | 默认 |
| `TIMEOUT_AFTER_COMMIT` | **先写账本**，再抛超时 | 短退避查单 → 查得 → `GRANT_SUCCESS`，不重发；两侧账本各 1 条 |
| `TIMEOUT_BEFORE_COMMIT` | 不写账本直接抛超时 | 短退避查单 → 连续查无达阈值 → 以**原 `opNo`** 重发；最终两侧各 1 条 |
| `PROCESSING` | 受理但不完成，第 N 次查单转成功 | 长退避，退避序列与短退避不同 |
| `FAIL` | 确定失败 | 唯一允许走失败分支的一类 |

**查无不立即重发**。`queryGrant` 查无返回 `UNKNOWN`，单次查无不足以判定「原调用未到达」—— 可能只是下游提交延迟。规则：`QUERY_GRANT` 连续查无满 3 次（短退避跑完一轮）才落 `GRANT` 任务重发，且必须复用原 `opNo`。

> **「连续」须按字面实现**（V2 PR-3 实施时补充）：计数不能复用任务的 `retry_count`——后者由调度器对所有非终态结果自增，`PROCESSING` 也算在内，于是「连续查无 3 次」会退化成「查询 3 次且最后一次查无」。下游回过一次 `PROCESSING` 即表明它已受理这笔请求，此后的查无更可能是查询侧抖动，重发就成了对一笔已受理的请求再发一次。计数独立存于任务 `payload`，遇 `PROCESSING` 归零。该阈值的误判是安全的：若原调用实际已到达，重发携带同一 `opNo`，被 mock 账本 put-if-absent 挡下并返回原 `providerOrderNo` —— 幂等键复用让「重发时机判早了」不构成资损，判晚了只是收敛慢。

模式经 HTTP 端点在运行期切换，作用于 mock 供应方与 mock 支付两侧。自动化测试与人工验证共用同一入口。

**不做成 Spring Profile 或测试作用域 Bean**：手动验证在运行中的实例上进行，需要在不重启的前提下切换模式。

### 5.4 收敛过程可观测

`queryOrder` 只返回三条子状态的当前值。V2 的退出标准 1、3 断言的是迁移序列与退避间隔，终态查询无法区分「正确收敛」与「未发生故障」。

新增只读端点，按 `bizNo` 返回：

| 来源 | 字段 | 用途 |
| --- | --- | --- |
| `play_op_record` | `op_type`、`status`、`downstream_result`、`retry_count` | `status` 与 `downstream_result` 分列承载本地执行态与下游四分类结果（技术方案 §6.6），合并即无法区分 `PROCESSING` 与 `UNKNOWN` |
| `benefit_task` | `task_type`、`status`、`retry_count`、`next_time`、`lease_owner`、`lease_expire` | 当前退避位置与租约持有者 |

**端点提供的是快照，序列由观察者累积**。`benefit_task` 每轮重试原地覆盖 `next_time` / `retry_count`，表中任一时刻只有当前值，不存在「相邻两次」。两类观察者各自累积：

- 自动化测试：调度器触发改为测试内显式驱动（`scheduler.runOnce()`），每驱动一轮立即读一次端点，序列保存在测试变量中。不依赖真实时间流逝，也不依赖轮询碰运气
- 人工验证：脚本按固定间隔轮询该端点，逐次记录 `retry_count` 与 `next_time`，形成 5.8 的「状态迁移序列」列

**不为序列建事件日志表**：它只服务验收观察，落库会让一张仅测试使用的表混进业务 schema，且每轮重试多一次写放大。终态方案里收敛历史的正式载体是 `play_op_record.retry_count` 与对账（技术方案 §6.8），不是逐次快照。

该端点同时是演示入口：「注入超时 → 观察 `GRANT_UNKNOWN` 停留 → 三次退避后收敛 → 发放记录仍为 1 条」为可现场复现的完整序列。

**V3 拆分布式后该端点需加鉴权或下线**，届时它将暴露跨服务的内部单据状态。

### 5.5 `payCallback` 放开 `CLOSED`

V1 的 `parsePayStatus` 对 `CLOSED` 返回 `4001`（§4.2）。退出标准第 5 条要求验证「先 `SUCCESS` 后 `CLOSED`」的乱序拦截，故 V2 须放开该值，否则第二条通知在参数校验处即被拒，执行不到条件更新。

放开后三个值的条件更新谓词，照录技术方案 §6.4 的条件更新清单，无新增推导：

| `payStatus` | 条件更新 |
| --- | --- |
| `SUCCESS` | `SET pay_status='PAY_SUCCESS' WHERE pay_status IN ('WAIT_PAY','CLOSING')` |
| `FAILED` | `SET pay_status='PAY_FAILED' WHERE pay_status='WAIT_PAY'` |
| `CLOSED` | `SET pay_status='CLOSED' WHERE pay_status IN ('WAIT_PAY','CLOSING')` |

`SUCCESS` 的前置状态含 `CLOSING`：关单受理后、确认前用户完成支付时，支付成功必须能够推进，否则钱已收而订单被关。这条入边是 V2 新增的路径中唯一「拦截了反而资损」的一条，退出标准第 6 条单独覆盖。

**`payStatus` 仍不入幂等键**（《开发规范》§5.5）。理由是键的构成原则而非乱序场景 —— 乱序的 `SUCCESS` 与 `CLOSED` 本就携带不同 `notifySeq`，各自成键、各自留痕，拦截本来就只能靠条件更新。`payStatus` 不入键，是因为它是**被通知的结果**而非**操作的标识**：键中混入结果字段后，同一条通知（同一 `notifySeq`）重传时若该字段被上游修正，重传会被当成新操作插入成功，`uk_biz_op` 挡重传的职责即告失效。

`op_seq` 仍取 `notifySeq`（《开发规范》§5.6）—— 三个 `payStatus` 是三个不同的业务事件，各自留痕。

### 5.6 关键取值与依据

十二项技术方案未给出取值或实现方式，此处定下，实施按此执行。第 ⑧ 项为 PR-4 实施时补入，第 ⑨ 项为 PR-5，第 ⑩ ⑪ 项为 PR-6a/6b，第 ⑫ 项为 PR-7a。

**① 跨库约束：配四个分库账号。**

四个 schema 位于同一 MySQL 实例时，多数据源只拦截不带库名限定的引用。实测：`SELECT ... FROM benefit_sku JOIN other` 报 `ERROR 1146`，`SELECT ... FROM db_reward.benefit_sku JOIN db_benefit.other` 正常返回。仅配多数据源，《开发规范》§4.5 的「禁止跨库 JOIN」在运行期无强制力。

在 `docker/mysql-init` 中为四库各建一个仅授权自身 schema 的账号，各数据源使用各自账号：

```sql
CREATE USER 'mp_reward'@'%' IDENTIFIED BY 'mp_reward';
GRANT ALL PRIVILEGES ON db_reward.* TO 'mp_reward'@'%';
-- 其余三库同构
```

代价是本地排查不能再用单一连接跨库查数，需按库切换账号。收益是约定变为约束，且 V3 拆实例后连接形态不变 —— 届时只改 host，不改权限模型。

**② 事务管理器按库绑定，禁止无限定的 `@Transactional`。**

四套 `DataSource` 意味着四个 `PlatformTransactionManager`。Spring 对不带 `transactionManager` 属性的 `@Transactional` 按类型注入取 `@Primary`—— 若 `OrderTxService` 的事务落到别库的管理器上，`db_benefit` 的写各自自动提交，「状态、操作记录、任务同库同事务」（技术方案 §6.5 本地消息表的前提）静默失效，**不报错**。这与 V1 缺陷 ①（同类调用注解不生效）同属一族：事务问题的失效形态是「没有事务」而非「事务出错」。

处置三条：

- 每库独立 `SqlSessionFactory` + `TransactionManager`，Bean 名带库前缀（`benefitTransactionManager` 等）
- 每模块定义组合注解（如 `@BenefitTx` = `@Transactional(transactionManager = "benefitTransactionManager")`），业务代码只用组合注解
- `ShapeFreezeTest` 增加静态检查：`*TxService` 中出现不带 `transactionManager` 属性的裸 `@Transactional` 即失败；同时以运行期回滚 IT 验证绑定正确（退出标准第 11 条）—— 静态检查证明「写了限定」，回滚 IT 证明「限定指向了正确的库」，缺一不可

**这条规则管的是「怎么加」，不是「哪里必须加」。** V3 PR-10 后置 review 提过一条意见：「`ManualRepairService` / `ReconcileService` 缺 `@BenefitTx`」。核实后**加上才是缺陷**，两个类各错一种：

- `ReconcileService` 调 `rewardService.batchQueryByOpNos`（跨库 RPC），且一轮扫十项、每项 200 行。包进事务违反 §7.4「事务内禁止 RPC」与冻结标准 26，还会让一项失败拖垮整轮（`run()` 的逐项异常隔离随之失效）。**而标准 26 的检查只读 `OrderTxService.java` 一个文件**（其注释原话：「全部事务边界收在 OrderTxService，故只需检查这一个类」）—— 所以这处违规它自己检查不出来。
- `ManualRepairService` 加上会真的生效（跨 bean 调用），代价是 `@BenefitTx` 带 `rollbackFor = Exception.class`：三个动作在**落审计之后**才抛 `BizException`，包事务会把审计行一起回滚。而「审计先于动作、动作失败也要留痕」是它明写的约束——**开了口却不留痕，比不开口更糟**。注入实测确认：加上注解后 `auditSurvivesFailedAction` 立刻转红。

真正的缺陷是类注释里「审计与动作**同事务**落库」这句话与实现不符——那句话的论据是「不另开审计表」，说的是同一张表，「同事务」属措辞不准。**改注释，不改行为**，并新增一条静态守卫断言这两个类不带事务注解：**这类「看起来漏了」的结论必须固定下来，否则每轮 review 都会重提一次**。

**③ 任务表的写回全部携带 fencing 条件。**

技术方案 §7.3 给了领取的 SQL，未给写回的。租约保证的接管窗口存在一个残余竞争：A 持有任务但执行变慢，租约过期，B 依租约语义正当接管并完成；随后 A 苏醒，把同一任务再写一遍终态，或续租把 B 的租约覆盖。A 的写不拦下，接管就只在「A 真死了」时正确，而租约过期无法区分「死了」与「慢了」。

处置：完成、失败重排、续租、死信四类 UPDATE 一律追加持有者校验 ——

```sql
UPDATE benefit_task SET ...
 WHERE id = ? AND status = 'DOING' AND lease_owner = ?
```

`affected_rows = 0` 即租约已被接管，当前实例立即放弃该任务且不得重试本次写回。业务副作用无需回滚 —— A 若已调了下游，B 接管后携带同一 `op_no` 重做，被下游幂等挡住，这正是「幂等键复用」承担的兜底。

**④ 租约 30 秒，任务执行超 20 秒续租一次。**

租约需长于单次任务执行耗时，否则任务执行中租约到期、被另一实例接管，同一任务并发执行两次；需短于可接受的故障接管延迟，否则实例宕机后任务长时间无人处理。V2 的任务均为单次 RPC + 两个短事务，正常耗时在百毫秒级，30 秒留了两个数量级的余量。续租阈值取租约的三分之二。

**⑤ 死信阈值：查单类 10 次，执行类 5 次。**

两类任务的失败语义不同。查单（`QUERY_GRANT` / `QUERY_CLOSE`）是读操作，重试无副作用，且 `PROCESSING` 本就可能持续较久，阈值可高；执行类（`GRANT` / `STOCK_RELEASE`）每次重试都是一次下游调用，连续 5 次失败已说明不是瞬时故障。

按长退避序列，查单 10 次约覆盖 1 小时，超出即需人工介入。

**⑥ 可观测端点：V2 无鉴权，V3 移入独立的运维端口。**

V2 单进程、仅本地运行，加鉴权无收益。V3 拆分布式后该端点会暴露跨服务的内部单据状态，届时移至独立端口并与业务端口分离，不对外网暴露。这与 `dubbo.application.qos-enable` 的处置一致。

**⑦ 任务的时间基准取数据库时钟，应用不传绝对时刻。**

调度判据是 `next_time <= NOW(3)`，右侧恒为数据库时钟。若 `next_time` 由应用侧 `LocalDateTime.now()` 写入，则是「拿 JVM 时钟写、拿 DB 时钟比」——两个时钟一旦不一致，任务要么永不到期、要么全部立刻到期。

PR-2 实施时即遭遇：Testcontainers 起的 MySQL 默认 UTC，而 JDBC URL 声明 `Asia/Shanghai`，`next_time` 比容器的 `NOW(3)` 超前 8 小时，调度器一条任务也领不到，表现为「履约不执行」而非任何时间相关的报错。

因此入队接口的入参是**延迟秒数**而非时刻，`next_time` 由 `DATE_ADD(NOW(3), INTERVAL ? SECOND)` 在库内算出。V3 多实例部署时这一点更关键：实例间时钟漂移会让调度时快时慢且无法复现。同理，退避后推也走 `NOW(3)`，`retry_count` 由 SQL 自增而非应用读出加一回写——后者在接管场景下会用陈旧值覆盖接管者的计数。

**⑧ 咨询凭证：HMAC-SHA256，有效期 15 分钟，密钥只从配置读。**

技术方案 §6.2 定了「HMAC 签名 + 时效」与绑定项，未给具体算法、有效期与密钥来源。PR-4 实施时定下，三条各有依据：

- **HMAC 而非加密**。载荷里没有秘密——用户自己的 ID、他正在看的商品、他看到的价格，都是他已经知道的。要防的是**篡改**，不是窥视。用加密解决完整性问题会带来一种错觉，以为「解得开就是真的」，而截断或重放的密文同样解得开。
- **有效期 15 分钟**，够用户看完权益详情再下单，又短到凭证泄露后价格早已刷新。**过期时刻在签发时算定并进签名**，不由消费侧传入——否则持有者可自行延长有效期，时效约束不成立。
- **密钥不设代码内默认值**。给了默认值，缺配置时应用照常启动、签名照常验过，而那把密钥在仓库里人人可见。失效形态是「一切正常」，与 §5.6 ② 的事务管理器同族，故以 `ShapeFreezeTest` 静态拦住 `@Value("${...:默认值}")` 的冒号形态。

**签名器落在 `mp-common` 而非 `mp-activity`**：技术方案 §4.2 明确「Token 解密不放在 activity」——解密结果含裂变组等玩法私有概念，放公共能力层就成了公共层依赖玩法层，方向反了。故做成公共 SDK，各玩法自行调用。

**载荷字段以控制字符分隔，且签发时拒绝含分隔符的值。** 用普通字符拼接时，`userId="ab" + activityId="c"` 与 `userId="a" + activityId="bc"` 会拼出同一个串、算出同一个签名，攻击者可据此挪走字段边界。

**验签之后必须逐字段比对**（退出标准第 16 条）。签名只证明「这张凭证是平台签发的、没被改过」，不证明「它是发给当前这个请求的」——用户 A 的合法凭证在用户 B 的请求里同样验签通过。

**静态检查须断言比对表达式本身，不能只断言字段名出现过。** 仅检查 `getUserId()` 在方法体内出现时，紧随其后的 `log.warn` 同样携带这三个 getter —— 将比对整体替换为 `true` 后检查仍通过。「提到了某个字段」与「拿它做了判断」是两回事。

**绑定项要按「它决定什么」来定，不能按「它叫什么」。** PR-4 初版签了 `activityId` 与 `configVersion` 就以为版本这一维已覆盖，而权益内容实际取决于 `sku.packageVersion` —— 名字里都有「version」，管的却是两件事。漏签的后果见退出标准第 16 条的第六类。

由此得出一条通用判据，V3 加城市、渠道、风控等绑定项时同样适用：**凡是会改变「用户看到的承诺」的字段，都必须进签名并比对**；只进签名不比对等于只留了审计痕迹，拦不住任何东西。反过来，不改变承诺的字段（如 `configVersion`）不作为拒绝依据，否则每次无关改版都会打断在途的下单。

**⑨ 限购数量挂在 SKU 上，周期键 V2 只用 `TOTAL`。**

技术方案 §3.4 定了 `user_purchase_quota` 的结构与 `period_key` 的取值形态（`TOTAL` / `D20260802` / `W202631`），未说限额从哪来。`benefit_sku` 已有 `purchase_limit_rule_id`，但 V2 不建限购规则表——规则表要承载周期、人群、叠加策略，属 V3 运营配置化范围。故在 `benefit_sku` 上补一个 `purchase_limit_qty` 列，V3 建规则表后改由规则快照填充，扣减逻辑不变。

**`0` 表示不限购，且不建额度行**。用 `NULL` 会让「没配规则」与「配了 0」无法区分，而后者语义上是「一件都不能买」。实现上也必须跳过建行——建一行 `limit_qty = 0` 的记录会让后续每次扣减都撞 `used_qty + qty <= 0` 而失败，等于把「不限购」实现成「一件都不能买」。

**周期键 V2 固定 `TOTAL`，不用当前日期拼**。日限购要等 V3，届时周期键须**随单据固化**而非每次现算：用户 23:59 下单、次日 00:01 超时关单，若关单时现算周期键，还的是新一天的额度，旧那天的永远还不回来。

**扣减的上限谓词读行内 `limit_qty`，不读应用传入的值**。传进来的那份是下单时从 SKU 读的快照，与本行可能不一致（运营刚调过限额）。以行内为准，「限额是多少」就只有一个来源。

**⑩ 关单与查单复用同一个下游接口，mock 支付方持有独立账本。**

技术方案 §4.5 给了关单的四分类分支，未说「怎么问支付方」。PR-6 实施时定下三条：

**`closePay` 一个接口既关单又查单**，不另开 `queryPay`。两者要问的是**同一个问题**——这笔到底支付了没：关单本身就要先确认对方是否已支付（已支付则不能关），而 `QUERY_CLOSE` 收敛要的也是这个答案。分成两个接口则两处的判定逻辑迟早漂移，而它们必须给出一致的结果。

**mock 支付方必须持有独立账本**（`PayLedger`），与 §5.3 对供应方账本的要求同源：

> 「已支付」这个事实只存在于**服务边界的另一侧**。平台的 `pay_status` 只能证明平台知道什么，证明不了支付方那边有没有收到钱——BR-B-17「关闭与支付并发时以支付系统结果为准」正是这个意思。

若 mock 只按注入模式机械返回，「已支付的单不能关」这条分支根本走不到：平台问「能关吗」，mock 答「能」，而它根本不知道这笔付没付。故账本记 `CREATED/PAID/CLOSED`，关单以它为判据；**注入模式只决定「这次调用能不能拿到结果」，账本决定「结果是什么」**。

**演示入口 `POST /api/fault/pay-ledger/{outTradeNo}/paid`**：真实链路里「用户付款」发生在收银台，mock 没有收银台，故留一个显式入口把账本置为 `PAID`。它**不等于发一条支付成功通知**——只改支付方账本，平台状态不动。两者的区别正是这个端点存在的理由，也是「已支付的单拒绝关闭」这条用例能成立的前提。

**⑪ 支付通知验签：HMAC-SHA256，密钥独立，V2 不做防重放。**

PRD FR-B03 ① 要求「验证签名、时间戳、防重放」，未给形态。PR-6b 实施时定下四条：

**签名覆盖全部业务字段，不只是金额。** 只签金额则攻击者可以拿一条真实通知改掉 `outTradeNo`，把 A 单的付款算到 B 单头上——金额没变，签名照样对。字段按名称排序后拼接，签发侧与验签侧只要集合一致就能对上，不必约定传参顺序。

**密钥与咨询凭证分开配置**（`mp.pay-notify.secret`）。两者是不同的信任边界：

| | 咨询凭证 | 支付通知 |
| --- | --- | --- |
| 签名方 | 平台自己 | 支付平台 |
| 挡什么 | 用户伪造自己的下单请求 | 伪造的收款成功通知 |
| 泄露后果 | 只影响下单校验 | 可伪造收款通知，直接资损 |

共用一把还会让「轮换支付方密钥」被迫连带作废所有在途凭证。

**验签必须是 `payCallback` 的第一件事，先于定位主单。** 顺序不是风格问题：金额校验要读主单，那意味着未验签的请求已经能通过响应差异探测「这个 `bizNo` 存不存在」「它的应付金额是多少」。**信任边界之外的输入，在通过验签以前不该触碰任何业务数据。**

**BR-B-12「未通过验签的通知不得更新任何业务状态」中的「任何」按字面理解**：状态、操作记录、可靠任务，一样都不能留。留痕看似无害，实则给了攻击者一个无需密钥就能写库的入口。

**V2 不做时间戳窗口与防重放**，记为 V3 待办。验签挡伪造、`uk_biz_op`（幂等键 `tradeNo + '_' + notifySeq`）挡重传，主要风险已覆盖；时间戳窗口挡的是「截获一条真实通知、隔很久重放」，而那条通知的 `notifySeq` 会被唯一键挡下，重放拿不到额外好处。V2 单进程本地跑，加窗口校验还要处理平台与支付方的时钟偏移，收益不抵复杂度。V3 上真实环境时补。

**⑫ L2 锁做成可关闭的开关，去锁对照组进 CI。**

技术方案 §6.3 给了锁的形状（`tryLock(0, LEASE)`、显式租约、解锁判持有者），退出标准第 15 条要求「移除 Redisson 的对照组与第 14 条正确性结果完全一致」。PR-7a 实施时把这条从**手工压测**提前到了 **CI 每次跑**：

`BizLock` 由 `mp.lock.enabled` 整体开关，`LockDisabledCorrectnessIT` 用 `@TestPropertySource` 关掉它，与开锁组压同一批场景。两组都在 `mvn verify` 里，这条对照关系因此不会随时间失守。

> 命令行 `-Dmp.lock.enabled=false` **不进入** `@DynamicPropertySource` 构造的上下文，此时跑出的「对照组」实为开锁组。须用 `@TestPropertySource` 让 Spring 另建一个上下文。

**开了锁的并发测试，覆盖不到锁本应保护的路径。**

把「幂等命中返回原单」那段删掉（即不捕获 `DuplicateKeyException` 分流），**开锁组四条用例全绿，只有去锁组变红**——因为锁把并发串行化了，第二个线程进临界区时第一笔单已提交，走的是「先查后得」而非「唯一索引冲突」，该分支未被执行。

这不是用例写得不好，是并发测试的固有性质：**锁越有效，越难压出底层的竞争**。所以两组必须成对存在，去锁组不是「顺便验一下」，而是唯一能验证 L3 的手段。

**另一件：并发用例压的是哪一道闸，取决于请求怎么构造，不取决于并发本身。** 同一 `notifySeq` 的并发投递压的是 `uk_biz_op`（唯一索引把第二条挡在条件更新之前），压不到主单谓词；要压谓词得用**不同 `notifySeq` 的乱序通知**。以前一种方式构造时，删除谓词后两组仍全绿；换用后一种方式方能暴露。

**已在技术方案中给出，此处不重复决策**：`CLOSING` 阶段不落任何库存任务，待 `QUERY_CLOSE` 收敛到 `CLOSED` 或 `PAY_SUCCESS` 后由确定的一方落任务；库存类任务的 `op_no` 取 `biz_no + '_' + task_type`（技术方案 §7.4）。

**「0 超卖」必须三处同时断言，缺一不可**：

| 断言 | 单独成立时仍可能漏掉的 |
| --- | --- |
| 成功计数 = 库存 | 接口返回成功但没真建单 |
| `total-locked-consumed` 终值 = 0 | 扣减写成「读-改-写」时数算对了，但订单多出几行 |
| 订单表实际行数 = 库存 | 库存被多扣（少卖），订单数对但可售余量为负 |

**超卖的失效形态是「全部成功」**——每个请求都拿到订单、均无异常，只是售出量超过库存量。故判据是数量关系而非「有没有报错」。

**并发用例必须用真实线程池压同一行**，不能串行调用 N 次：串行永远测不出「两个线程同时读到还剩 1」，而那正是要防的。第 18 条同理——「先查 `used_qty` 再更新」在串行下完全正确，并发下 N 个线程会同时查到 0 然后各自加一。

**「库存任务重复执行」必须构造为「另有一笔单占着库存」**：单笔单场景下释放后 `locked` 归零，第二次释放被下界拦下，用例通过的原因是下界生效，而非每单幂等生效。两者的区别与承重点见技术方案 §7.4。

判据分两组，挡的是**两类不同的失效**，缺任一组另一组都补不上：

- **验签 + 逐字段比对**挡伪造与越权。「他人的合法凭证」与「他物的合法凭证」两条是这一组的核心：那两张凭证由平台签发、签名正确、未过期，**验签这一关完全通过**，只有逐字段比对拦得住。只验签不比对时，其余用例全绿，仅这两条会红。
- **服务端重算比价**挡「凭证合法但价格已过时」—— 凭证是平台自己签的、字段也全对，只是运营在咨询之后改了价。

**两个场景缺一不可**。秒杀场景每个 VU 用独立幂等键，不存在键竞争 —— 实测两组的冲突指标都是 0，看起来像「锁没用」，实际是**压不到锁该起作用的地方**。锁减少的是「多个请求抢同一业务对象」时走到 L3 的次数，须专门构造（`k6/contention.js`）。

**这组数据是技术方案 §6.1 的实证**：去掉锁，正确性一点没变；去掉锁，L3 的负载差两个数量级。绝对值有波动（复跑两轮 5/4 与 494/494），量级差稳定。若哪天去锁组的正确性结果变了，说明有地方错把锁当成了正确性依据。

**第六类「换版后的旧凭证」由 PR-4 补入，补入前为真实缺陷。** 初版仅将 `activityId` 签进凭证，而权益内容取决于 `sku.packageVersion`，与活动版本无关。用户按「月卡 + 券」咨询，运营把 SKU 改指向只剩券的新版而价格一分不动，于是验签过、比价也过，建单时快照读的是新版本 —— **用户按月卡+券付了钱只拿到券**。

前五类均拦不住：签名字段全对、价格未变。「活动改版但价格未变时用户看到的承诺没有变化」这一判断不成立 —— **价格没变不代表承诺没变**。修法是把 `packageVersion` 签进凭证并比对（技术方案 §6.2）。

**「均不建单」必须与「拒绝了」同时断言**：先建单再校验同样会抛出预期的错误码，只断言异常则那种实现照样全绿 —— 而它已经占了库存、留了脏单。PR-5 引入库存后代价更实。

**「改价后重新咨询可正常下单」是必要的一条**：没有它，「一律拒绝」可能被实现成「改过价的商品从此卖不出去」—— 那不是防线，是故障。

**退避序列的验证方式**：退避基数须可配置，测试注入毫秒级基数。第 1、3 条断言的是**两条序列的倍率关系与彼此不相等**，不是绝对值 —— 生产长退避跑满需 12.5 分钟，而现有集成测试全套不足 8 秒。人工验证按生产取值跑，记录真实收敛耗时。

**`PROCESSING` 在 V2 只有查单一条收敛通路**。技术方案 §6.6 的处置是「等下游通知为主，查单兜底」，其中「下游通知」指 `providerCallback`，属 V3 范围（§6）。V2 的 `PROCESSING` 收敛完全依赖查单任务，长退避取值因此不能太长，否则演示时等不到收敛。该约束在 V3 引入回调后解除。

第 10 条对应能力清单第 3 项。V1 的 `IdempotencyIT` 均为单线程重复调用，验证的是「第二次调用返回原结果」；并发场景验证的是「两个线程同时进入同一分支时唯一索引生效」，二者的失效模式不同。

第 11 条对应能力清单第 9 项。V1 缺陷 ① 即事务边界问题：`@Transactional` 用于同类内部调用时不经代理、不生效、不报错。静态检查证明「注解写了且带限定」，回滚 IT 证明「限定指向正确的库」—— 多数据源下二者缺一不可（5.6 ②）。

第 15 条对应能力清单第 6 项。k6 通过不能证明 Redisson 生效：DB 原子扣减单独即可满足 0 超卖，删掉分布式锁后正确性结果不变。这正是技术方案 §6.1 的论断 —— L2 是性能优化，L3 才是正确性兜底。锁的价值只能从 L3 的负载侧读出：锁生效时并发被串行化在锁上，条件更新冲突与唯一键冲突应当更少。只看锁自身的竞争计数没有意义 —— 移除锁后该指标必然为 0，那只说明锁代码没有运行。

| 断言 | 挡住的失效 |
| --- | --- |
| `reward_grant_record` 按 `op_no` 计数 = 1 | 平台侧重复受理 |
| `reward_grant_item` 按 `(op_no, item_seq)` 无重复 | 明细重复插入（记录仅 1 条但明细翻倍时，只查记录表漏检） |

不以日志或调用次数为准 —— 收敛过程本就包含重复调用，重复调用不等于重复发放。

#### 缺陷：查单已收敛的单，其 `GRANT` 任务仍重试至死信

**五种模式跑完后发现，`TIMEOUT_BEFORE_COMMIT` 与 `PROCESSING` 两个场景的订单虽已 `GRANT_SUCCESS`，其支付回调落的那条 `GRANT` 任务却停在 `DEAD`、`retry_count=5`。**

成因是**两条任务各自独立地在收敛同一件事，而它们互不知情**：

| | `GRANT` 任务（`op_no = bizNo + '_GRANT'`） | `QUERY_GRANT` 任务（`op_no = bizNo + '_G_' + providerType`） |
| --- | --- | --- |
| 来源 | 支付回调事务内落 | `grantBenefit` 返回未收敛时落 |
| 职责 | 驱动履约编排 | 查单收敛 |
| 退避 | 短退避，`maxRetry=5` | 长/短退避，`maxRetry=10` |

`grantBenefit` 在任一组未收敛时返回 `UNKNOWN`，调度器据此对 `GRANT` 任务按短退避重试；而真正的收敛通路是 `QUERY_GRANT`。下游持续不可达期间，`GRANT` 任务的 5 次重试先于查单跑完，进 `DEAD`；此后查单收敛，主单转 `GRANT_SUCCESS`，**那条死信却留在表里**。

**后果不是资损，是死信失真。** 实测确认发放记录四处仍各 1 条、下游账本 1 条 —— 每次重试都携带同一 `opNo`，被 mock 账本 put-if-absent 挡下。但死信的语义是「重试至阈值仍未收敛，需人工介入」，而这些单已经自行收敛了。**这与 PR-8 修正的第 2 项（已支付订单的关单任务重试至死信）是同一类失效**：死信被正常业务填满后失去人工处置入口的作用。

**判据是「有没有另一条通路在收敛这件事」**：`grantBenefit` 已落 `QUERY_GRANT` 任务时，`GRANT` 任务的职责就已交接完毕，它应当置 `DONE` 而非继续重试。当前实现让两条任务重复驱动同一次履约 —— 实测 `grantBenefit` 被调了 5 次，每次都重新调用下游全部供应方。

**已在 V2 修复**（PR #23）：判据落在 `GrantTaskHandler`，以「该单是否存在**在途**的查单任务」区分「已移交」与「下游未响应」—— 前者返回 `SUCCESS` 使调度器置 `DONE`。`grantBenefit` 的签名与语义不动：它是 `mp-api` 的接口方法，`payCallback` 与 V3 的对账补偿都是调用方，改返回值要连带改三处。

**任务置 `DONE` 不等于把「未知」谎报成「成功」**：任务的终态描述任务自身的执行结果，下游发放的结果记在 `play_biz_record.grant_status` 与 `play_op_record` 上，此刻仍是 `GRANT_UNKNOWN`，对账与查单都据此工作。

**「在途」须排除 `DONE` / `DEAD`**：前者表示上一轮查单已收敛完毕，后者表示查单自己也放弃了，两者都不构成「另有通路正在收敛」。把终态也算作有人接手的话，重发的 `GRANT` 会在首轮直接置 `DONE`，而上一轮那条查单任务早已结束 —— 主单永停 `GRANT_UNKNOWN`，两条通路都不再看它。

**这一条只有按生产退避取值、在运行中的实例上跑才发现得了**：集成测试注入毫秒级退避基数，两条序列都在几秒内跑完，`GRANT` 任务的 5 次重试与查单收敛几乎同时发生，死信是否残留取决于线程调度 —— 用例断言的是主单终态与发放记录数，两者在缺陷存在时照常全绿。**退出标准第 1、3 条的判据（状态序列 + 两侧账本）不覆盖「过程中留下了什么」。**

**修复顺带暴露了两处既有用例的隐藏依赖**，二者都不是「放宽断言」：

| 用例 | 原先 | 为什么变 |
| --- | --- | --- |
| `FaultInjectionIT` 的两条重发用例 | 驱动 3 轮即收敛 | 修复前 `GRANT` 任务的**每一次自身重试都在重发履约**，绕开了 §5.3「连续查无满 3 次才重发」的约束 —— 那两条用例此前正是靠这条计划外的快路径收敛的。移除后回到设计的通路：查单再攒满 3 次查无 → 落重发 → 第 4 轮执行 |
| `ReliableTaskIT` 的死信用例 | 以 `GRANT` 任务构造死信 | `GRANT` 落了查单任务后即移交、自身终结，走不到重试至阈值那条路 —— **用它构造出的「死信」正是本次判定为缺陷的那个现象**。改用 `QUERY_CLOSE`：查单类，没有可移交的对象，下游持续不可达时只能自己退避到阈值 |

第一条与 §5.9 的注入自查是同一个教训的另一面：那次是「用例存在但未覆盖其声称的分支」，这次是**用例通过的原因与它声称验证的机制无关** —— 两者都只有在改动了被测行为之后才暴露。

**新增用例的断言分两半，缺一不可**：任务终态为 `DONE`，且下游只收到过一次发放请求。只断言前者的话，「重试若干轮后恰好收敛」同样能得到 `DONE`，而每一轮都白调了一次下游全部供应方。调用次数取 mock 账本新增的 `grantAttempts`，不看日志 —— 账本条数受幂等保护恒为 1，看不出多余的重试。

**关单与 `CLOSING` 收敛实测**（PR-6a，在运行中的实例上验证）：

| 场景 | 操作 | 实测结果 |
| --- | --- | --- |
| 正常关单 | `POST /api/benefit/close/{bizNo}` | `SUCCESS`；`pay_status=CLOSED`、`stock_status=RELEASED`、`locked` 归还 |
| **已支付拒绝关闭** | 先 `POST /api/fault/pay-ledger/{bizNo}/paid` 再关单 | `1741 订单已支付，拒绝关闭`；`pay_status` 仍为 `WAIT_PAY`，**`locked` 未减** |
| **关单超时进 `CLOSING`** | 注入 `TIMEOUT_BEFORE_COMMIT` 后关单 | 返回 `UNKNOWN`；`pay_status=CLOSING`、**`stock_status` 仍为 `LOCKED`、`locked` 未减**；落 `QUERY_CLOSE` 任务 |
| **`CLOSING` 期间支付成功** | 上一步之后投递 `SUCCESS` 通知 | 放行，`pay_status=PAY_SUCCESS`；补建 `GRANT` 与 `STOCK_CONSUME` |
| `CLOSING` 查单收敛 | 恢复支付方后驱动 `QUERY_CLOSE` | `pay_status=CLOSED`、`stock_status=RELEASED` |
| 支付回调乱序 | 先 `SUCCESS` 后 `CLOSED` | 第二条 ACK（`code=0`）**且留痕 2 条操作记录**，但 `pay_status` 保持 `PAY_SUCCESS`、无释放任务 |

**「已支付拒绝关闭」的前提是支付方账本**：该场景下平台的 `pay_status` 还是 `WAIT_PAY`（通知尚未到达），「已支付」只存在于 mock 的 `PayLedger` 里。若关单不问支付方、只看平台状态，这单会被关掉而钱已经收了。

**「`CLOSING` 期间不释放」必须查 `locked` 而非只看状态**：状态对了而库存被释放，是最容易漏的一种 —— 前者由条件更新保证，后者取决于有没有多落一条任务。

**乱序那条的三个数缺一不可**：只断言 `pay_status` 不变，无法区分「被条件更新拒绝」与「通知未到达」；只断言留痕，无法证明状态没被改回。

**库存与限购实测**（PR-5，`docker compose down -v` 后在运行中的实例上验证）：

| 场景 | 操作 | 实测结果 |
| --- | --- | --- |
| 并发抢购 | 库存置 5，30 个不同用户并发下单 | 5 个 `code=0`、25 个 `1712`；`locked=5`、`available=0` 不为负、订单表恰好 5 行 |
| 限购 | 同一用户连买 3 件（限额 2） | 前两件 `code=0`，第三件 `1713`；`used_qty=2`，且 **`locked` 仍为 2 而非 3** —— 限购拒绝时库存预占同步回滚 |
| 转消耗 | 支付成功后驱动调度器 | `locked` 减 1、`consumed` 加 1，**可售余量不变**；`STOCK_CONSUME` 任务 `DONE` |
| 释放 | 支付失败后驱动调度器 | `locked` 归还、`consumed` 不变、`used_qty` 归零；`STOCK_RELEASE` 任务 `DONE`（库存与额度由它一条承接） |

**并发那条的三个数必须同时看**：只看「返回了几个成功」不足以证明未超卖 —— 超卖的形态即全部成功。

**最后一条验证的是每单幂等，必须让 B 单占着库存**：单笔单场景下释放后 `locked` 归零，第二次释放被 SQL 下界拦下，用例照常通过 —— 起作用的是下界，不是幂等闸。

**额度每单幂等实测**（PR-8，在运行中的实例上验证）：

| 场景 | 操作 | 实测结果 |
| --- | --- | --- |
| **未占额度的单释放** | 限额置 0 时下 A 单 → 调高限额为 2 → 同用户下 B 单 → A 单支付失败释放 | `used_qty` 仍为 1（B 的那份未被动）；A 单 `quota_status=NONE`、`stock_status=RELEASED` —— 库存那一半照常释放 |
| **重复释放不多还** | A、B 两单各占 1，A 释放后把 A 的任务打回重跑 | `used_qty` 仍为 1；A 单 `quota_status=RELEASED` |

### 5.9 V2 收口修正（PR-8）

V2 整体通读后修正三项，对应退出标准 21、22、23。

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | 额度返还无每单幂等闸 | 未占用额度的单释放时扣减同用户另一笔单的额度 | 主单增 `quota_status`，与 `stock_status` 分列（技术方案 §7.4） |
| 2 | 调度器将业务规则拒绝判为 `UNKNOWN` | 已支付订单的超时关单任务重试至死信，死信失去人工处置入口的作用 | 按错误码号段分流：`1xxx`/`4xxx` 判 `FAIL`，`5xxx` 仍判 `UNKNOWN` |
| 3 | 去锁对照组缺并发发奖场景 | 退出标准 21 的「正确性结果完全一致」仅覆盖三道闸中的两道 | 补 `concurrentGrantRewardStillProducesOneRecordWithoutLock` |

**第 1 项与 PR-5 修正的库存缺陷同构**，区别仅在计数器，论证见技术方案 §7.4。**显形条件是限额中途变更** —— 既有用例的限额恒为 2，每单均占额度，「无条件返还」与「按本单是否占用返还」表现一致。

**第 2 项的判据错误**：调度器原将全部异常映射为 `UNKNOWN`，依据是「异常可能发生在 RPC 发出之后」。该依据对系统异常成立，对业务规则拒绝不成立 —— `1741` 表示订单已支付，重试结果不变。`StockTaskHandler` 对「订单不存在」判 `FAIL`，两处口径原本不一致。

分流判据取错误码号段而非异常类型：`BizException` 同时承载三个分区，按类型分流会将 `5001` 一并判为终态失败。

**`ReliableTaskIT` 的死信用例随之改写**：原用例借「订单不存在」构造死信，该构造属于被修正的误判类型。改为注入下游超时，符合死信的定义 —— 重试至阈值仍未收敛，而非已有确定结论。

**三项均由逐行审阅代码发现，注入自查未产出。** 注入验证的是既有用例是否有效，不能验证缺少哪个用例。

**注入自查结果**：

| 注入 | 结果 |
| --- | --- |
| 移除额度闸 | `StockAndQuotaIT` 红 2 条 |
| 移除业务拒绝分流 | `CloseOrderIT` 红 2 条 |
| 将 `5xxx` 一并判为确定拒绝 | 全绿，用例无效（已修正） |

第三项暴露的问题：`systemLevelUnknownStillRetries` 原以注入关单 RPC 超时构造，该路径不抛 `BizException`（异常由 `askPayToClose` 转为 `UNKNOWN`），未触及分流分支。改用 `BizLock` 的 `5002` 后覆盖成立。另需注意 `RLock` 可重入且 `runOnce()` 同步执行，持锁线程须独立于任务执行线程。

**声称锁定某条边界的用例，须破坏该边界验证其变红。** PR-4、PR-5 的教训是「结论无对应用例」，此处是「用例存在但未覆盖其声称的分支」，后者仅注入可证伪。

### 6.3 裂变接入公共能力层的观察方式

退出标准第 1 条要求「`reward` 接口签名零改动，若有改动如实记录」。**这条不能靠「实现完回头看 git diff」判定** —— 改动可能发生在实现过程中的任意时刻，且改完就忘了为什么。

处置：PR-4 开工前，把 `GrantRewardReq` 的六个字段各写一句「裂变怎么传」，落在 PR 描述里。

**填表结论**（PR-2 开工前完成，早于原计划的 PR-4 —— 该表一旦暴露问题，改的是 `mp-api` 的 DTO，越早越便宜）：

| 字段 | 权益售卖 | 裂变·徒弟发奖 | 裂变·师傅返奖 |
| --- | --- | --- | --- |
| `playType` | `BENEFIT_SELL` | `FISSION` | `FISSION` |
| `activityId` | 活动号 | 同 | 同 |
| `bizOrderNo` | 订单 `bizNo` | **`relation_id`** | **`relation_id`** |
| `opNo` | `bizNo + '_G_' + providerType` | `outFlowNo + '_FL'` | `outFlowNo + '_SP'` |
| `receiverId` | 买家 `userId` | 徒弟 `userId` | 师傅 `userId` |
| `rewardItems[]` | 权益项快照 | 徒弟奖励快照 | 师傅返奖快照 |

**`bizOrderNo` 取 `relation_id` 是这张表里最容易填错的一格**：直觉会填 `group_id`（「一个裂变组是一次业务」），但一个组下有 N 条关系、每条关系各自发奖，填 `group_id` 会让 `uk_biz_op(biz_order_no, op_type, op_seq)` 把同组第二个徒弟的发奖当成重复操作挡下 —— 而这与技术方案 §3.3 对 `fission_task.biz_no` 的注释（「`SPONSOR_REWARD` 取 `relation_id`（非 `group_id`），否则一师傅仅一条任务→漏发」）是同一个错误的两种形态。

#### 填表实际暴露的一处：判据只念了一层

**`GrantRewardReq` 六格全部填得出，但 `rewardItems[]` 这一格下钻后有三个字段对裂变无语义。**

冻结项 6 的原判据是「逐字段念一遍 `GrantRewardReq`，任何一个字段说不出裂变怎么传即为不通过」（§2.4）。`rewardItems` 当时作为一个整体过关，没有下钻到 `RewardItem` 的六个字段：

| `RewardItem` 字段 | 裂变能否填 |
| --- | --- |
| `itemSeq` / `rewardType` / `qty` | 能，语义相同 |
| `providerType` / `providerProductId` | **裂变奖励由平台直发，无外部供应方** |
| `core` | **「核心权益」是权益售卖概念** |

`core` 的语义写在它自己的注释里 ——「核心项失败需回收附加项后退款」。回收与退款都属权益售卖的逆向链路，而裂变是纯补贴、无逆向（PRD 附录 A：「裂变逆向链路几乎没有」）。这个字段对裂变不成立。

`providerType` 的牵连更深：`grantOpNo` 的粒度定死为「一次调用 = 一个供应方」，`RewardItem` 也约定「一次调用内的项须同属一个 `providerType`」。裂变没有这个维度。

**处置：裂变填约定值，不改接口。**

| 字段 | 裂变取值 | 依据 |
| --- | --- | --- |
| `providerType` | `PLATFORM` | 平台直发是一种发放渠道，mock 供应方按此值走内部发放分支 |
| `providerProductId` | 奖励配置 id | 「发什么」的标识，与供应方商品 id 同位 |
| `core` | 恒 `true` | 裂变无附加项概念，全部奖励项等价 |

**这是妥协而非设计，如实记录**：三个字段对裂变是「填了但不承载原意」。选它而非改 DTO 的理由是代价对比 —— 改 `RewardItem` 要动 `mp-api` 的公共契约，牵连 V1/V2 已合入的权益售卖链路与 `ShapeFreezeTest` 的字段断言；而约定值方案下 `reward` 接口零改动，退出标准第 1 条成立。

**若 V4 接入真实的裂变奖励供应方，这三个字段会重新有意义** —— 届时 `PLATFORM` 变成真实渠道之一，约定值自然退场。这也是选它的另一半理由：妥协是可逆的。

**填不出来的那一格就是抽象的漏洞**，不是「裂变的特殊情况」。填表在写代码之前做，改接口的成本此时最低 —— 本次提前到 PR-2 之前，正是因为发现问题时越早越便宜。

### 6.4 关键取值与依据

技术方案未给出取值或实现方式的部分，此处定下，实施按此执行。

**① 好友过滤的 before/after 对照必须同时保留两套实现。**

退出标准第 2 条要 SQL 次数、扫描行数、P99 三组对照数据。若只写优化后的实现，「基线」就只能靠口算或引用文档里的公式 —— 那不是实测。

处置与 V2 的去锁对照组（§5.6 ⑫）同构：过滤器实现由开关 `mp.fission.filter.pushdown` 切换，两条路径都进 CI 的正确性用例（**断言两者过滤结果完全一致**），性能对照另跑压测。**正确性一致是性能对照有意义的前提** —— 两个实现若筛出的人不一样，比 P99 没有意义。

**基线实现不是「写得差的版本」，是技术方案 §7.1 写死的那个形态**（逐用户查 + 内存 join），照抄即可，不额外劣化。

**② 关系过期治理的分片区间由 `MIN(id)/MAX(id)` 均分，实例数取配置。**

技术方案 §3.3 定了「各实例认领 `id BETWEEN` 的连续区间」，未说区间怎么算。V3 单进程只有一个分片，但**分片逻辑必须此时就写对**：V4 多实例时改的只是「我是第几个分片」的来源（配置 → 注册中心实例序号），不改分片算法。

单进程下取 `shardIndex=0, shardTotal=1`，即全区间。**不因为「只有一个分片」就省掉 `id BETWEEN` 条件** —— 省了它，V4 加分片时这条 SQL 要重写，而它是一条会扫百万行的批量语句，重写要重新验证执行计划。

**③ `granting_until` 的收敛窗口取 10 分钟。**

技术方案 §3.3 定了它的语义（发奖在途豁免过期治理，过期即允许接管并告警），未给时长。取值依据与 V2 的死信阈值同源：它须长于「发奖 + 查单收敛」的正常耗时，短到不让一行永久豁免。

§5.8 实测的 `PROCESSING` 收敛耗时为 153s（长退避 30s→2m→10m 的前两档），10 分钟覆盖到第三档一轮。超时后按技术方案的规定「允许治理接管并告警」，对应对账第 13 项。

**④ 对账的 15 项分两批做，扫描一律走索引且不跨库 JOIN。**

15 项不是同一类：第 1、2、4、7、9、10、12、13、14 项是**单库扫描 + 补建任务**，第 3、5、6、8、11、15 项是**跨库或跨系统比对 + 告警**。前一批的处置动作幂等（补建任务本身带幂等闸），后一批一律只告警不自动改数（§6.8 的明确约束）。

实施时前一批先做 —— 它们的自动补偿是「收敛率 100%」的最后一道，且验收方式明确（人为注入差异，看能否检出并修复）。

**跨库比对走 `batchQueryByOpNos` 分批拉取在内存比对**，不做跨库 JOIN。V2 已配四个分库账号，跨库 JOIN 在运行期直接 `access denied`（退出标准第 13 条）—— 这条约束在 V3 首次真正被使用。

**⑤ 事件广播用 RocketMQ 普通消息，消费侧幂等，停机不影响收敛。**

技术方案 §6.7 已定「事件负责加速收敛，查单负责保证收敛」。V3 实施的关键是**这条论断要能被演示**：退出标准第 5 条要求「RocketMQ 停机时收敛时间退化到查单周期，但仍然收敛、无资损」。

因此消费侧的 `opNo` 幂等与查单任务**必须并存**，不得因为「有了事件就不用查单了」而把 `QUERY_GRANT` 去掉 —— 那样事件丢失即永久悬挂，与 §6.7 的设计恰好相反。

**⑤a 事件传输 V3 取进程内总线，接口留在 `mp-common`。**（PR-9 实施时定下）

§6.1 已定「V3 仍为单进程，V4 才拆」，而扩展性表把 RocketMQ 列在 V3。两者的落点是：**发布侧只认 `GrantResultPublisher` 接口，V3 的实现是进程内事件总线，V4 换成 RocketMQ 只改一个 `@Bean`。**

**V3 不接真实 broker 的理由不是省事**：这一层要验的是「事件加速、查单保证」这条分工是否成立，而它由**消费侧的幂等与查单任务并存**决定，与传输是进程内还是跨进程无关。接真实 broker 只会让每次 IT 多起一个容器（nameserver + broker 两个进程），验不出额外的东西。「至少一次投递」「broker 停机」这类真实 MQ 语义属 V4 退出标准第 5 条。

**接口这一层的代价是值得的**：它把「换传输」的影响面锁在一个实现类里。若 V3 直接调 Spring 的 `ApplicationEventPublisher`，V4 时要在 `reward` 的业务代码里逐处找发布点——而那时那些代码已被用例锁定。

**⑤b 通知幂等按 `(opNo, notifySeq)` 两维，与「终态不被覆盖」是两道不同的闸。**（PR-9 实施时定下）

同一个 `opNo` 会收到多条**语义不同**的通知（先受理后成功、供应方补发），只按 `opNo` 去重会把第二条真实通知当成重传丢弃。判「是不是同一条通知」的依据是流水号。

两道闸各管一件事，缺一不可：

| 闸 | 挡什么 | 失效后果 |
| --- | --- | --- |
| `uk_notify(op_no, notify_seq)` | 同一条通知重复投递 | 每次重投都发一次事件，消费侧独自承担全部去重压力（而消费侧有两个） |
| `result NOT IN ('SUCCESS','FAIL')` | 后到的结果覆盖先到的 | 一笔已确认成功的发放被迟到的失败通知翻掉 |

**重复投递返回 `accepted=true`**：ACK 的语义是「别再投了」，返回失败会让供应方一直重投同一条已处理的通知。

**⑤c 对账第 10 项改为只告警，不自动改进度。**（PR-10 实施时定下）

§6.8 给第 10 项（关系完成但轮次进度未推进）写的处置是「重放关系后处理」。实施时确认这条走不通：重放的入口 `settleDone` 的关系推进用条件更新 `WHERE status='JOINED'`，对一条已 `DONE` 的关系命中 0 行，**进度加不上去**。

而 `progress` 是共享计数器，与库存 `locked`、限购 `used_qty` 同类——正确值取决于历史上哪些关系完成过，直接改数会把一次错误固化成新基线。故按 §6.8 对第 6、15 项的同一条处置：**告警，人工核**。

**第 13 项是唯一直接改字段的**（清 `granting_until`），理由是不改它就没有任何机制能再动这行：治理因豁免跳过它，也没人推进它。清的是**豁免标志**不是业务结果，清完关系回到治理的扫描范围，仍然是「把单子推回收敛通路」。

**⑥ `manualRepair` 的七类动作复用既有幂等键，不新造。**

FR-C07 列了七类处置动作（重查支付、重查发奖、重试发奖、重试回收、重试退款、标记人工完成、导出对账证据）。前五类都是「重新驱动一条已有的收敛通路」，**必须复用原幂等键**：重试发奖用原 `grantOpNo`，重试回收用原 `revokeNo`，重试退款用原 `refundNo`。

新造键即绕开 `uk_biz_op`，等于给人工处置开了一个可以重复发奖的后门 —— 而人工处置是最容易被重复点击的入口（客服连点）。

**「标记人工完成」是唯一会写终态而不调下游的动作**，故必须落 `operator` 与 `reason`（BR-C-27），且在对账中可被识别为人工干预，不计入自动收敛率。

**⑦ 履约扇出用虚拟线程 + `invokeAll`，禁止 fail-fast。**

技术方案 §7.2 与《开发规范》§6.5 均已写明。此处强调实施判据：`invokeAll` 等全部任务结束才返回，**一组供应方失败不得取消其余组**。用 `invokeAny` 或在任一 future 异常时提前返回，会让已发出的其余调用变成「结果未知且无人收敛」—— 那正是 `UNKNOWN` 悬挂的制造方式。

**⑧ 新增的任务类型须各自明确「谁负责等到结果」。**

V2 的 §5.8 缺陷是这条约束缺失的产物：`GRANT` 与 `QUERY_GRANT` 各自独立地收敛同一件事而互不知情，前者重试至死信而后者已收敛。修法是让「发起」与「等待」的职责显式交接（已在 V2 落地，见 §5.8）。

V3 新增的 `REFUND`、`REVOKE`、`SPONSOR_REWARD`、`RELATION_EXPIRE` 四类任务须逐一回答同一个问题：**它的结果未定时，由谁继续收敛，以及它自己此刻该置什么状态**。凡是「发起类」任务，一旦把结果交给了对应的查单任务，就应当置 `DONE` 而非陪着重试 —— 否则死信表会被已自行收敛的单填满，与 PR-8 修正的第 2 项、§5.8 的缺陷是同一族失效。

**这类缺陷只有按生产退避取值、在运行中的实例上跑才发现得了**：集成测试注入毫秒级退避基数，发起类与查单类的序列几乎同时跑完，死信是否残留取决于线程调度。故 V3 的人工验证须包含「跑完一轮后查死信表」这一步。

**⑩ 关系过滤在分享侧关闭，其余七条照常。**（PR-6 实施时定下）

BR-F-12 要求「被分享对象须通过 FR-F04 过滤」，而 BR-F-11 要求「重复分享不重复创建关系，且**不作为错误**」。两条规则在关系过滤这一维上直接冲突：已有进行中关系的人，按前者应判 `1611`（未通过过滤），按后者应回报「已邀请」。

**处置：分享路径关闭关系过滤那一条，其余七条照常执行。**

二者并不真的矛盾，是同一件事在两条路径上的不同呈现：

| 路径 | 对「已有进行中关系」的处置 | 理由 |
| --- | --- | --- |
| 读（`getFriends`） | 从可选名单中剔除，记入拒绝集合 | 免得用户点了没反应 |
| 写（`shareInvite`） | 撞唯一键 → 回报「已邀请」 | BR-F-11 的幂等命中，不是错误 |

故关系维度在两侧都在起作用，只是一侧记「拒绝」、一侧记「已邀请」。其余七条两侧一致——账号注销、被拉黑、人群不匹配，在哪条路径上都是拒绝。

**分享侧必须独立过滤一次，不信任 `getFriends` 的结果**：两次调用之间对方可能已注销、已被拉黑，或客户端根本没调过 `getFriends` 而直接构造了一批 id。**分享是写路径，把关只在读路径上做等于没做。**

**⑪ 「命中才保留」类规则的三态输入。**（PR-6 实施时定下）

八条规则里有两条（实验分组、营销人群）的下游返回「谁在组里」，其余六条返回「谁该被剔除」。前者的入参有**三种**而非两种：

| 下游返回 | 含义 | 处置 |
| --- | --- | --- |
| `null` | 该活动没配这条规则 | 规则不适用，全员放行，**不计降级** |
| 空集 | 配了，但这批人一个都不在组里 | 全员拒绝 |
| 非空集 | 部分命中 | 命中者保留，其余拒绝 |
| 抛异常 | 依赖不可用 | 按 fail-open 放行，**计入降级清单** |

**`null` 与空集合并的后果**：未配置实验的活动把全部候选人拒光，而多数活动本来就不做实验分组。详见 6.6 的 PR-6 记录。

**`null` 与异常也不可合并**：前者是「这条规则对本活动不存在」，后者是「这条规则本该生效但问不到人」。前者不该出现在降级清单里——清单是给运维看「本次结果在什么条件下算出」的，把常态塞进去会让它失去信噪比。

**⑨ 周期任务的形态：一次执行即了结，周期性由播种提供。**（PR-5 实施时定下）

`RELATION_EXPIRE` 是本项目第一个**周期任务**，与此前全部任务不同类：`GRANT`、`QUERY_GRANT`、`SPONSOR_REWARD` 都由一次业务事件建立、收敛后了结，而治理任务没有对应的业务事件——建立者只能是系统自己。

两种形态都跑得通，此处定为前者：

| 形态 | 做法 | 问题 |
| --- | --- | --- |
| **扫完置 `DONE` + 播种复活**（选定） | 处理器返回 `SUCCESS`，播种器每周期 `enqueue` 一次 | 无 |
| 返回 `PROCESSING` 永不了结 | 借长退避序列当作周期 | `retry_count` 随每轮累加，达阈值进 `DEAD`——而那不是失败 |

**第二种形态的失效与 V2 PR-8 修正的第 2 项同族**：死信表被正常运转的任务填满，人工处置入口随之失去作用。退出标准第 24 条对本任务要的正是 `DONE` 而非 `DEAD`。

选定形态**不需要任何新增 SQL**：`enqueue` 的 upsert 对终态行的处置本就是「复活为 `PENDING` 且 `retry_count` 归零」——该分支原为查单重发链路所写（V2），此处第二次用上它，两者要的是同一件事：`op_no` 标识的操作可以被重新发起。

**播种周期即治理周期**，取 30 秒，不与调度器同频：播种是一条 upsert，每轮调度都播一次等于每秒一次无意义的写；而治理晚 30 秒开始没有后果——过期关系多存在半分钟不影响任何不变量，唯一键的占用要到该师徒下一轮分享时才显形。

**播种器与其定时触发器拆成两个类**，与调度器/触发器同一处置且理由更强：集成测试要显式调 `seed()` 再驱动 `runOnce()`，才能断言「播了但还没跑」这个中间状态；条件注解若打在播种器上，关掉定时器的测试连 bean 都注入不到。

**第 24 条是 §5.8 缺陷的同族防线**（该缺陷本身已在 V2 修复，见 §6.4 ⑧）。**两半断言缺一不可**：只断言终态 `DONE` 的话，「重试若干轮后恰好收敛」同样能得到 `DONE`，而每一轮都白调了一次下游。发起次数须取下游侧的计数，不看日志，也不看账本条数 —— 后者受幂等保护恒为 1，看不出多余的重试。

**第 2、3 条是裂变最容易静默失败的两处**。第 3 条尤其：技术方案 §3.3 已写明「若过期治理只置 `status='EXPIRED'` 而不改 `active_flag`，该行仍占着唯一键，下一轮分享插入时冲突被当成幂等命中，静默返回那条已过期的关系」。**判据必须是「是不是新行」而非「有没有报错」** —— 静默失败的形态是接口返回成功。

**第 8 条是第 6 项能力有意义的前提**：两套实现筛出的人不一样时，比 P99 是在比两个不同的功能。这与 V2 第 21 条（去锁对照组正确性完全一致）是同一条判据。

**第 17 条是 §6.7「事件加速、查单保证」论断的唯一验证手段**：事件正常工作时，收敛由谁完成无法区分 —— 关掉事件才能证明查单这条 lower bound 真的在。这与 V2 第 21 条「锁越有效越难压出底层竞争」同构。

**第 19 条挡的是 `invokeAny` / fail-fast 写法**：失败形态是「B 组的调用发出了但结果无人收敛」，而主单状态看起来正常。只断言主单终态发现不了，必须断言 B 组明细的实际状态。

**第 15 条挡的是对账把黑名单写成白名单**（§6.8 第 1 项的注释）：谓词写成「排除 `GRANT_SUCCESS`」时，一笔已全额退款的失败单会被当作待履约补发一次 —— 钱退了、货也给了。

**第 10、11 条在 PR-7/8 合入后的专项 review 中各补了一条断言**（详见 §5.9 的 ④⑤⑥）。两条补充针对同一个盲区：**这两条原先只验了同步链路**。第 11 条补收敛通路的对称性——`REVOKING` 是「回收已完成」的凭据，凡能置入该状态的路径都要真的确认过回收发生了，而 `reconcileRevoke` 是第二条这样的路径；第 10 条一侧补的是「金额未知的单不受理」，它不在五态之内，却是同一张准入表必须回答的问题——**准入判据是「能不能退」，而「退多少不知道」同样是不能退**。

**人工验证**

裂变全链路在运行中的实例上跑一遍：师傅进场 → 拉好友（观察过滤拒绝原因分布）→ 分享 → 徒弟建联 → 加入 → 完成 → 双方到账 → 关系 `DONE`。退款链路同理跑一遍（含回收）。记录填入 6.6。

#### PR-2 发现的技术方案缺陷：`fission_group` 缺一道唯一键

**技术方案 §3.3 把「并发进场不创建重复轮次」（BR-F-02）的兜底职责记在 `uk_activity_sponsor_round (activity_id, sponsor_id, round_no)` 上，实测不成立。**

轮次号由「读 `MAX(round_no)` 再 +1」算出，两条并发路径算出的是**不同的号**：

| 时刻 | 线程 A | 线程 B |
| --- | --- | --- |
| t1 | 读 `MAX` → null，算出轮 1 | |
| t2 | 插入轮 1，提交 | |
| t3 | | 读 `MAX` → 1，算出轮 2 |
| t4 | | 插入轮 2，**唯一键不冲突** |

结果是同一师傅在同一活动下有两轮 `RUNNING`。该唯一键实际挡的是「同一个轮次号被建两次」，而那在「读 MAX 再 +1」的算法下本就不会发生 —— **它挡的是一件不会发生的事，而要挡的那件事它挡不住**。

**修法**：补 `uk_activity_sponsor_active (activity_id, sponsor_id, active_flag)`，机制与 `fission_relation.active_flag` 完全相同 —— `RUNNING` 时恒为 `ACTIVE`（受唯一键约束，至多一条），进终态时置为该行的 `group_id`。

**同构的不变量应当用同构的手段**：`fission_relation` 的「同组同师徒进行中关系 ≤ 1」与 `fission_group` 的「同师傅同活动进行中轮次 ≤ 1」是同一类约束，前者用了部分唯一键，后者却指望一个语义不同的唯一键代劳。技术方案对两张表分别设计时没有把它们放在一起看。

**由并发用例实测发现**：`concurrentEntryCreatesExactlyOneRound` 起 8 线程压同一 `(activityId, sponsorId)`，实测建出 2 轮。**串行调用永远发现不了** —— 那正是「并发用例必须用真实线程池压同一行」（§5.7）的又一个实例。

**连带确定的一条语义**：已过期但未被治理的轮次<b>仍占着 `active_flag`</b>，必须先终结才能开下一轮。判据取 `selectActive`（只认 `active_flag`）而非 `selectRunning`（带 `expire_time` 过滤）—— 两者对这类轮次给出相反答案，用后者会放行开新轮而唯一键挡下它，异常从业务提示退化成 `DuplicateKeyException`；更糟的是若被撞键分支捕获，调用方会拿到那条过期轮次，看起来「开轮成功」而实际什么也没发生。轮次过期治理随关系过期治理在 PR-5 落地（**该条已实施**，并在实施时发现 `fission_group` 缺扫描索引，见下文）。

#### PR-2 修正的一处实现偏差：跨服务调用不提前用 `@DubboReference`

`FissionServiceImpl` 初版以 `@DubboReference` 注入 `ActivityService`，与既有形态不一致 —— `benefit-order` 与 `reward` 均为 Spring 注入，注释写明「V0/V1 单进程用 Spring 注入，拆服务后改回」。

#### PR-7/8 发现的三处

**① 幂等键长度溢出，且失效形态与下游超时不可区分。**

回收键首版写成 `revokeNo + "_" + grantOpNo`（两把完整的键相接），实测 90+ 字符、溢出 `VARCHAR(64)`。

**关键在于它怎么失效的**：插入异常被回收链路的「异常一律映射 UNKNOWN」捕获 → 主单进 `REVOKING`、落一条 `REVOKE` 任务、对上游回报「结果未定」。**这与供应方超时的表现一模一样**，而实际上回收请求根本没发出去，重试多少次都是同一个结果。

修法是由三段来源直接拼出（`bizNo + "_V_" + refundReqNo + "_" + providerType`），不拼接完整的键。**教训是幂等键的长度是它契约的一部分** —— 键由拼接构成时每加一段都要回头核对列宽，而列宽定在 DDL、拼接写在工具类，两处不会互相提醒。

**这条当时只修了一半**（V3 全量 review 补）：改短了拼接式，却没管**上游能塞多长**。`ReqFields` 只校验非空，而 `refundReqNo` / `outFlowNo` 的长度平台管不着——实测一个 40 字符的客服工单号（比 UUID 的 36 位还短，完全正常的取值）会让 `revokeNo` 达到 77 字符、`revokeItemNo` 达到 88 字符，双双溢出。**同一个根因换个入口又回来了。**

三条处置：

- **校验放在派生处**（`IdempotentKeys` 的每个方法），不放各调用方——漏一处就是一条溢出路径，而放在派生处则新增一把键时不可能忘。
- **校验成品键，不校验单个上游字段的长度**。起初按「上游字段最长 16 字符」写，实测判红了一条正常用例：键的形状并不统一——退款键是 `bizNo + 分隔符 + refundReqNo`（本地单号先占 34 字符），建单键却是 `userId + activityId + skuId + clientReqNo` 四个上游字段拼成，两者留给单个字段的余量差着数倍。**一刀切的单字段上限对前者太松、对后者太紧。**
- **准入入口要提前量最长的那把键**。`revokeNo`（短）在准入时派生，而逐供应方的 `revokeItemNo`（长）要到回收阶段才派生——那时主单已进 `REVOKING`。只靠派生处的校验，一个只让长键溢出的工单号会让准入「成功一半」：状态推进了、回收发不出去。**校验来得晚等于没校验**，这一条由用例「被拒时不得推进退款态」守住（注入去掉提前校验即转红）。

**② 幂等判据错写成「看状态」而非「看键」。**

`revokeAndAdmit` 与 `createRefund` 首版都写成「主单已在退款中就返回成功」。于是客服换个工单号再点一次，会拿到 `admitted=true`——**而那笔退款根本没发生**。

钱不会多退（三道闸挡得住），但调用方据此把工单标为已处理，**用户的第二次诉求就此消失**。修法是判据取「同一个 `refundReqNo`」：命中原键才算幂等，否则按「本单已有其他退款」拒绝。

由 `twoDifferentRefundNosStillRefundOnlyOnce` 发现——**这条用例专门测「两个不同退款号」，而非同键重传**。只测同键重传的话，一个「只有 `refundNo` 唯一索引」的实现照样全绿，而客服连点在真实系统里比重传常见得多。

**③ 「先回收后退款」只由服务层一个 `if` 守着，DB 谓词从未被执行。**

注入「把 `startRefund` 的前置态从 `REVOKING` 放开为 `NONE/REVOKING/REVOKE_FAILED`」（即允许未经回收直接退款），**此前 20 条用例全部保持绿色**——因为服务层的 `doCreateRefund` 先一步用 `if (current != REVOKING)` 拒掉了，那条 SQL 谓词根本没有机会执行。

于是 §5.6 的核心约束「顺序不可颠倒」，实际上只由一处可被随手改掉的 `if` 守着：谁把那个分支挪走或写反，DB 这一层不会有任何抵抗，而没有任何用例会红。

补两条<b>直接调 `tx.startRefund` 绕开服务层</b>的用例，注入后转红。

**这与 PR-5 的「约束在单分片下不可观测」同类**：约束存在、用例齐全，但内层约束被外层拦截遮住。三处已构成一个可复用的判断——**「这条约束有几层实现？每一层都被单独验过吗？」**：

| PR | 遮蔽物 | 破除方式 |
| --- | --- | --- |
| 5 | 单分片使区间恒为全空间 | 直接传窄区间 |
| 6 | 数据量不足一页 | 灌到跨页 |
| 7/8 | 服务层 `if` 先行拒绝 | 绕过服务层直调事务方法 |

**注入自查结果**：

| --- | --- |

| 退款前置态放开（允许未回收直接退） | **全绿，用例无效**（已补两条后转红） |

| 回收 `UNKNOWN` 时照常放行退款 | 红 1 条 |

**另由全量回归发现两处**：`ShapeFreezeTest.noCatchAllMapsToFailure` 的扫描窗口取「`catch` 起始后固定 400 字符」，越过块尾把其后的四分类汇总一并纳入检查，产生误报——改为按花括号配对截取实际块范围。**修检查器而非改业务代码**：迁就检查器会让下一个人倾向于放宽断言，那道防线随之变弱。`MultiDataSourceIT` 则再次拦下「新增迁移未申报」（V3201），与 PR-5 的 V3305 同一处。

#### PR-7/8 合入后专项 review 发现的三处

合入后按「同一条规则有几条实现路径」逐条重走了一遍退款链路，写成三个探针实测，**三个疑点全部命中**。它们有一个共同结构，见本节末。

**④ `pay_amount` 可空，退款侧直接拆箱 —— NPE 被吞成 `UNKNOWN`，且收敛通路救不回来。**

`callPayRefund` 把 `Long` 传给 `long` 形参。而 `pay_amount` 可空**是 V2 有意留下的**：`applyPaidAfterClosing`（关单受理后查单确认已支付）此时手上没有支付通知，按 §5.6 的口径留空等回填——「实付金额未知」本身是可表达的状态，而一个猜来的数不是。这条路径真实存在。

实测：

```
PROBE pay_amount = null
PROBE createRefund result = UNKNOWN
PROBE refund_status = REFUNDING
PROBE payLedger delta = 0
java.lang.NullPointerException: Cannot invoke "java.lang.Long.longValue()"
	at BenefitOrderServiceImpl.callPayRefund(BenefitOrderServiceImpl.java:987)
```

**失效形态与 ① 的键长溢出同族，但更严重**：NPE 被「异常一律映射 `UNKNOWN`」捕获 → 主单进 `REFUNDING`、落 `QUERY_REFUND` 任务、回报「结果未定」，与支付方超时**不可区分**。比 ① 严重在收敛通路也救不回来——查单每轮问同一个 `refundNo`，支付方查无恒答 `UNKNOWN`，重试满 10 次进 `DEAD`，**这单永停 `REFUNDING`**：钱没退、状态显示退款中、没有任何机制会再看它一眼。而它正是 V2 花了整条退出标准第 6 条才从 `CLOSING` 黑洞里救出来的那类单。

修法是新增 `1754`，**在准入与退款执行两处各拦一道**：准入那道保证「回收不会白做」——回收不可逆，若只在退款时拒绝，权益已收走而钱退不出去，用户既没权益也没钱；退款那道保证「不会拆箱成 NPE」——它是公开接口，不强制经过准入。**不以 `order_amount` 代入**：实付 ≠ 应付时按应付退是多退或少退，与 `advanceToPaySuccess` 拒绝以应付额填充是同一条理由。

**⑤ 回收留痕的粒度与回收动作不一致，部分核销时已收走的那件不留痕。**

`markRevoked` 的谓词是「一单一次」，而回收本身**逐供应方发起**。一单跨两个供应方、A 已核销 B 未使用时实测：

```
PROBE provider actually revoked count = 1     ← B 真被收走了
PROBE revoke_no marked on items = 0           ← 一条都没留痕
```

后果是**对账第 2 项（已退款权益未回收）扫到 B 判为差异并补一次回收**。下游按 `revokeNo` 幂等挡得住二次回收，但**告警是假的，而这条项是资损哨兵**；人工据此处置时也会以为一件都没收回来。

同一处还有第二半：`usageStatus` 在循环里逐条覆盖，汇总值取决于 `selectGranted` 的返回顺序。A 已核销、B 回收成功时最终留下 `REVOKED`，实测 `reasonCode` 拿到 **1753 而非 1752**——调用方看到「失败，但券没被用过」，与事实相反，人工会把一笔永远不可能成功的回收当成普通出错去重试。

修法：`markRevoked` 加 `grant_op_no` 维度、逐笔留痕（三个出口——成功/失败/未定——都要留，留痕的判据是「这一项收没收走」，与整笔汇总无关）；`usageStatus` 改为取最阻断的那一项，与 `retStatus` 的汇总同一判据。

**⑥ `reconcileRevoke` 对空明细收敛成「成功」，「先回收后退款」被从内部绕过。**

同步链路的 `revokeGranted` 判得对：`granted.isEmpty()` 时打 ERROR、置未定、交人工，理由写在注释里——「不静默当作无需回收，那会退掉一笔可能已发放的单」。**收敛通路没有对称的判断**，循环一次不执行直接落到 `settleRevoke`。实测：

```
PROBE admit retStatus = UNKNOWN          ← 同步链路正确
PROBE reconcileRevoke = SUCCESS          ← 收敛通路判成功
PROBE revoked item count = 0             ← 一次回收都没发生
```

`REVOKE` 任务置 `DONE`、操作记录 `SUCCESS`、主单进入「回收已完成」。危害在下一步：`createRefund` 的前置态谓词正是 `REVOKING`，这单被照常放行——**「先回收后退款」从内部被绕过，三道闸一道都不会响**。

**这三处的共同结构，是 §6.6 那条判断的另一面**：

> 前三处是「同一条约束有几层实现，只验了外层」；这三处是「**同一条规则有同步与收敛两条实现路径，只验了同步那条**」。

- ⑥ 直接就是：两条路径对同一个输入给出相反的答案
- ⑤ 是粒度在两处不一致：回收按供应方逐笔，留痕按单一次
- ④ 是 V2 的一条路径（留空 `pay_amount`）与 V3 的一条路径（读它去退款）之间没有对上

故 §6.6 的自查问句要补一句：**「这条规则有几条执行路径？同步的、收敛的、对账补偿的，各自都验过吗？」**——凡是「结果未定」有出口的地方，那个出口就是第二条路径。

**注入自查结果（本轮）**：

| 注入 | 结果 |
| --- | --- |
| 撤销两处 `requirePayAmount` | `RefundAdmissionIT` 红 2 条 |
| `markRevoked` 谓词退回「一单一次」 | 红 1 条（留痕数为 0） |
| `mergeUsage` 退回「逐条覆盖」 | 红 1 条（`reasonCode` 取到 1753） |
| 撤销 `reconcileRevoke` 的空明细拦截 | `RefundExecutionIT` 红 1 条 |

四条全部转红，无「注入后仍全绿」的情形。

**新增用例时自身被断言拦下一次**：`reconcileRevokeDoesNotSettleWhenNoGrantedItemExists` 首版用「正常准入后改库」造场景，而那条路径的回收本就成功、操作记录已是 `SUCCESS`，断言「不得置 `SUCCESS`」被前置状态直接满足——**测不到收敛通路做了什么**。改为注入回收超时走真实的未收敛路径。这是「构造场景时前置状态已满足断言」的一类，与「多层遮蔽」不同：那类是断言够不着，这类是断言恒真。

#### PR-9 的两处「用例齐全但约束不可观测」

两处都由注入自查发现，且**都不是缺用例，而是用例的输入让约束的两侧取值相同**——断言够得着，只是分辨不出。这是 §5.9 那张遮蔽表的第三种形态。

**① 「后到的通知不得覆盖已终结的结果」不可观测。**

去掉 `settleUnresolved` 的 `result NOT IN ('SUCCESS','FAIL')` 谓词后，此前 9 条用例全绿——因为它们发的两条通知携带的结果**都是 `SUCCESS`**，覆盖与不覆盖的写入结果一模一样。

破除方式是让第二条通知携带**相反的结果**（供应方补发一条迟到的失败通知）。补 `lateNotifyDoesNotOverwriteSettledResult` 后注入转红。

**② 「扇出不得 fail-fast」不可观测。**

把扇出改成「任一失败即 `cancel` 其余」后，此前 10 条用例全绿——因为 mock 全部瞬时返回，**取消发出去的时候其余组早就跑完了**。退出标准第 19 条要挡的正是这种写法，而它挡不住。

破除方式是给 B 组布置 300ms 延迟，让取消真的能打断它。补 `slowSiblingIsNotCancelledWhenAnotherProviderFailsFast` 后注入转红。

**这条的代价特别值得记**：fail-fast 的失效形态是「调用发出去了、本地没记」——权益已发出却无任何记录，后续按「核心失败→回收附加项后退款」处置时回收清单里没有它，退了钱、货还在用户手里。而**只看平台侧的明细分辨不出**，断言必须落在下游账本上。

**三种遮蔽形态至此齐了**：

| 形态 | 例 | 破除方式 |
| --- | --- | --- |
| 外层拦截使内层不可达 | PR-5 单分片、PR-7/8 服务层 `if` | 绕过外层直调内层 |
| 数据规模不触发边界 | PR-6 不足一页 | 灌到跨页 |
| **输入让约束两侧取值相同** | PR-9 两处 | 让两侧取不同值（换结果 / 加耗时） |
| **断言比约束宽**（P1/P2 收口补） | 索引项：断言「不是全表扫」 | 断言到约束本身（`type = RANGE`） |

**第四种是最隐蔽的**：前三种是「用例够不着约束」，这一种是**用例够到了、但判据放得太松**。删掉 `idx_pay_update` 之后，查询退回 `idx_pay_grant` 的最左前缀，`EXPLAIN` 的 `type` 从 `RANGE` 变成 `REF` 而不是 `ALL`——「不是全表扫」这条断言照样成立，而 `update_time` 已经退化成回表后逐行过滤，在真实数据量下与全表扫相差无几。**「走了索引」与「走对了索引」是两回事**，弱断言把后者放过去了。

判断问句：**「这条断言排除掉的，是不是恰好就是我要修的那个缺陷？」**——若缺陷的一个变体仍能满足断言，断言就还不够紧。

**第五种：一条规则在几条同类链路上只实现了一部分**（V3 全量 review 补）。

| 形态 | 例 | 破除方式 |
| --- | --- | --- |
| **规则只在部分链路上实现** | 对账第 4 项覆盖履约、漏退款；键长校验覆盖派生、漏入口 | 按规则枚举它该管的全部对象，逐个查 |

它与前四种的差别在于**缺陷不在任何一处代码里，而在覆盖面上**：`repairUnresolvedOps` 的两条分支各自都对，`IdempotentKeys` 的每处校验也都对——错的是「还有两个中间态没有分支」「还有一个入口没被覆盖」。逐文件读代码看不出这种缺陷，**每一处单看都是对的**。

破法是**按规则枚举对象再逐个查**，而不是按文件读：状态机就枚举全部中间态、幂等键就枚举全部派生处与全部入口、共享计数器就枚举全部增减点。§6.4 那句「任何中间态都必须同时具备准入谓词的入边与对账的一行」本身就是这种枚举式规则——**它写下来了，但没有任何机制检查它是否被逐条满足**，于是 `CLOSING` 补上了（第 14 项），退款的两个中间态漏了三个版本。

**对照组是这类排查的关键手段**：本轮判定第 4 项缺陷时，同样删掉查单任务，`GRANT_UNKNOWN` 的单收敛了而 `REFUNDING` 的单没有——**同一段代码两种结果**，排除了「测试环境问题」这类解释，也直接指出了缺的是哪一支。

| --- | --- |
| `uk_notify` 退化为只按 `op_no` | `ProviderCallbackIT` 红 1 条 |

**另有一处布置泄漏**：`ProviderLedger` 的定向失败设置跨用例存活，下一个用例的 `PROVIDER_A` 拿到 `FAIL`。与 §5.9 记的「账本计数器是全局的」同族，差别是那处改断言方式（取增量），这处要在 `@AfterEach` 清状态——因为定向失败是**布置**而非计数。

#### PR-10 发现的两处

**① `manualRepair` 新造键的危害被外层短路遮住。**

注入「重试发奖时每次派生一把新键」后，此前四条断言**全绿**——下游账本没多、发放记录没多、供应方单号没变。原因是 `grantBenefit` 对已终态的单直接短路返回，新造的键根本走不到下游；而下游那一层还有 `opNo` 幂等兜底。**外层的短路把内层的键失效遮住了。**

新造键的实际危害不在发放，而在 `uk_biz_type_op` 不再去重：每点一次就多几条 `GRANT` 任务，每条都会被调度器领走再跑一遍。补一条「第二次点击前后任务数不变」的断言后注入转红。

**断言取「前后不变」而非绝对值**：一单跨两个供应方即两把原键，加上支付回调落的那条，基数取决于 seed 权益包的构成——写死绝对值会在改 seed 时误红。首版写死 1，实测 `expected 1 but was 3`，**是断言错了而非代码错了**。

**② 对账扫全表，绝对值断言被别的用例污染。**

`nullPayAmountIsNotAmountMismatch` 首版断言「金额差异数为 0」，实测 `expected 0 but was 1`——别的用例留下的差异行也在扫描范围内。改为取增量。

这与 §5.9 记的「账本计数器是全局的」是同一类，但**触发条件更宽**：账本那处要两个用例操作同一个计数器，而对账扫的是全表，**任何用例留下的任何差异行都会进来**。凡是断言「全局扫描的结果」，一律取增量。

#### PR-10 合入后专项 review 发现的两处

**这两处与此前七处不是同一族。** 前七处都是「约束存在但不可观测」——实现是对的，用例够不着；这两处是**判据本身与方案对不上**：实现与用例一起错，注入自查发现不了（注入是「破坏实现看用例红不红」，而这里没有一个正确的基准可破坏）。只能拿代码与 §6.8 的十五条判据逐条对读。

**① 第 3 项扫错了集合，该项近乎空转。**

`checkGrantMissingDownstream` 复用了 `scanPaidNotGranted`，而那条的谓词是 `grant_status IN ('NOT_START','GRANTING','GRANT_UNKNOWN')`——**还没发完**的单。方案给第 3 项写的判据是「`op=SUCCESS` 但 reward 侧查无」，两个集合几乎不相交。

实测：造一笔正常发放成功的单，删掉 `reward_grant_record` 与 `reward_grant_item`，跑对账：

```
PROBE grant_status = GRANT_SUCCESS
PROBE reward rows left = 0
PROBE GRANT_MISSING_DOWNSTREAM diff = 0      ← 一条都没检出
```

它只在单子还没发完时去比对下游，而那种单本来就没有发奖记录，查无是正常的。**真正要找的「平台记着已发成功、下游却没有」完全扫不到。**

修法是给它自己的扫描（`grant_status = 'GRANT_SUCCESS'`）与自己的取键（明细限 `grant_status='SUCCESS'`）。补两条用例：正向检出、反向不误报（发放失败的单在下游查无是正常的）。

**用例为什么漏了**：`ReconcileIT` 按退出标准 14/15/16 组织，而第 3 项不在那三条的字面要求里。**按退出标准写用例，覆盖的就只有退出标准点名的那几项**——十五项里有九项没有对应的退出标准条目。

**② 第 6/15 项拿份数与单数比，量纲错配。**

`consumed` 与 `used_qty` 都按份数累加（`consumed = consumed + qty`），而对账拿它们与 `COUNT(*)` 比。一笔 `quantity=3` 的单会让 `consumed=3` 而单数为 1，**每轮对账报一次假差异**——而假告警会让资损哨兵失效，那正是 §6.8 要避免的。

**它当前不报错，只因为 `doCreateTrade` 有一道 `quantity=1` 的守卫**：

```
BizException: V1 仅支持 quantity=1，实际 3
```

**故这不是今天的缺陷，是一颗埋着的雷**：`quantity` 在 DDL、DTO、库存 SQL 里全都按份数设计，守卫一放开（多份购买是常规需求）两项立刻开始刷假告警。改为 `SUM(quantity)`。

**放开守卫时一并改的两处**（V3 全量 review 逐链路核对得出，已随守卫一起放开）：

| 处 | 原状 | 不改的后果 | 处置 |
| --- | --- | --- | --- |
| `createOrder` 的 `order_amount` | `= salePrice`，未乘份数 | **买 3 份收 1 份钱**，直接资损 | `Math.multiplyExact(salePrice, qty)` |
| 履约的 `RewardItem.qty` | 硬编码 `setQty(1)` | 收 3 份钱发 1 份货 | 传 `order.getQuantity()` |

**checklist 上的第三项被实测推翻**：原列「`SnapshotItem` 无 `qty` 字段，快照存不下份数」，而实际不需要——两处读快照的地方都能从 `order` 直接拿到 `quantity`，回收侧则根本不读快照（走履约明细）。**列 checklist 时按「份数是权益项的属性」假设，实际它是订单的属性。** 照着清单写会多加一个没用的快照字段，而快照字段是长期持久化数据、加了就难删。

**库存与额度本来就是对的**——`tryLock` / `tryConsume` / `tryRelease` / `tryRestore` 四处都传 `order.getQuantity()`，对账第 6、15 项也已改成 `SUM(quantity)`。当时只剩金额与发放这两条链路仍按单数算，而金额那处是资损方向。

用例用**直接改库**造出 `quantity=3` 绕过守卫——与 PR-7/8「绕过服务层直调事务方法」同一处置。

#### PR-6 合入后复审补入：召回分页整段无用例覆盖

**PR-6 合入后逐条注入复审，发现召回分页的三处约束全部无用例覆盖**——注入后 20 条用例保持全绿：

| 注入 | 补测前 | 补测后 |
| --- | --- | --- |
| 只召回第一页（`page < 1`） | **全绿** | 红 3 条 |
| 召回不去重（`LinkedHashSet` → `ArrayList`） | **全绿** | 红 1 条 |
| 去掉 `maxPages` 上限校验 | **全绿** | 红 1 条 |

**原因是数据量，不是用例写得不对**：每条用例的好友数都在 10 以内，而一页是 200。分页、跨页去重、提前退出、页数上限——整段代码从未被执行过。

**这与 PR-5 的「约束在单分片下不可观测」是同一族，但更容易避免**：那处需要构造特殊入参才可观测（单分片时区间恒为全空间），此处只要把数据量提到一页以上。**默认的测试数据量落在第一个分页边界以内时，分页逻辑等同于不存在。**

补 6 条用例，均落在边界上：

| 用例 | 锁定的约束 |
| --- | --- |
| 250 人（跨页，末页不满） | 第 2 页的人在结果里；末页不满即停止翻页 |
| 恰好 200 人 | **整除时须多问一次**——提前退出条件写成 `<=` 会丢掉最后一页 |
| 跨页重复 10 人 | 去重在召回侧做，`passed` 无重复项 |
| `maxPages=51` | 超限抛 `4001`，不静默截断 |
| `maxPages=1` 而好友有 3 页 | 上限**限制实际拉取页数**，不只是参数校验 |
| 拉到第二页时下游挂掉 | 抛 `5603`，不返回半份名单 |

**「翻了几页」只有下游数得准**：平台拿到的是合并去重后的候选集，页数信息在返回值里已不存在。故在 `SocialProfileStore` 加召回次数计数器，与 `ProviderLedger.recordGrantAttempt`（发起次数与账本分开计数）同一处置——**没有它，「不足一页即停止翻页」只能靠读代码确认**：多问一次拿到空页，最终候选集完全一样。

**本次补的是用例，生产代码一行未改**——三处实现原本都是对的。这正是注入自查的用途：它验的不是代码对不对，而是**用例能不能发现代码变错**。

#### PR-6 实测发现的一处：「规则未配置」与「配了但无人命中」不可合并

**实验分组与营销人群这两条是「命中才保留」**——下游返回的是应保留的集合。若下游对「该活动没配实验」返回空集，编排层按正常路径处理时，空集意味着「没人在组里」，结果是**全员被拒**。

而多数活动本来就不做实验分组。失败形态是**分享名单恒为空，且不报任何错**——端上显示「你没有可邀请的好友」，运营查不出原因。

**修法**：下游对未配置的规则返回 `null`，编排层据此跳过该规则（全员放行）；空集仍表示「配了但一个都没命中」，全员拒绝。两条语义各有用例。

**由 `BaselineFriendFilterIT` 连带发现**：那两条用例只关心关系过滤，不布置实验与人群——于是全部候选人被判「不在实验组」，`shareInvite` 抛 `1611`。

**这类缺陷在「每个用例都先把场景布置齐全」的写法下永远不会显形**，而生产环境里「没配」才是常态。测试的默认场景应当是**最朴素的那个**，不是最完整的那个——完整场景掩盖了「缺省值是否正确」这整类问题。

**注入自查结果**：

| 注入 | 结果 |
| --- | --- |
| 降级处置一律按 fail-open（去掉语义判断） | `FriendFilterIT` 红 1 条（四条 fail-close 规则未阻断） |
| 交换两条规则的失败语义（账户状态改 fail-open、人群改 fail-close） | 红 2 条（两个方向各一） |
| 下推查询漏掉 `status IN (...)` | `BaselineFriendFilterIT` 红 1 条（终态关系被算作进行中） |
| 分享侧跳过过滤（BR-F-12 失效） | 红 2 条 |

**第三条注入验证的是「两套实现各写各的」这个事实**：`status` 谓词在下推与基线两条 SQL 里各出现一次，漏在任一侧都会让该实现把历史关系当成进行中——表现是「这个好友邀请过一次后就再也点不了」。退出标准第 8 条的「两者结果完全一致」正是为这类不对称失效而设。

#### PR-5 注入自查暴露的一处：约束在当前形态下不可观测

**注入「删掉批量语句的 `AND id BETWEEN`」（改为恒真条件），此前的 12 条用例全部保持绿色。**

原因不是用例写得不好，而是**该约束在 V3 的形态下不可观测**：单进程恒为单分片，区间即 `[0, Long.MAX_VALUE]`，删与不删的执行结果完全一致。而 §6.4 ② 明确要求「不因为只有一个分片就省掉 `id BETWEEN`」——省了它，V4 加分片时这条会扫百万行的批量语句要重写，届时需重新验证执行计划。

**修法：直接调 mapper 传一个刻意排除目标行的窄区间**，绕开「单分片」这个使区间不可观测的前提。补 `batchExpireRespectsShardInterval` 与 `groupExpireRespectsShardInterval` 两条，注入后转红。

**三段断言缺一不可**：区间落在目标行之前、之后各断言一次「未被更新」，再用覆盖目标行的区间断言「被更新」——只写前两段的话，「这行本来就治理不了」（比如 `expire_time` 造错了）同样得到两个 0。第三段证明前两次的 0 是区间挡住的。

**这与 §6.6 已记的两处教训同类但不同**：PR-4、PR-5 的「结论无对应用例」是缺用例，此处是**约束存在、用例齐全，而约束在当前部署形态下无法被任何黑盒用例区分**。这类约束只能构造出可观测的条件来验，否则它会在形态变化时静默失效——而那时距离写下它已隔了一个大版本。

**注入自查结果**：

| 注入 | 结果 |
| --- | --- |
| 批量语句不释放 `active_flag` | `FissionExpireGovernanceIT` 红 2 条（含重建关系撞唯一键） |
| `granting_until` 只写 `IS NULL`、去掉超时兜底 | 红 1 条（豁免超时那一半） |
| 处理器返回 `PROCESSING` 而非 `SUCCESS` | 红 3 条（任务终态、播种复活、任务驱动治理） |
| 删掉 `AND id BETWEEN` | **全绿，用例无效（已补两条后转红）** |

**第 2 条注入验证的是 §3.3 那句「只写前一个分支即为漏兜底」**：`granting_until` 的两个分支——`IS NULL`（不在发奖流程）与 `< NOW(3)`（超时兜底）——分别对应 BR-F-26 的正面与防止行永生。测试把两半放在同一个用例里：先断言在途关系被跳过，再把 `granting_until` 置为过去、断言同一条关系转 `EXPIRED`。**分成两个用例则前半段无法排除「治理根本没扫到这一行」**，而那正是分片区间写错时的表现。

#### PR-5 补入的一处技术方案缺口：`fission_group` 缺过期扫描索引

原设计只为 `fission_relation` 安排了过期治理（FR-F09 的字面范围就是关系），而**轮次治理是 PR-2 修正唯一键时连带确定的语义**（见上文「连带确定的一条语义」），当时只写进了文档，扫描它所需的索引到 PR-5 落地治理时才发现缺失。

补 `V3305__add_group_expire_index.sql`，与 `fission_relation.idx_expire` 同构。没有它，轮次治理只能退回 `idx_activity_sponsor`——首列是 `activity_id`，而治理语句不带活动维度，等于全表扫描。

**`fission_group` 行数远小于 `fission_relation`，全表扫描一时不会显形**，正因如此更要在此刻建好：等它显形时，加索引是在一张持续写入的表上做 DDL。

**由 `MultiDataSourceIT` 连带发现新迁移未申报**：该用例逐个断言四库的 `flyway_schema_history` 版本号集合，加脚本不改断言即变红。这是「新增迁移必须显式登记」的机器化形式——比人工核对可靠，且失败信息直接指向缺哪一号。

#### PR-4 实施中修正的三处

**① 幂等前置查必须先于定位关系。** 初版先定位关系再判幂等，而确权成功后关系已进 `DONE` 并释放 `active_flag` —— `selectActive` 查不到它。重复确权因此拿到「关系不存在」而非幂等命中：**对上游是一个会触发告警的错误，而它本该静默成功**。

由用例 `repeatedDoneIsIdempotentOnOutFlowNo` 发现。修法是把幂等查提到最前，命中时用 `selectLatest`（不看 `active_flag`）回查那条已终结的关系。

前置查与插入之间仍保留并发兜底分支：**前置查挡「重传」，唯一索引挡「并发」**，两者不可互相替代。

**② 裂变的任务类与权益的同名，Spring 扫描时 bean 名冲突。** `TaskClaimService` / `TaskHandler` / `BackoffPolicy` 三个类名在两个包下重复，`ConflictingBeanDefinitionException` 让整个上下文起不来。裂变侧统一加 `Fission` 前缀。

**这不是命名洁癖**：默认 bean 名取类的简单名，两个模块各有一份同名类时必然撞车。V4 拆进程后不会有这个问题，但那不是现在不处理的理由。

**③ 注入自查的恢复须用备份文件，不能用 `git checkout`。** 后者的参照系是上一次提交，而在 PR 实施中途，`HEAD` 是上一个 PR —— checkout 回退的不是「注入的那一处」，而是「本 PR 的全部改动」。本次即因此抹掉了整个 `followerDone`，从备份重建后跑全量回归确认无残留。

#### PR-4 逐行审阅发现的缺陷：`QUERY_GRANT` 没有处理器

**裂变侧只注册了 `SPONSOR_REWARD` 一个任务处理器，而 `prepareDone` 落的是 `QUERY_GRANT` —— 那是 `UNKNOWN` 的收敛通路，无人处理。**

失效形态是**静默悬挂**：任务落进调度器的「无处理器」分支，`PENDING → DOING → PENDING` 无限循环；该分支刻意不计 `retry_count`（V2 的设计：等处理器接入期间不该累积重试），于是**连死信都进不去**。关系永久停在 `JOINED`，徒弟究竟收没收到奖无人查证 —— 正是 §5.1 ④ 说的「对账若只扫 `UNKNOWN` 就永久悬挂」。

**原用例分不出这个失效**：它断言查单任务为 `PENDING`，而「等待收敛」与「无人处理」**都是 `PENDING`**。补 `unknownGrantIsActuallyConvergedByQueryTask`，判据改为**驱动调度器后关系推进到 `DONE`**，即收敛真的发生了。

**这一条注入自查产不出。** 注入验的是既有用例是否有效，验不出缺少哪个用例 —— 与 §5.9 的三项是同一条教训，而那三项同样由逐行审阅发现。

**收敛后复用 `settleDone` 的四写**，不另写一段：两条路径若各写一份，「四写完整性」要证明两遍。查单任务手上只有 `(relationId, followerGrantNo)`，其余参数由后缀规则反推 —— 反推而非存进 payload，因为 payload 里存一份就多一处可能与键规则漂移的副本。

#### PR-4 注入自查

| 注入 | 结果 |
| --- | --- |
| 四写拆开：`SPONSOR_REWARD` 任务不落库 | `followerDoneGrantsBothSidesAndAdvancesRelation` 红 —— 「师傅返奖任务须与徒弟发奖同事务落库」 |

第二条挡的是四分类在裂变侧的同一条约束：判 `FAIL` 会让一笔可能已发放的奖被当成没发，补发即重复发放。第三条是补完用例后的回验 —— **先有缺陷、后有用例，再用注入确认用例有效**，三步缺一不可。

# V4：分布式

## 6A. V4 范围

**主题**：把已经正确的系统换成分布式部署形态，验证业务代码不变。

**第 10 项来自 §7.7**，V1/V2 的 `ActivityServiceImpl` 注释已标「V3 加本地缓存」。放在 V4 的理由是它属性能项：预咨询 ≥1000 QPS 的目标要在压测中验证，而压测本身在 V4。

### 6A.2 实现顺序

```
PR-1  5 服务独立打包 + tri 协议 + Nacos             ← 形态切换
        ↓
PR-2  三机部署脚本 + 多实例启动
        ↓
PR-3  多实例调度验证（kill 实例、租约接管）        ← 分布式能力首次可验证
        ↓                        ↘
PR-4  SkyWalking + Prometheus       PR-5  Sentinel 限流降级
        ↓                        ↙
PR-6  Grafana 三块看板 + 告警规则
        ↓
PR-7  k6 全链路压测 + 活动配置缓存
        ↓
PR-8  运维端点收口 + 鉴权                          ← 收口
```

**PR-1 的验收方式是「两套 profile 各跑一遍全链路 e2e，业务代码零改动」**（技术方案 §7.6）。判据不是「能跑起来」，而是 **`git diff` 中不含 `src/main/java` 下的业务逻辑改动** —— 只有配置、注解与打包描述。若出现业务代码改动，如实记录改了什么，那是模块化单体策略的实测代价。

**PR-3 是 §7.4 记载的「分布式能力验证前置说明」的兑现点**：租约抢占、`SKIP LOCKED`、故障接管在 V2 已由多线程持不同 `lease_owner` 在单进程内验证过 SQL 语义，V4 补的是**真实的 `kill -9`**。二者不重复：前者证明 SQL 写对了，后者证明进程死掉时系统真的能恢复。

**PR-8 置于末位但不得省略**：压测与演示都需要 `/api/fault/**`，收口早了自己也用不了。但它必须在交付前完成，不能留到「以后」。

### 6A.3 退出标准

| # | 标准 | 验证方式 |
| --- | --- | --- |
| 1 | **两套 profile 全链路 e2e 均通过，业务代码零改动** | `injvm` 与 `tri` 各跑一遍；`git diff` 断言改动仅在配置/注解/打包 |
| 2 | **kill 掉一个实例，其持有的租约到期后任务被另一实例接管并完成** | 三实例部署，任务执行中 `kill -9`，断言任务最终 `DONE` 且发放记录仍 1 条 |
| 3 | 被 kill 实例苏醒后的写回被 fencing 拒绝 | 断言接管者的结果不被覆盖（沿用 V2 第 9 条的判据，形态改为真实进程） |
| 4 | 多实例并发调度不重复执行同一任务 | 三实例同时跑，断言每条任务仅一个 `lease_owner` 领走 |
| 5 | **RocketMQ 停机时收敛时间退化到查单周期，但仍然收敛、无资损** | 停 broker，注入 `UNKNOWN`，断言最终收敛 + 记录数不变（V3 第 17 条的分布式形态） |
| 6 | Nacos 停机时已建立的连接不中断 | 停注册中心，断言在途请求正常完成 |
| 7 | 三机部署下 k6 六个场景全部达标 | 逐场景对照 §8.5 的断言列 |
| 8 | **秒杀场景跨实例仍不超卖** | 500VU 打到三实例，断言售出恰好 100、库存终值 0（V2 第 14 条的分布式形态） |
| 9 | Grafana 三块看板可用，资损哨兵三项恒为 0 | 压测与混沌注入期间录屏 |
| 10 | 一次请求可按 traceId 在三支柱间双向追踪 | 取一笔业务，从 Grafana 毛刺 → SkyWalking 跳 → 日志与操作记录 |
| 11 | Sentinel 限流生效且降级不影响正确性 | 超阈值请求被拒且不留脏单 |
| 12 | `/api/fault/**` 与 `/api/benefit/convergence/{bizNo}` **已下线或加鉴权** | 无凭证访问返回 401/404；`ShapeFreezeTest` 断言它们不在业务端口暴露 |
| 13 | 活动配置缓存：改配置后秒级生效，存量单仍按快照 | 断言 TTL 内读到旧值、发布主动失效后读到新值；存量单履约金额不变 |

**第 8 条不是第 2 条的重复**：前者验的是跨实例的库存正确性（DB 原子扣减是否仍是唯一的正确性来源），后者验的是任务接管。V2 的 500VU 压的是单进程，锁与库存都在一个 JVM 里 —— **分布式下 Redisson 锁才第一次真正跨进程**，而正确性仍应来自 L3。

**第 12 条的失效形态是「忘了」**：它不影响任何功能，测试不做断言就永远不会红。故列为退出标准并配静态检查。

| 场景 | 目标 | 实测 P99 | 系统错误 | 结论 |
| --- | --- | --- | --- | --- |
| 预咨询 1000 QPS × 30s | ≤100ms | **4.88ms** | 0 | 达标。配置缓存生效，30001 次迭代 |

**创建订单首轮 5405 次「系统错误」是库存售罄，不是故障**。此前的演示与验证把 100 个
库存买光了，`库存不足` 这个业务拒绝跨 Dubbo 后以 5001 回来 —— 补货后归零。这引出下面
那处真实缺陷。

#### 压测暴露的缺陷：`BizException` 跨 Dubbo 丢错误码

`payNotify` 场景 10000 次调用全部记为系统错误，查日志实为 `BizException: 订单不存在`
—— 一个正常的业务拒绝（1721）。

**根因**：`BizException` 未实现 `Serializable`，异常经 tri 协议序列化时降级为
`RuntimeException`，`code` 字段在传输中丢失，调用侧只能按未知异常处理，统一映射为 5001。

`FissionServiceImpl` 的注释早已预言过这件事（「injvm 会把 BizException 包成
RuntimeException 而丢错误码」），当时判断切 tri 后会自动修好 —— **实测相反**：injvm
传引用不序列化，异常对象原样传递，错误码反而是在的；切 tri 后经序列化才真正丢掉。

**影响面**：所有跨服务的业务拒绝在调用侧都表现为系统错误。这不产生资损（拒绝本身生效了），
但让「业务拒绝」与「系统故障」在监控上不可分 —— 而 §8.4 的 P1 告警正是按 5xxx 错误率设的，
限购生效、库存售罄这些正常行为会持续触发告警。

**处置**：V4 本轮不修。它需要给 `BizException` 加序列化支持并在消费侧还原错误码，属跨模块
的异常契约改动，与「业务代码零改动」的本阶段目标冲突。记为已知缺陷，压测脚本按实际行为
分类（见 `k6/throughput.js` 的 `payNotify` 注释）。

#### 第 5 项的偏差：以 Micrometer 替代 SkyWalking

原定接 SkyWalking 做链路追踪。实测判断为收益不抵成本后改以现有设施达成同一目标：

- 挂 agent 需给六个服务各改启动命令，另起 OAP 服务与独立存储，本地演示环境的资源开销
  接近业务服务总和
- 「traceId 贯穿三支柱」这个目标，现有 `TraceIdHolder` + 日志 MDC + 响应体已经达成 ——
  任一条日志、任一个响应都能拿到 traceId 并互相对照
- Micrometer 已随 actuator 接入，指标侧完备

代价是没有可视化的调用链拓扑图。分布式形态下这确实是缺失，如实记录，不粉饰为「不需要」。

## 7. 延后成本评估

### 7.1 零返工延后项

以下均为增量新增而非结构改动，延后不累积返工成本：

| 能力 | 延后为何零成本 |
| --- | --- |
| Redisson 分布式锁 | 套在方法外层，不改内部逻辑 |
| 可靠任务调度器 | 事务边界（冻结项 5）已收拢，建任务仅需在事务内增一条 `insert` |
| RocketMQ 事件广播 | 新增订阅方，对发布侧和现有链路零侵入 |
| 对账 | 纯旁路读，不侵入主链路 |
| 好友过滤优化 | 纯 SQL + 索引改动，不动接口 |
| Sentinel / SkyWalking | 旁路接入，配置级 |
| 裂变模块本身 | 独立 module，不修改既有模块（**前提是冻结项 6 做对**） |

### 7.2 有返工风险的一处

**V3 接裂变时，公共能力层的抽象大概率需要调整，预估改动量 20%。**（V3 的观察方式见 §6.3，退出标准第 1 条与实测记录 §6.6 承接。）

冻结项 6 能挡掉大部分，但挡不干净 —— 一个抽象对不对，只有第二个使用者接入时才能验证。这是设计的固有性质，不是排期能规避的。

**处置**：接入过程中如实记录公共能力层动了哪几处、每处为什么。讲「接第二个玩法时公共能力层动了哪三处、为什么」，比「我一次设计对了」更可信。

### 7.3 V1 明知不对但先这么做的十处

| # | 做法 | 为什么先这样 | 后续怎么改 |
| --- | --- | --- | --- |
| 1 | `payCallback` 事务提交后同步调用 `grantBenefit` | 任务表在 V2 才引入 | V2 改为事务内落 `GRANT` 任务，调度器驱动。影响范围限于 `payCallback` 一个方法内部 |
| 2 | **「已支付未履约」无兜底机制** | 无任务表即无收敛通路 | V2 的可靠任务表就是为补这个缺口而做 |
| 3 | 四分类只实现 `SUCCESS` 分支 | mock 固定成功，其余分支无法验证 | V2 填三个分支的实现。枚举与调用点的分支结构 V1 已定，只加实现不改结构 |
| 4 | `createTrade` 不预占库存 | 库存在 V2 引入 | V2 在同一事务内加原子扣减。事务边界 V1 已收好，是加语句不是改结构 |
| 5 | `quantity` 冻结为 1 | 三处语义要与库存一起定 | V2 随库存与限购一并放开 |
| 6 | `grantBenefit` 串行调用各供应方 | V1 只有两组，串行不影响演示 | **改在 V3**（能力清单第 15 项）：它是性能项而非正确性项，V2 未纳入。虚拟线程扇出（技术方案 §7.2）必须用 `invokeAll` 而非 fail-fast 语义，退出标准第 19 条覆盖 |
| 7 | 支付回调不验签 | L1 防线随咨询凭证一起做 | **已补齐**：PR-4 做咨询凭证（`preConsult` 签发、`createTrade` 验签），PR-6b 做支付通知验签（`4731`，退出标准第 19 条）—— 见下方展开 |
| 8 | **单数据源承载四个库的表** | 单进程形态下配多数据源无收益，且会拖慢 V1 交付 | V2 配四套 `DataSource` + `SqlSessionFactory` + Flyway `locations`，按 mapper 包路径绑定。见下方展开 |
| 9 | `RewardServiceImpl.queryGrant` 查无记录时返回 `FAIL` | V1 仅在幂等冲突后调用，此时记录必然存在 | V2 改为 `UNKNOWN`。查单任务驱动后，「查不到」可能是尚未提交或主从延迟，判 `FAIL` 会让调用方走失败分支 |
| 10 | `mp-reward` 无事务边界类 | 单项发放、下游固定成功，多次自动提交观察不到中间态 | V2 补 `RewardTxService`，与 `OrderTxService` 同构：中间态落库、明细写入、终态回写各为一个事务单元 |

**第 2 条是 V1 最大的缺口**：正向链路能跑通，但在「支付成功后、履约调用前」的窗口崩溃，订单永久停在已收款未发奖，无机制能发现或恢复。可靠任务表不是附加中间件，是这类系统的骨架 —— **V2 补的是 V1 结构上的洞，不是加功能**。

#### 第 8 条展开：单数据源

**现状**：仅配一个 `DataSource` 指向 `db_reward`，`flyway.locations: classpath:db/migration` 将 12 个脚本全部执行于该库，另三库为空。

**影响**：《开发规范》§4.5「禁止跨库 JOIN」失去强制力 —— 当前无跨库 JOIN 是因为尚无此类查询，非架构拦截。V2 的对账与库存会引入跨表统计需求，届时约束须已生效。

**不属 §7.1 零返工项**：需拆分 `DataSource` / `SqlSessionFactory` / `TransactionManager` 三组 Bean、`@MapperScan` 按包绑定、Flyway 分库、集成测试基类改造 —— 改结构而非加语句。V2 成本约一个工作日；拖到 V3 则与服务拆分耦合。

**V2 验收**：在 `mp-benefit-order` 写一条 JOIN `db_reward` 表的查询，确认运行期失败。不以「代码里没有跨库 JOIN」为准。

#### 第 7 条展开：PR-4 只补了 L1 的一半

本条原文「支付回调不验签」被归入「随咨询凭证一起做」，但两者是**两条不同的信任边界**，PR-4 只做了前者：

| | 咨询凭证（PR-4 已做） | 支付通知验签（仍未做） |
| --- | --- | --- |
| 签名方 | 平台自己 | 支付平台 |
| 密钥 | 平台自持，签发与校验同一把 | 对方持私钥，平台持公钥/共享密钥 |
| 挡什么 | 用户伪造或篡改自己的下单请求 | 伪造的支付成功通知 |

误判的代价也不同：凭证被伪造，用户拿到的是一个价格不对的订单，**尚未付款**；支付通知被伪造，平台会认为钱已收到并触发履约，**直接资损**。后者更重。

**当前的实际保护**：`payCallback` 校验金额、币种与商户号，不符即拒绝且不改任何状态（`1731`）。这挡得住「金额被改小」，挡不住「照着真实订单的金额伪造一条成功通知」—— 伪造者只需先下一单，就知道该填多少钱。

**为什么不在 PR-4 一并做**：mock 支付方当前不签名，要做通知验签得先给 mock 加签发侧，那是改 `mp-mock-downstream` 的契约，与 PR-4 的改动面（`benefit-order` 前置流程）没有交集，合在一个 PR 里两边都不好审。

**实际落在 PR-6b**：PR-6 原计划四块一起做（关单主流程 + `CLOSING` + `QUERY_CLOSE` + 通知验签），实施前拆成两个——`6a` 关单三块、`6b` 通知验签。理由与上一段相同且更强：关单改的是 `benefit-order` 的状态机，通知验签改的是 mock 的签名契约，两者在一个 diff 里会互相淹没。拆开后单个 PR 的规模与前几个持平。

**PR-6b 已实施**（详见 §5.6 ⑪）：`PayNotifySigner` 落在 `mp-common`，密钥独立于咨询凭证；验签是 `payCallback` 的第一件事，先于定位主单；BR-B-12 的「不留任何痕迹」按字面实现并断言。**时间戳窗口与防重放不在 V2 范围**——验签挡伪造、`uk_biz_op` 挡重传，主要风险已覆盖，V3 上真实环境时补。

以上十处均为已知的临时形态，非疏漏。

### 7.4 分布式能力的验证前置说明

租约抢占、`SKIP LOCKED`、实例故障接管这些能力，**在单实例上无法被验证** —— V1/V2 阶段代码写了也观察不到现象。

因此统一放在 V3 验收，验收方式必须是**多实例 + 主动 kill**，而不是「代码里有这个逻辑」。V3 的 `docker-compose` 需支持三实例启动。

## 8. 协作方式

| 环节 | 做法 |
| --- | --- |
| 方案 | 每阶段开工前在本文档对应章节补写细化（表、接口、时序），发群评审 |
| 评审 | 三人评审通过后开工，**不另起方案文件** |
| 实现 | 每阶段由一人主导实现 |
| 代码 review | **不设为合入闸**（《开发规范》§2）。CI 全绿即可合入；涉及资金路径的变更由提交者按 §11 自查，也可主动请人看 |
| 轮换 | 按阶段轮换实现人 |
| 收口 | 阶段结束前跑一遍退出标准，逐条打钩，未过不进下一阶段 |

**方案评审保留、代码 review 取消**：方案阶段改一个决定只需改文档，一次对齐可省数周返工；代码阶段的错误多数由 CI 与集成测试拦住，人工逐行读产出率低且阻塞他人时间。

代价是「三人都读懂全部代码」不再由流程保证。若需保留该目标，在阶段收口时单独安排走查，不经由 PR 流程。

每阶段固定产出：代码（CI 全绿）、集成测试（覆盖每条退出标准）、本文档对应章节的实测记录与偏差说明。
