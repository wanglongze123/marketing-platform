# 营销活动平台 分阶段方案

## 0. 本文档的定位

三份文档配套使用，职责不重叠：

| 文档 | 回答什么 |
| --- | --- |
| 《技术方案》 | **怎么设计的、为什么这么设计**。表结构、接口签名、时序、四层防线的推导 —— 终态,不随阶段修改 |
| 《环境与依赖》 | **用什么版本、怎么跑起来** |
| 本文档 | **这一阶段从终态里裁哪一块、裁的时候不能裁掉什么、做到什么程度算完** |

本文档大量引用技术方案章节号（如 `§3.4`），写代码时两份对着看：本文档说「V1 建 `play_biz_record`，全量字段」，具体字段去技术方案 §3.4 抄，不在此重复。

**评审节奏**：每阶段开工前评审本文档对应章节，通过后开工。阶段细化直接补写进本文档，不另起文件。

## 1. 阶段划分

| 阶段 | 一句话 | 交付形态 | 演示什么 |
| --- | --- | --- | --- |
| **V0** | 骨架 | 空壳工程 + CI | 提 PR 触发 CI，全绿 |
| **V1** | 跑通 | 单进程模块化单体，下游 mock 固定成功 | 下单 → 支付回调 → 发放 → 查得到 |
| **V2** | 扛住 | 单进程，下游 mock 可注入异常 | 注入超时自动收敛不重复发放；500VU 抢 100 不超卖 |
| **V3** | 铺开 | 5 服务分布式，多实例 | 新玩法接入后段零改动；kill 实例任务被接管 |

### 1.1 为什么这样切

**按「可验证的正确性」切，不按模块切。** 每一刀落在「能不能演示一个现象」上。按模块切需要先冻结全部接口再付集成成本，而接口在实现中大概率还会变。

**先权益、后裂变。** 权益售卖链路短、状态机简单，适合把「主单 + 操作记录 + 可靠任务」这套骨架立起来。裂变的关系状态机（四态 + 两条终止边 + `active_flag` 部分唯一 + `granting_until` 过期豁免）复杂度高，压在骨架不稳时做会返工。

**V2 在 V3 之前。** 先让系统面对「下游不可靠」，再面对「分布式」。次序颠倒则压测暴露的问题无法归因 —— 锁未生效、结果分类判错、RPC 序列化异常三者混杂。

**分布式化放最后。** 拆服务、多实例是把已经正确的系统分布式化，正确性不来自它们。放前面会让每次调试都要起 5 个进程。

### 1.2 第二个玩法为什么排在 V3

技术方案 §5.0 的核心论断：`FissionFollowerDone` 与 `payCallback` 占据同一架构位置 —— 都是「确权事件 → 触发公共能力层发放」。

这个论断**只有在第二个玩法接入的那一刻才被证明**。裂变接入不是「补一个功能」，而是**对公共能力层抽象的验收**。接入过程中 `reward` 接口的改动量本身就是交付物 —— 改动越小，说明抽象越对。

## 2. V1 形状冻结清单

### 2.1 为什么先讲这个

真正导致返工的从来不是「某功能没做」，而是「某个形状定错了」。功能是**加代码**，形状是**改所有调用方**。

V1 的功能仅为 happy path，无可评之处，**首次评审的重点即这份清单** —— 此时修改成本最低。

### 2.2 八项

| # | 冻结项 | V1 只需做到 | 不冻结的代价 |
| --- | --- | --- | --- |
| 1 | **幂等键进接口 + 唯一索引** | 接口参数带 `clientReqNo` / `opNo`；`uk_idempotent` 系列索引全建 | 改所有调用方签名 + 洗历史数据 |
| 2 | **下游返回四分类枚举** | 定义 `RetStatus{SUCCESS, FAIL, PROCESSING, UNKNOWN}`（命名以技术方案 §4.1 为准）；mock 只返 `SUCCESS`，其余分支 `throw UnsupportedOperationException("V2")` | 若 V1 返 `boolean`，V2 要改每个调用点的分支逻辑 |
| 3 | **状态枚举一次定全** | 三条子状态线按 §3.4 全部写进代码，V1 用不到的也写 | 加枚举值要写 migration，且所有查询条件要重新审查 |
| 4 | **`play_op_record` 建表并写入** | 建表 + 每个写操作插一条 | 后加等于在每条写路径中间插一层，且要与事务边界重新对齐 |
| 5 | **事务边界收成一个方法** | 状态变更用一个 `@Transactional` 方法包住 | 可靠任务表要求「任务写入与状态变更同事务」，边界散了就要重构 |
| 6 | **`reward` 接口通用化** | 入参只有 `playType / activityId / bizOrderNo / opNo / receiverId / rewardItems[]`，**不出现 `orderId` / `tradeNo` 等权益售卖专有概念** | 裂变接入时要改接口，「后段零改动」的论断直接落空 |
| 7 | **Maven 模块按终态切** | 建全部 module，模块间 `injvm` 调用 | V3 拆服务变成重写而非改配置 |
| 8 | **异常映射方向** | facade 层：`BizException` → `FAIL`，**其余未预期异常 → `UNKNOWN`** | 未预期异常若映射为 `FAIL`，调用方会走补偿路径，而下游可能已执行成功 |

**八项加起来，V1 的额外工作量约半天。** 省下它们，V2 起步就是重构。

第 8 项容易被忽略：V1 阶段 mock 固定成功，几乎不会触发异常分支，很容易顺手写成 `catch (Exception e) { return FAIL; }`。这行代码在 V2 引入真实异常后就是资损入口。

### 2.3 第 6 项展开（最容易做错）

V1 只有权益售卖一个调用方，写 `reward` 接口时手会自然地把 `orderId` 塞进去 —— 因为当下只有它。等 V3 接裂变时才发现这是「权益专用发放接口」，不是「通用发放接口」。

**判据**：写完 `grantReward` 签名后，问自己「裂变的师徒双向发奖能不能原样调用这个方法」。答案必须是能。裂变发放的入参是「师傅 userId + 奖励包」，没有订单号 —— 所以 `bizOrderNo` 必须是**通用业务单号**，语义是「调用方的业务标识」，不是「订单号」。

### 2.4 评审时逐项确认的方式

第一次评审的产出应当是这张表填满，而不是「大家觉得没问题」：

| 冻结项 | 确认方式 |
| --- | --- |
| 1 幂等键进接口 | 打开 `CreateTradeReq` / `GrantRewardReq`，确认幂等字段存在；打开 DDL，确认唯一索引存在 |
| 2 四分类枚举 | 打开 `RetStatus.java`，确认四个值；打开调用点，确认是 `switch` 四分支而非 `if (success)` |
| 3 状态枚举定全 | 与技术方案 §3.4 的状态迁移表逐行对照 |
| 4 `play_op_record` | 打开 DDL 与写入代码 |
| 5 事务边界 | 全局搜索 `@Transactional`，确认每处都只包状态变更，且方法内无 RPC |
| 6 `reward` 接口通用化 | 逐字段念一遍 `GrantRewardReq`，任何一个字段说不出「裂变怎么传」即为不通过 |
| 7 模块切分 | `mvn dependency:tree` 看依赖方向 |
| 8 异常映射 | 全局搜索 `catch`，确认没有 `catch (Exception) → FAIL` |

# V0：工程骨架

## 3. V0 做什么

V0 不写业务代码，只回答一个问题：**这套工程结构、构建、CI、测试基础设施，是不是真的能跑通。**

产出是一个 **walking skeleton** —— 一条极简但**贯穿全部层次**的链路，把每一样基础设施都实际用一遍。用不上的基础设施不在 V0 引入。

### 3.1 交付清单

| # | 项 | 内容 |
| --- | --- | --- |
| 1 | 仓库 | 建仓、`main` 分支保护、`.gitignore`、`README.md` |
| 2 | 构建骨架 | 根 `pom.xml` + 全部 module 空壳，版本按《环境与依赖》锁定 |
| 3 | 依赖方向 | 各 module 的 `pom.xml` 只声明允许方向的依赖 |
| 4 | 格式化 | Spotless 绑到 `verify` 阶段 |
| 5 | Git 钩子 | `git-build-hook-maven-plugin` + `.githooks/commit-msg` + `.githooks/pre-commit` |
| 6 | 中间件 | `docker-compose.yml`，V0/V1 只需 MySQL |
| 7 | Flyway | 四个库的 `CREATE DATABASE` + 迁移目录骨架；V0 只有一个脚本 `V0201__create_smoke_record.sql`（发奖库） |

**第 11 项放在 V0 而非 V1**：traceId 与全局异常处理是横切能力，V1 一旦开始写业务代码再补，每个已写的 facade 都要回头改一遍。

### 3.2 冒烟链路的设计

冒烟链路要**贯穿全部层次**，否则验证不到分层是否真的成立。

```
HTTP GET /smoke/{bizNo}
    ↓ gateway
BenefitOrderService.smoke(bizNo)          玩法层
    ↓ Dubbo injvm
RewardService.smoke(bizNo)                公共能力层
    ↓ Dubbo injvm
MockProviderService.smoke(bizNo)          下游 mock
    ↓ 返回
reward 写一行 smoke_record（Flyway 建表）    验证 Flyway + MyBatis-Plus + 事务
    ↓ 返回
gateway 返回 {"code":0,"data":{"bizNo":"...","chain":["gateway","benefit-order","reward","mock"]}}
```

**这条链路验证了七件事**：多模块能编译、Dubbo `injvm` 能通、依赖方向没写反、Flyway 能在真实 MySQL 跑起来、MyBatis-Plus 能写库、Spring Boot 3.5 + JDK 21 组合可用、Testcontainers 能起容器。

**冒烟链路刻意走「逐层向下」**（玩法层 → 公共能力层 → 下游），是为了把四层都串一遍。但这不是唯一合法形状 —— V1 的 `createTrade` 直接调 `mock-downstream` 的支付服务、跨过公共能力层，同样合法（《开发规范》§3.2 规则 1：跨层向下允许）。

**`smoke_record` 建在 `db_reward`**（脚本 `V0201__create_smoke_record.sql`，放 `mp-reward` 模块下），因为链路末端是 reward 写库。表结构极简：`id` + `biz_no` + `create_time`。

**它和全部 `smoke` 方法在 V1 结束时删除**（`V1203__drop_smoke_record.sql`，不修改 V0 的历史脚本）。它是脚手架，不是功能。

### 3.3 依赖方向的验证方式

依赖方向靠 `pom.xml` 编译期强制（见《开发规范》§3.2）。V0 要**实际验证一次它真的会挡住**：

1. 临时在 `mp-reward/pom.xml` 里加一条对 `mp-benefit-order` 的依赖（下层依赖上层）
2. `mvn clean compile`，确认**构建失败**
3. 删掉这条依赖，确认构建恢复
4. 把这次验证的结论写进 PR 描述

省去此步，「依赖方向编译期强制」只是一项未经验证的声明。

### 3.4 CI 必过项

GitHub Actions，触发条件：向 `main` 提 PR、push 到 `main`。

| # | 检查 | 命令 |
| --- | --- | --- |
| 1 | commit message 格式 | 正则校验 Conventional Commits |
| 2 | 代码格式 | `mvn spotless:check` |
| 3 | 编译 | `mvn clean compile` |
| 4 | 单测 | `mvn test` |
| 5 | 集成测试 | `mvn verify`（Testcontainers 起 MySQL） |
| 6 | Flyway 从零执行 | 包含在集成测试内 —— 容器是全新的库，迁移必须从零跑通 |
| 7 | 文档一致性 | `python3 docs/check-docs.py`（V1 补入，见 §4.8） |

任一不过不允许合入。CI 用 JDK 21，与本地一致。第 7 项在 V0 阶段为 6 项，V1 起为 7 项。

**CI 上不要跑 `mvn validate` 装钩子** —— CI 环境不需要 git 钩子，且 `git-build-hook-maven-plugin` 在 detached HEAD 下可能报错。CI 直接从 `spotless:check` 开始。

# V1：跑通

> 预计一周。目标是**一条能演示的正向链路**，以及八项形状冻结全部落地。

## 4. V1 范围

### 4.1 一句话

用户下单 → 支付成功 → 权益发放 → 查得到。下游全部 mock 且固定成功，不考虑任何异常。

### 4.2 链路时序

```
① createTrade                            benefit-order
     校验活动有效（调 activity.queryActivityConf）
     读 benefit_sku → benefit_package → benefit_item，组装 benefit_snapshot
     生成 bizNo（BizNoGenerator）—— 同时作为支付侧的商户订单号
     事务：建 play_biz_record（pay=WAIT_PAY, grant=NOT_START, refund=NONE）
          + 写 play_op_record(CREATE_TRADE, op_seq='', SUCCESS)
     事务外：调 mock 支付下单，传 outTradeNo=bizNo
     第二个短事务：回填 trade_no
                ↓
② payCallback                            benefit-order
     按 outTradeNo（=bizNo）定位主单     ← 不依赖 trade_no 是否已回填
     验金额/币种/商户号，任一不符 → 不改任何状态，返回失败
     事务：按 payStatus 分支做条件更新（见下表）
          + 写 play_op_record(PAY_CALLBACK, op_seq=notifySeq)
     仅当推进到 PAY_SUCCESS 时，事务提交后：
          【V1 同步调用 grantBenefit；V2 改为事务内落 GRANT 任务】
                ↓
③ grantBenefit                           benefit-order
     读 play_biz_record.benefit_snapshot，按 provider_type 分组
     事务 A：条件更新 grant_status NOT_START → GRANTING
            + upsert play_op_record(GRANT_BENEFIT, op_seq='', status=PROCESSING)
            ※ 二者 affected_rows 均为 0 时 → 走重入分支（见下）
     事务外，每组派生 grantOpNo = bizNo + '_G_' + providerType
       → 调 reward.grantReward
       → upsert benefit_fulfillment_record（按 uk_biz_item，一权益项一行）
     事务 B：条件更新 grant_status GRANTING → GRANT_SUCCESS
            + 回写 op_record(GRANT_BENEFIT).status = SUCCESS
                ↓
④ reward.grantReward                     reward
     按 op_no 查 reward_grant_record，命中则直接返回原结果（幂等出口）
     未命中：插入 reward_grant_record(result=PROCESSING)   ← 落库态，非下游返回值
            → 调 mock 供应方（V1 固定返回 SUCCESS）
            → 落 reward_grant_item（一奖励项一行）
            → 回写 reward_grant_record.result = SUCCESS
                ↓
⑤ queryOrder                             benefit-order
     返回主单三子状态 + 履约明细列表
```

#### `payStatus` 的分支处置

`PayCallbackReq.payStatus` 在 V1 只接受两个值，各自的条件更新谓词不同：

| `payStatus` | 条件更新 | 后续 |
| --- | --- | --- |
| `SUCCESS` | `SET pay_status='PAY_SUCCESS' WHERE pay_status='WAIT_PAY'` | `affected_rows=1` 才触发 `grantBenefit` |
| `FAILED` | `SET pay_status='PAY_FAILED' WHERE pay_status='WAIT_PAY'` | 不触发履约，链路终止 |

**`affected_rows=0` 时直接 ACK 返回成功，不抛异常、不重试。** 这是幂等三道闸的第三道生效，不是错误。

**V1 不接受 `CLOSED`**：关单是 V2 的 `closeOrder` 引入的语义，V1 收到该值直接拒绝并返回参数错误。不要为了「以后要支持」提前写分支 —— 提前写的分支没有测试覆盖，而 V2 引入 `CLOSING` 中间态后逻辑还要重写。

#### 关于支付侧的关联号

`bizNo`（`play_biz_record_no`）**同时作为传给支付方的商户订单号**（即微信/支付宝语境下的 `out_trade_no`），回调按它定位主单。

不新增字段的理由：`bizNo` 本身已全局唯一、已有 `uk_biz_no`、且在调用支付方**之前**就已落库。若改为「支付方返回 `tradeNo` 后再按 `tradeNo` 定位」，则在「支付下单成功但 `trade_no` 尚未回填」的窗口内进程崩溃，回调将无法定位业务单 —— 钱收了，订单还是 `WAIT_PAY`。

`trade_no` 仍然回填并保留 `uk_trade_no`，它的作用是反查与对账，不是回调的定位依据。

#### 关于 `quantity`

**V1 冻结为 `quantity = 1`**，`createTrade` 校验不等于 1 时直接拒绝（`4001`）。

字段保留在 `CreateTradeReq` 里（形状冻结，V2 引入库存时才真正生效）。V1 不实现的理由：`quantity > 1` 会牵连三处语义——应付金额如何计算、`RewardItem.qty` 传什么、`benefit_fulfillment_record` 是一项一行还是一份一行。这三处都要在库存与限购一起做时才定得下来，V1 定了大概率要改。

**显式校验而非默默忽略**：如果只是不读这个字段，调用方传 `quantity=3` 会得到一份权益却付了一份的钱，且没有任何报错。

#### 关于 `benefit_snapshot`

在 `createTrade` 时从 `benefit_sku` → `benefit_package` → `benefit_item` 组装并落库，履约时只读快照、不再查配置表。这样即使运营改了权益包，历史订单仍按下单时的配置履约。V1 就要这么做 —— 后改要洗数据。

#### `grantBenefit` 重入怎么处理

V1 虽然是 happy path，但 `grantBenefit` 会被重复调用（重复的支付回调、V2 的任务重试）。**这条路径上有三处会命中约束，都不是错误**：

| 位置 | 现象 | 处置 |
| --- | --- | --- |
| 条件更新 `NOT_START → GRANTING` | `affected_rows = 0` | 读出当前 `grant_status`，按下表分支 |
| 插入 `op_record(GRANT_BENEFIT, '')` | `uk_biz_op` 冲突 | **upsert**：`ON DUPLICATE KEY UPDATE retry_count = retry_count + 1` |
| 插入 `benefit_fulfillment_record` | `uk_biz_item` 冲突 | **upsert**：命中则更新 `provider_order_no` / `grant_status`，不新增行 |

**这三处必须写成 upsert 而非 insert**，否则第二次调用抛 `DuplicateKeyException` 中断链路，而重入的正确行为是正常返回。

按 `grant_status` 的分支：

| 已有 `grant_status` | 处置 |
| --- | --- |
| `NOT_START` | 正常首次执行 |
| `GRANTING` | 继续走发放流程 —— `reward.grantReward` 按 `opNo` 幂等，返回原结果；`benefit_fulfillment_record` 走 upsert 更新为最新结果 |
| `GRANT_SUCCESS` | 直接返回原结果，**不再调用 reward** |

**正确性由 reward 侧的 `uk_op_no` 兜底，不由 benefit 侧的状态判断兜底。** 即使两个线程同时进入 `GRANTING` 分支，`grantOpNo` 是确定性派生的（`bizNo + '_G_' + providerType`），reward 侧只会有一条记录、只发一次奖。状态判断只是避免无谓的 RPC，是优化不是保证。

V2 引入任务调度后，`GRANTING` 分支改为交给查单任务收敛，不再直接重发。

#### `op_record(GRANT_BENEFIT)` 为何跨两个事务

`grantBenefit` 的 `op_record` 先写 `PROCESSING`（事务 A）、调用完成后回写 `SUCCESS`（事务 B），这与 `CREATE_TRADE` / `PAY_CALLBACK` 一次性写 `SUCCESS` 不同。

原因是它包含**跨服务调用**：调用发出前必须先留痕（否则 RPC 发出后崩溃就没有任何记录），调用结果回来后才能判定终态。这正是终态设计中「`op=PROCESSING` + 状态置 `GRANTING` + 查单任务，三者同一事务提交后才发 RPC」的形状（技术方案 §5.3 ④）—— V1 只是暂时缺了查单任务这一项。

**代价**：事务 A 与 B 之间崩溃，`op_record` 永久停在 `PROCESSING`，V1 无机制收敛。这与 §7.3 第 2 条是同一个缺口，V2 的任务表一并补上。

#### 关于 ②→③ 的调用位置

**这是 V1 的临时形态。** V2 改为「payCallback 事务内落 `GRANT` 任务，调度器驱动 `grantBenefit`」，因为任务表在 V2 才引入。冻结项 5（事务边界收成一个方法）保证了这次改动只影响一个方法内部。全部临时形态见 §7.3。

**调用位置必须在事务提交之后**，不在事务内 —— 事务内调 RPC 违反《开发规范》§7.4。V2 改成任务驱动时，正好是在事务内加一行 `insert`、删掉这行同步调用。

**代价要说清楚**：事务提交后、`grantBenefit` 调用前若进程崩溃，订单会停在「已支付未履约」且**没有任何机制能恢复** —— V1 没有任务表。这是 V1 接受的已知缺口，V2 的任务表就是为了补上它。演示时不要刻意制造这个场景。

| 调用 | `opNo` | `rewardItems` | `itemSeq` |
| --- | --- | --- | --- |
| 第一次 | `BZxxx_G_PROVIDER_A` | [项 A] | 0 |
| 第二次 | `BZxxx_G_PROVIDER_B` | [项 B] | 0 |

**签名自检**：裂变的师徒双向发奖调用它时，`playType` 传 `FISSION`、`bizOrderNo` 传裂变关系号、`opNo` 传 `outFlowNo + '_FL'`、`receiverId` 传徒弟 userId、`rewardItems` 传奖励包展开项。**能原样调用，不需要改签名。**

#### 「V1 只实现 SUCCESS 分支」的准确含义

冻结项 2 说其余三个分支 `throw UnsupportedOperationException`，指的是**处理下游返回值的 `switch` 分支**，不是禁止 `PROCESSING` 这个值出现在数据库里。

| 位置 | V1 是否出现非 SUCCESS |
| --- | --- |
| mock 下游的**返回值** | 否，固定 `SUCCESS` |
| 调用方处理返回值的 `switch` | `FAIL`/`PROCESSING`/`UNKNOWN` 三个 case 抛 `UnsupportedOperationException` |
| `reward_grant_record.result` **落库中间态** | **是** —— 调用下游前先落 `PROCESSING`，返回后回写 `SUCCESS` |
| `play_op_record.status` 落库中间态 | **是** —— 同上，`GRANT_BENEFIT` 先 `PROCESSING` 后 `SUCCESS` |

**「调用前先落中间态」是必须在 V1 就做对的形状**：若省略这一步、等结果回来才插记录，则 RPC 发出后崩溃将没有任何痕迹 —— 这正是 V2 查单收敛所依赖的锚点。V1 缺的只是「查单任务」，不是「中间态」。

**mock 支付不自动回调。** `createPay` 只返回 `tradeNo`，不异步触发 `payCallback`。回调由外部触发：

| 场景 | 触发方式 |
| --- | --- |
| 集成测试 | 测试代码主动调用 `payCallback`，自行构造 `notifySeq` |
| 手工演示 | `curl` 打 gateway 的 `/api/benefit/pay-callback` |

**不做自动回调的理由**：自动回调会让「支付完成」变成一个看不见的异步过程，演示时无法暂停在「已付款未履约」这个中间状态观察，V2 要注入回调乱序、重复投递时也无从下手。真实支付平台的通知本来就是外部事件，mock 保持这个形状是对的。

V1 不做验签 —— 签名校验是 L1 防线，V2 随咨询凭证一起做。

#### gateway HTTP 端点

对外响应统一 `{code, message, data, traceId}`，`RetStatus` 的四分类语义不暴露给端（技术方案 §4.1）。

| 方法 | 路径 | 转调 |
| --- | --- | --- |
| POST | `/api/benefit/trade` | `createTrade` |
| POST | `/api/benefit/pay-callback` | `payCallback` |
| GET | `/api/benefit/order/{bizNo}` | `queryOrder` |
| GET | `/api/benefit/convergence/{bizNo}` | `queryConvergence`（V2 PR-2 引入，见 §5.4） |
| GET | `/api/fault/mode` | 故障注入当前模式（V2 PR-3 引入，见 §5.3） |
| POST | `/api/fault/provider/{mode}` | 切换供应方模式，`PROCESSING` 可带 `turns` |
| POST | `/api/fault/pay/{mode}` | 切换支付模式 |
| POST | `/api/fault/reset` | 复位全部模式（不清账本） |
| GET | `/api/fault/ledger/{opNo}` | 下游账本快照，「无重复发放」的跨边界判据 |
| DELETE | `/api/fault/ledger` | 清空下游账本，只在开始一轮新演示时用 |

`grantBenefit` 不对外暴露 —— 它是内部编排入口，V1 由 `payCallback` 调用，V2 由任务调度器驱动。

`RetStatus` → HTTP `code` 的转换规则：

| RetStatus | code | 说明 |
| --- | --- | --- |
| `SUCCESS` | `0` | |
| `FAIL` | 原 `retCode`（`1xxx`/`4xxx`） | 展示给用户 |
| `PROCESSING` / `UNKNOWN` | `0`，`data.status` 标记处理中 | **对端不返回失败** —— 结果未定时告诉用户「失败」，用户会重试，形成重复下单 |

上表是终态规则。V1 下游固定成功，仅 `SUCCESS` 一行被真实走到，`data.status` 字段与其余三行的分支留待 V2 填实现。

**业务拒绝与请求级失败分开处置**：业务拒绝走 HTTP 200 + 业务码，由端侧按 `code` 分支；路由不存在、方法不支持、报文不可读属请求级失败，保留框架给出的 4xx，仅套用统一响应壳。二者不可合并 —— `5xxx` 的语义是「结果未知，按 UNKNOWN 查单收敛」，若把客户端错误记为 `5001`，调用方会为一件未发生的事发起重试与对账。

| --- | --- |
| `marketing_activity.cur_version` | seed 里写 `1` |
| `play_biz_record.config_version` | 建单时读 `marketing_activity.cur_version`，即恒为 `1` |

**`mp-common` 里两个工具类是 V1 必须有的**，把《开发规范》§5 的规则集中在一处，review 只需盯这两个类：

```java
/** 业务单号：全局唯一，每次调用必须不同。UUIDv7 —— 近似有序且随机空间充足 */
public final class BizNoGenerator {
    public static String bizNo()         { return gen("BZ"); }   // play_biz_record_no
    public static String fulfillmentNo() { return gen("FF"); }   // 履约明细号
    private static String gen(String prefix) {
        return prefix + UuidCreator.getTimeOrderedEpoch().toString().replace("-", "");
    }
}

/** 幂等键：确定性可重算，同一操作重试必须得到同一个值 */
public final class IdempotentKeys {
    /** 履约发奖：一次调用 = 一个供应方 */
    public static String grantOpNo(String bizNo, String providerType) {
        return bizNo + "_G_" + providerType;
    }
    /** 支付回调 —— payStatus 不入键 */
    public static String payCallback(String tradeNo, String notifySeq) {
        return tradeNo + "_" + notifySeq;
    }
    // V2 补：closeOrder；V3 补：refundNo、revokeNo、followerGrantNo、sponsorFlowNo
}
```

**两个类的规则相反**，放在一起是为了让这个反差在代码里可见：`BizNoGenerator` 必须用随机源，`IdempotentKeys` 恰恰禁止随机源。把它们写成一个工具类是常见的错误起点。

**不用「时间戳 + 8 位随机」**：32 bit 随机空间在同一秒内约 7.7 万次调用即有 50% 碰撞概率，压测（500 VU）与并发重试下不是理论风险。UUIDv7 前 48 bit 是毫秒时间戳，同样近似有序（降低 B+ 树页分裂），但随机空间足够。理由详见《开发规范》§5.2。

**无论生成器多可靠，插入路径都要处理唯一冲突**：捕获 `DuplicateKeyException` → 重新生成 → 重试，最多 3 次。生成器是概率保证，唯一索引是确定性保证。

#### 缺陷

四处，均由实施期自查与集成测试发现。

**① `@Transactional` 同类内部调用静默失效。** 初版事务方法与编排逻辑同在 `BenefitOrderServiceImpl`，注解不经代理、不生效、不报错，后果是状态已改而操作记录未落库。修正：抽出 `OrderTxService`，五个事务方法各为一个事务单元。

**② 全局异常处理器把请求级失败吞成 `5001`。** `HttpEndpointIT.grantBenefitIsNotExposedOverHttp` 发现：不存在的路由期望 404，实测 500。`@ExceptionHandler(Exception.class)` 捕获了 `NoResourceFoundException`。修正：继承 `ResponseEntityExceptionHandler`，沿用框架的状态码映射，仅覆写响应体包装。

**④ pre-commit 钩子在非交互 shell 下找不到 `JAVA_HOME`。** git 钩子不读 `.zshrc`，表现为终端 `mvn` 正常、提交即失败。修正：钩子自行解析 JDK 路径，按《环境与依赖》§1.1 的 brew formula 路径兜底。

### 5.3 故障注入控制面

**注入模式必须区分「下游已执行」与「下游未执行」。** 若注入实现为「抛异常且不落库」，则 `UNKNOWN` 收敛时查到「未发放」并重发，结果正确 —— 但该场景下即使把 `UNKNOWN` 误判为 `FAILED` 走补偿，结果同样正确。四分类的价值在此场景不可见。

需要构造的是**下游已执行成功但调用方未收到结果**：mock 先记账，再抛超时。此时误判 `FAILED` 触发补发即为重复发放。

**mock 必须持有独立账本**。`reward_grant_record` 是平台侧记录，且在调用 mock 之前就已落 `PROCESSING`（§4.2 三段式）—— 对它计数只能证明平台幂等，不能证明供应方实际只发了一次。「下游已执行」必须建模在服务边界的另一侧：

- mock 供应方维护自有账本，键为 `opNo`，put-if-absent 语义等价唯一索引。不落四个业务库 —— 外部系统的存储不属于平台 schema，进程内结构即可，重启丢失可接受（mock 无状态重启本就是允许的）
- 契约补 `MockProviderService.queryGrant(opNo)`，返回账本中的结果与 `providerOrderNo`；**查无返回 `UNKNOWN`**，不返回 `FAIL` —— 查无可能是提交在途，判失败会触发误补偿（§7.3 缺陷 9 同源）
- 「无重复发放」的最终断言落在两侧：平台记录计数 1，且 mock 账本中该 `opNo` 的 `providerOrderNo` 与平台侧一致、全程不变

| 模式 | mock 行为 | 期望收敛 |
| --- | --- | --- |
| `SUCCESS` | 正常返回 | 默认 |
| `TIMEOUT_AFTER_COMMIT` | **先写账本**，再抛超时 | 短退避查单 → 查得 → `GRANT_SUCCESS`，不重发；两侧账本各 1 条 |
| `TIMEOUT_BEFORE_COMMIT` | 不写账本直接抛超时 | 短退避查单 → 连续查无达阈值 → 以**原 `opNo`** 重发；最终两侧各 1 条 |
| `PROCESSING` | 受理但不完成，第 N 次查单转成功 | 长退避，退避序列与短退避不同 |
| `FAIL` | 确定失败 | 唯一允许走失败分支的一类 |

**查无不立即重发**。`queryGrant` 查无返回 `UNKNOWN`，单次查无不足以判定「原调用未到达」—— 可能只是下游提交延迟。规则：`QUERY_GRANT` 连续查无满 3 次（短退避跑完一轮）才落 `GRANT` 任务重发，且必须复用原 `opNo`。

> **「连续」须按字面实现**（V2 PR-3 实施时补充）：计数不能复用任务的 `retry_count`——后者由调度器对所有非终态结果自增，`PROCESSING` 也算在内，于是「连续查无 3 次」会退化成「查询 3 次且最后一次查无」。下游回过一次 `PROCESSING` 即表明它已受理这笔请求，此后的查无更可能是查询侧抖动，重发就成了对一笔已受理的请求再发一次。计数独立存于任务 `payload`，遇 `PROCESSING` 归零。该阈值的误判是安全的：若原调用实际已到达，重发携带同一 `opNo`，被 mock 账本 put-if-absent 挡下并返回原 `providerOrderNo` —— 幂等键复用让「重发时机判早了」不构成资损，判晚了只是收敛慢。

模式经 HTTP 端点在运行期切换，作用于 mock 供应方与 mock 支付两侧。自动化测试与人工验证共用同一入口。

**不做成 Spring Profile 或测试作用域 Bean**：手动验证在运行中的实例上进行，需要在不重启的前提下切换模式。

### 5.4 收敛过程可观测

`queryOrder` 只返回三条子状态的当前值。V2 的退出标准 1、3 断言的是迁移序列与退避间隔，终态查询无法区分「正确收敛」与「未发生故障」。

新增只读端点，按 `bizNo` 返回：

| 来源 | 字段 | 用途 |
| --- | --- | --- |
| `play_op_record` | `op_type`、`status`、`downstream_result`、`retry_count` | `status` 与 `downstream_result` 分列承载本地执行态与下游四分类结果（技术方案 §6.6），合并即无法区分 `PROCESSING` 与 `UNKNOWN` |
| `benefit_task` | `task_type`、`status`、`retry_count`、`next_time`、`lease_owner`、`lease_expire` | 当前退避位置与租约持有者 |

**端点提供的是快照，序列由观察者累积**。`benefit_task` 每轮重试原地覆盖 `next_time` / `retry_count`，表中任一时刻只有当前值，不存在「相邻两次」。两类观察者各自累积：

- 自动化测试：调度器触发改为测试内显式驱动（`scheduler.runOnce()`），每驱动一轮立即读一次端点，序列保存在测试变量中。不依赖真实时间流逝，也不依赖轮询碰运气
- 人工验证：脚本按固定间隔轮询该端点，逐次记录 `retry_count` 与 `next_time`，形成 5.8 的「状态迁移序列」列

**不为序列建事件日志表**：它只服务验收观察，落库会让一张仅测试使用的表混进业务 schema，且每轮重试多一次写放大。终态方案里收敛历史的正式载体是 `play_op_record.retry_count` 与对账（技术方案 §6.8），不是逐次快照。

该端点同时是演示入口：「注入超时 → 观察 `GRANT_UNKNOWN` 停留 → 三次退避后收敛 → 发放记录仍为 1 条」为可现场复现的完整序列。

**V3 拆分布式后该端点需加鉴权或下线**，届时它将暴露跨服务的内部单据状态。

### 5.5 `payCallback` 放开 `CLOSED`

V1 的 `parsePayStatus` 对 `CLOSED` 返回 `4001`（§4.2）。退出标准第 5 条要求验证「先 `SUCCESS` 后 `CLOSED`」的乱序拦截，故 V2 须放开该值，否则第二条通知在参数校验处即被拒，执行不到条件更新。

放开后三个值的条件更新谓词，照录技术方案 §6.4 的条件更新清单，无新增推导：

| `payStatus` | 条件更新 |
| --- | --- |
| `SUCCESS` | `SET pay_status='PAY_SUCCESS' WHERE pay_status IN ('WAIT_PAY','CLOSING')` |
| `FAILED` | `SET pay_status='PAY_FAILED' WHERE pay_status='WAIT_PAY'` |
| `CLOSED` | `SET pay_status='CLOSED' WHERE pay_status IN ('WAIT_PAY','CLOSING')` |

`SUCCESS` 的前置状态含 `CLOSING`：关单受理后、确认前用户完成支付时，支付成功必须能够推进，否则钱已收而订单被关。这条入边是 V2 新增的路径中唯一「拦截了反而资损」的一条，退出标准第 6 条单独覆盖。

**`payStatus` 仍不入幂等键**（《开发规范》§5.5）。理由是键的构成原则而非乱序场景 —— 乱序的 `SUCCESS` 与 `CLOSED` 本就携带不同 `notifySeq`，各自成键、各自留痕，拦截本来就只能靠条件更新。`payStatus` 不入键，是因为它是**被通知的结果**而非**操作的标识**：键中混入结果字段后，同一条通知（同一 `notifySeq`）重传时若该字段被上游修正，重传会被当成新操作插入成功，`uk_biz_op` 挡重传的职责即告失效。

`op_seq` 仍取 `notifySeq`（《开发规范》§5.6）—— 三个 `payStatus` 是三个不同的业务事件，各自留痕。

### 5.6 关键取值与依据

七项技术方案未给出取值或实现方式，此处定下，实施按此执行。

**① 跨库约束：配四个分库账号。**

四个 schema 位于同一 MySQL 实例时，多数据源只拦截不带库名限定的引用。实测：`SELECT ... FROM benefit_sku JOIN other` 报 `ERROR 1146`，`SELECT ... FROM db_reward.benefit_sku JOIN db_benefit.other` 正常返回。仅配多数据源，《开发规范》§4.5 的「禁止跨库 JOIN」在运行期无强制力。

在 `docker/mysql-init` 中为四库各建一个仅授权自身 schema 的账号，各数据源使用各自账号：

```sql
CREATE USER 'mp_reward'@'%' IDENTIFIED BY 'mp_reward';
GRANT ALL PRIVILEGES ON db_reward.* TO 'mp_reward'@'%';
-- 其余三库同构
```

代价是本地排查不能再用单一连接跨库查数，需按库切换账号。收益是约定变为约束，且 V3 拆实例后连接形态不变 —— 届时只改 host，不改权限模型。

**② 事务管理器按库绑定，禁止无限定的 `@Transactional`。**

四套 `DataSource` 意味着四个 `PlatformTransactionManager`。Spring 对不带 `transactionManager` 属性的 `@Transactional` 按类型注入取 `@Primary`—— 若 `OrderTxService` 的事务落到别库的管理器上，`db_benefit` 的写各自自动提交，「状态、操作记录、任务同库同事务」（技术方案 §6.5 本地消息表的前提）静默失效，**不报错**。这与 V1 缺陷 ①（同类调用注解不生效）同属一族：事务问题的失效形态是「没有事务」而非「事务出错」。

处置三条：

- 每库独立 `SqlSessionFactory` + `TransactionManager`，Bean 名带库前缀（`benefitTransactionManager` 等）
- 每模块定义组合注解（如 `@BenefitTx` = `@Transactional(transactionManager = "benefitTransactionManager")`），业务代码只用组合注解
- `ShapeFreezeTest` 增加静态检查：`*TxService` 中出现不带 `transactionManager` 属性的裸 `@Transactional` 即失败；同时以运行期回滚 IT 验证绑定正确（退出标准第 11 条）—— 静态检查证明「写了限定」，回滚 IT 证明「限定指向了正确的库」，缺一不可

**③ 任务表的写回全部携带 fencing 条件。**

技术方案 §7.3 给了领取的 SQL，未给写回的。租约保证的接管窗口存在一个残余竞争：A 持有任务但执行变慢，租约过期，B 依租约语义正当接管并完成；随后 A 苏醒，把同一任务再写一遍终态，或续租把 B 的租约覆盖。A 的写不拦下，接管就只在「A 真死了」时正确，而租约过期恰恰无法区分「死了」与「慢了」。

处置：完成、失败重排、续租、死信四类 UPDATE 一律追加持有者校验 ——

```sql
UPDATE benefit_task SET ...
 WHERE id = ? AND status = 'DOING' AND lease_owner = ?
```

`affected_rows = 0` 即租约已被接管，当前实例立即放弃该任务且不得重试本次写回。业务副作用无需回滚 —— A 若已调了下游，B 接管后携带同一 `op_no` 重做，被下游幂等挡住，这正是「幂等键复用」承担的兜底。

**④ 租约 30 秒，任务执行超 20 秒续租一次。**

租约需长于单次任务执行耗时，否则任务执行中租约到期、被另一实例接管，同一任务并发执行两次；需短于可接受的故障接管延迟，否则实例宕机后任务长时间无人处理。V2 的任务均为单次 RPC + 两个短事务，正常耗时在百毫秒级，30 秒留了两个数量级的余量。续租阈值取租约的三分之二。

**⑤ 死信阈值：查单类 10 次，执行类 5 次。**

两类任务的失败语义不同。查单（`QUERY_GRANT` / `QUERY_CLOSE`）是读操作，重试无副作用，且 `PROCESSING` 本就可能持续较久，阈值可高；执行类（`GRANT` / `STOCK_RELEASE`）每次重试都是一次下游调用，连续 5 次失败已说明不是瞬时故障。

按长退避序列，查单 10 次约覆盖 1 小时，超出即需人工介入。

**⑥ 可观测端点：V2 无鉴权，V3 移入独立的运维端口。**

V2 单进程、仅本地运行，加鉴权无收益。V3 拆分布式后该端点会暴露跨服务的内部单据状态，届时移至独立端口并与业务端口分离，不对外网暴露。这与 `dubbo.application.qos-enable` 的处置一致。

**⑦ 任务的时间基准取数据库时钟，应用不传绝对时刻。**

调度判据是 `next_time <= NOW(3)`，右侧恒为数据库时钟。若 `next_time` 由应用侧 `LocalDateTime.now()` 写入，则是「拿 JVM 时钟写、拿 DB 时钟比」——两个时钟一旦不一致，任务要么永不到期、要么全部立刻到期。

PR-2 实施时即遭遇：Testcontainers 起的 MySQL 默认 UTC，而 JDBC URL 声明 `Asia/Shanghai`，`next_time` 比容器的 `NOW(3)` 超前 8 小时，调度器一条任务也领不到，表现为「履约不执行」而非任何时间相关的报错。

因此入队接口的入参是**延迟秒数**而非时刻，`next_time` 由 `DATE_ADD(NOW(3), INTERVAL ? SECOND)` 在库内算出。V3 多实例部署时这一点更关键：实例间时钟漂移会让调度时快时慢且无法复现。同理，退避后推也走 `NOW(3)`，`retry_count` 由 SQL 自增而非应用读出加一回写——后者在接管场景下会用陈旧值覆盖接管者的计数。

**已在技术方案中给出，此处不重复决策**：`CLOSING` 阶段不落任何库存任务，待 `QUERY_CLOSE` 收敛到 `CLOSED` 或 `PAY_SUCCESS` 后由确定的一方落任务；库存类任务的 `op_no` 取 `biz_no + '_' + task_type`（技术方案 §7.4）。

**退避序列的验证方式**：退避基数须可配置，测试注入毫秒级基数。第 1、3 条断言的是**两条序列的倍率关系与彼此不相等**，不是绝对值 —— 生产长退避跑满需 12.5 分钟，而现有集成测试全套不足 8 秒。人工验证按生产取值跑，记录真实收敛耗时。

**`PROCESSING` 在 V2 只有查单一条收敛通路**。技术方案 §6.6 的处置是「等下游通知为主，查单兜底」，其中「下游通知」指 `providerCallback`，属 V3 范围（§6）。V2 的 `PROCESSING` 收敛完全依赖查单任务，长退避取值因此不能太长，否则演示时等不到收敛。该约束在 V3 引入回调后解除。

**第 2、4、6、8、9、10、11、15 条为本次评审后新增或改写。**

第 2、4 条：`TIMEOUT_BEFORE_COMMIT` 与 `FAIL` 均为 V2 新实现的分支，只列人工验证则回归无保护。

第 6 条：`CLOSING → PAY_SUCCESS` 是放开 `CLOSED` 后新增的入边中唯一「拦截了反而资损」的一条（5.5），乱序用例（第 5 条）验的是「该拦的拦住」，这条验的是「不该拦的放行」，缺任一侧都不完整。

第 8、9 条：`SKIP LOCKED` 与租约解决两个不同问题（技术方案 §7.3）。前者管同轮扫描的并发互斥，后者管跨轮次的僵尸任务回收。租约失效的后果是被 kill 实例持有的 `GRANT` 任务永久停在 `DOING`，即「已收款未发奖」。V2 为单进程形态，`kill -9` 验证留在 V3；但抢占、接管、fencing 均为 SQL 语义，与部署形态无关，可由多线程持不同 `lease_owner` 在单进程内验证。若不在 V2 覆盖，则该段代码自编写至 V3 之间不会被执行。

第 10 条对应能力清单第 3 项。V1 的 `IdempotencyIT` 均为单线程重复调用，验证的是「第二次调用返回原结果」；并发场景验证的是「两个线程同时进入同一分支时唯一索引生效」，二者的失效模式不同。

第 11 条对应能力清单第 9 项。V1 缺陷 ① 即事务边界问题：`@Transactional` 用于同类内部调用时不经代理、不生效、不报错。静态检查证明「注解写了且带限定」，回滚 IT 证明「限定指向正确的库」—— 多数据源下二者缺一不可（5.6 ②）。

第 15 条对应能力清单第 6 项。k6 通过不能证明 Redisson 生效：DB 原子扣减单独即可满足 0 超卖，删掉分布式锁后正确性结果不变。这正是技术方案 §6.1 的论断 —— L2 是性能优化，L3 才是正确性兜底。锁的价值只能从 L3 的负载侧读出：锁生效时并发被串行化在锁上，条件更新冲突与唯一键冲突应当更少。只看锁自身的竞争计数没有意义 —— 移除锁后该指标必然为 0，那只说明锁代码没有运行。

**「无重复发放」的判定口径**，四处同时成立：

| 断言 | 挡住的失效 |
| --- | --- |
| `reward_grant_record` 按 `op_no` 计数 = 1 | 平台侧重复受理 |
| `reward_grant_item` 按 `(op_no, item_seq)` 无重复 | 明细重复插入（记录仅 1 条但明细翻倍时，只查记录表漏检） |
| `benefit_fulfillment_record` 按 `(play_biz_record_no, benefit_item_id)` 无重复 | 订单侧履约明细重复 |
| mock 账本按 `opNo` 计数 = 1，且 `providerOrderNo` 与平台侧一致、收敛前后不变 | 供应方实际重复发放 —— 前三条都只证明平台记录，只有这条跨过服务边界（5.3） |

不以日志或调用次数为准 —— 收敛过程本就包含重复调用，重复调用不等于重复发放。

**人工验证**

自动化测试验证代码逻辑是否正确，被追问的是观察到了什么现象。5.3 的五种模式各在运行中的实例上跑一遍，记录填入 5.8。

## 7. 延后成本评估

### 7.1 零返工延后项

以下均为增量新增而非结构改动，延后不累积返工成本：

| 能力 | 延后为何零成本 |
| --- | --- |
| Redisson 分布式锁 | 套在方法外层，不改内部逻辑 |
| 可靠任务调度器 | 事务边界（冻结项 5）已收拢，建任务仅需在事务内增一条 `insert` |
| RocketMQ 事件广播 | 新增订阅方，对发布侧和现有链路零侵入 |
| 对账 | 纯旁路读，不侵入主链路 |
| 好友过滤优化 | 纯 SQL + 索引改动，不动接口 |
| Sentinel / SkyWalking | 旁路接入，配置级 |
| 裂变模块本身 | 独立 module，不修改既有模块（**前提是冻结项 6 做对**） |

### 7.2 有返工风险的一处

**V3 接裂变时，公共能力层的抽象大概率需要调整，预估改动量 20%。**

冻结项 6 能挡掉大部分，但挡不干净 —— 一个抽象对不对，只有第二个使用者接入时才能验证。这是设计的固有性质，不是排期能规避的。

**处置**：接入过程中如实记录公共能力层动了哪几处、每处为什么。讲「接第二个玩法时公共能力层动了哪三处、为什么」，比「我一次设计对了」更可信。

### 7.3 V1 明知不对但先这么做的十处

| # | 做法 | 为什么先这样 | 后续怎么改 |
| --- | --- | --- | --- |
| 1 | `payCallback` 事务提交后同步调用 `grantBenefit` | 任务表在 V2 才引入 | V2 改为事务内落 `GRANT` 任务，调度器驱动。影响范围限于 `payCallback` 一个方法内部 |
| 2 | **「已支付未履约」无兜底机制** | 无任务表即无收敛通路 | V2 的可靠任务表就是为补这个缺口而做 |
| 3 | 四分类只实现 `SUCCESS` 分支 | mock 固定成功，其余分支无法验证 | V2 填三个分支的实现。枚举与调用点的分支结构 V1 已定，只加实现不改结构 |
| 4 | `createTrade` 不预占库存 | 库存在 V2 引入 | V2 在同一事务内加原子扣减。事务边界 V1 已收好，是加语句不是改结构 |
| 5 | `quantity` 冻结为 1 | 三处语义要与库存一起定 | V2 随库存与限购一并放开 |
| 6 | `grantBenefit` 串行调用各供应方 | V1 只有两组，串行不影响演示 | V2 改虚拟线程扇出（技术方案 §7.2），且必须用 `invokeAll` 而非 fail-fast 语义 |
| 7 | 支付回调不验签 | L1 防线随咨询凭证一起做 | V2 引入 |
| 8 | **单数据源承载四个库的表** | 单进程形态下配多数据源无收益，且会拖慢 V1 交付 | V2 配四套 `DataSource` + `SqlSessionFactory` + Flyway `locations`，按 mapper 包路径绑定。见下方展开 |
| 9 | `RewardServiceImpl.queryGrant` 查无记录时返回 `FAIL` | V1 仅在幂等冲突后调用，此时记录必然存在 | V2 改为 `UNKNOWN`。查单任务驱动后，「查不到」可能是尚未提交或主从延迟，判 `FAIL` 会让调用方走失败分支 |
| 10 | `mp-reward` 无事务边界类 | 单项发放、下游固定成功，多次自动提交观察不到中间态 | V2 补 `RewardTxService`，与 `OrderTxService` 同构：中间态落库、明细写入、终态回写各为一个事务单元 |

**第 2 条是 V1 最大的缺口**：正向链路能跑通，但在「支付成功后、履约调用前」的窗口崩溃，订单永久停在已收款未发奖，无机制能发现或恢复。可靠任务表不是附加中间件，是这类系统的骨架 —— **V2 补的是 V1 结构上的洞，不是加功能**。

#### 第 8 条展开：单数据源

**现状**：仅配一个 `DataSource` 指向 `db_reward`，`flyway.locations: classpath:db/migration` 将 12 个脚本全部执行于该库，另三库为空。

**影响**：《开发规范》§4.5「禁止跨库 JOIN」失去强制力 —— 当前无跨库 JOIN 是因为尚无此类查询，非架构拦截。V2 的对账与库存会引入跨表统计需求，届时约束须已生效。

**不属 §7.1 零返工项**：需拆分 `DataSource` / `SqlSessionFactory` / `TransactionManager` 三组 Bean、`@MapperScan` 按包绑定、Flyway 分库、集成测试基类改造 —— 改结构而非加语句。V2 成本约一个工作日；拖到 V3 则与服务拆分耦合。

**V2 验收**：在 `mp-benefit-order` 写一条 JOIN `db_reward` 表的查询，确认运行期失败。不以「代码里没有跨库 JOIN」为准。

以上十处均为已知的临时形态，非疏漏。

### 7.4 分布式能力的验证前置说明

租约抢占、`SKIP LOCKED`、实例故障接管这些能力，**在单实例上无法被验证** —— V1/V2 阶段代码写了也观察不到现象。

因此统一放在 V3 验收，验收方式必须是**多实例 + 主动 kill**，而不是「代码里有这个逻辑」。V3 的 `docker-compose` 需支持三实例启动。

## 8. 协作方式

| 环节 | 做法 |
| --- | --- |
| 方案 | 每阶段开工前在本文档对应章节补写细化（表、接口、时序），发群评审 |
| 评审 | 三人评审通过后开工，**不另起方案文件** |
| 实现 | 每阶段由一人主导实现 |
| 代码 review | **不设为合入闸**（《开发规范》§2）。CI 全绿即可合入；涉及资金路径的变更由提交者按 §11 自查，也可主动请人看 |
| 轮换 | 按阶段轮换实现人 |
| 收口 | 阶段结束前跑一遍退出标准，逐条打钩，未过不进下一阶段 |

**方案评审保留、代码 review 取消**：方案阶段改一个决定只需改文档，一次对齐可省数周返工；代码阶段的错误多数由 CI 与集成测试拦住，人工逐行读产出率低且阻塞他人时间。

代价是「三人都读懂全部代码」不再由流程保证。若需保留该目标，在阶段收口时单独安排走查，不经由 PR 流程。

每阶段固定产出：代码（CI 全绿）、集成测试（覆盖每条退出标准）、本文档对应章节的实测记录与偏差说明。
