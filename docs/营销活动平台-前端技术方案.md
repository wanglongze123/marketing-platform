## 0. 先说结论

三句话：

1. **方向对**：目标形态确实是「活动平台 → 玩法（权益售卖 / 裂变）→ 每个玩法多页面」，且必须换成有构建链的 Web 工程，单文件 HTML 撑不住这个结构。
2. **但今天后端只支撑得起其中一小块**：现有对外 HTTP 端点共 **3 个**，全部属于权益售卖正向链路。活动管理、裂变、退款、订单列表的接口**都还不存在**，其中裂变模块 `mp-fission` 目前只有一个 `pom.xml`。
3. **所以方案分两段**：先搭骨架 + 把权益售卖正向链路做成真实可用的页面，其余页面以**契约先行 + 显式 MOCK 标记**的方式占位，随 V2/V3 后端到位逐块换成真实接口。不把 mock 页面伪装成能用的功能。

## 1. 现状盘点：后端到底提供了什么

这一节是整份方案的约束来源。**不先对齐这个，前端设计出来就是空中楼阁。**

### 1.1 现有对外端点（全部）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/benefit/trade` | 下单 |
| POST | `/api/benefit/pay-callback` | 支付结果通知 |
| GET | `/api/benefit/order/{bizNo}` | 单笔订单查询 |

就这三个。`grantBenefit` 不对外暴露（内部编排入口）。

### 1.2 前端想要、但后端还没有的能力

| 页面需要的能力 | 后端现状 | 排期 |
| --- | --- | --- |
| 活动列表 / 创建 / 发布 / 上下线 | **无接口**，配置由 seed SQL 初始化 | 《分阶段方案》§4.6 列为**范围外** |
| SKU / 权益包 / 权益项 管理 | **无接口**，同上 | 范围外 |
| 按用户查订单列表 | **无接口**，只能按 bizNo 单查 | 未排期 |
| 预咨询试算（价格、库存、限购） | **无接口** | V2 |
| 订单关闭 | **无接口** | V2 |
| 裂变全部 13 个接口 | **模块为空**，`mp-fission` 只有 pom.xml | V3 |
| 退款准入 / 权益回收 / 退款执行 | **无接口** | V3 |
| 操作记录查询（客服排查用） | 有表 `play_op_record`，**无查询接口** | 未排期 |
| 对账结果、可靠任务看板 | 表都还没建 | V2 / V3 |

**结论**：按 PRD 的完整页面清单算，今天能接真实接口的大约只有「商品页 + 收银台 + 订单详情」三屏。这不是前端的问题，是后端阶段决定的，方案必须如实反映，而不是画一个 30 个页面的大饼。

### 1.3 三条必须在前端编码的后端语义约束

这三条是这个项目**特有**的，通用后台模板不会带，漏掉就会做出「看起来对、实际会造成资损」的前端。

**① 五个结果类枚举不得合并、不得对齐取值**

`mp-common` 里 `GrantStatus`（主单，带 `GRANT_` 前缀）与 `ItemGrantStatus`（履约明细，无前缀）是**不同层级**，两张表列名都叫 `grant_status`。后端用两个枚举类型隔开，使串用变成编译错误。`ShapeFreezeTest` 会断言这两组终态**完全不重叠**。

前端同样不能合并成一张 `STATUS_MAP`。必须按枚举分别建映射表，否则把明细的 `SUCCESS` 当主单状态渲染，页面会显示「已到账」而主单其实还在 `GRANTING`。

同理 `RetStatus.FAIL`（下游回报）与 `OpStatus.FAILED`（本地判断）刻意拼写不同，前端不得归一。

**② 错误码按区间决定处置方式，不是「非 0 即失败」**

| 区间 | 语义 | 前端处置 |
| --- | --- | --- |
| `1xxx` | 业务规则拒绝 | 终态失败，**可展示给用户**，不重试 |
| `4xxx` | 入参/凭证非法 | 终态失败，不重试，属前端 bug 或过期凭证 |
| `5xxx` | 系统异常，**结果未知** | **不得显示「失败」**，须按查单收敛 |

`5001` 的语义是「结果未知」——下游可能已经执行了。前端若显示「失败，请重试」，用户会重复下单。这条在《开发规范》§ 里写明「前端展示与重试策略完全不同」。

**③ `code === 0` 不等于「成功」**

《分阶段方案》§4.3 的转换规则：`PROCESSING` / `UNKNOWN` 也返回 `code = 0`，靠 `data.status` 标记处理中。理由写在文档里：结果未定时告诉用户「失败」会引发重复下单。

V1 下游固定成功，只有 `SUCCESS` 一行被真实走到，所以现在写 `if (code === 0) 成功` 不会出错；**V2 注入 timeout / PROCESSING 后就是错的**。前端的响应解析层从第一天就要把 `data.status` 纳入判定，否则 V2 要回头改每一个调用点。

## 2. 为什么必须换成有构建链的 Web 工程

现有 `index.html` + `console.html` 是两个单文件，各约 1100 / 800 行，纯手写 DOM 字符串拼接。它在「一个玩法、三个端点」时能用，往目标形态走会立刻碰到四堵墙：

| 问题 | 单文件方案 | 影响 |
| --- | --- | --- |
| 无路由 | 一个页面一个文件，跳转靠 `<a href>` | 20+ 页面时无法共享布局、登录态、面包屑 |
| 无组件复用 | 状态徽章、履约表格在两个文件里各写一遍 | 已经发生了：`pill()` / `badge` 两套实现 |
| 无类型 | 手写 `d.payStatus` 字符串 | 后端改字段名，前端运行时才报错 |
| 无契约同步 | 枚举取值手抄 | 后端加一个枚举值，前端静默漏渲染 |

其中「无类型」和「无契约同步」在这个项目里代价特别高——因为 §1.3 那三条约束全靠字符串比对实现，写错一个 `GRANT_SUCCESS` 不会报错，只会显示错的状态。**TypeScript + 从 Java 枚举镜像出的联合类型，是把这类错误从运行期挪到编译期的唯一手段。**

## 3. 技术选型

### 3.1 选型表

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | **Vue 3**（`<script setup>` + Composition API） | 后端团队为主的项目，Vue 的模板语法上手成本低于 JSX；中文生态与后台模板最完整 |
| 语言 | **TypeScript**（`strict: true`） | §1.3 三条约束靠类型系统兜底，非可选项 |
| 构建 | **Vite** | 开发期 proxy 直连 gateway，免 CORS；见 §3.2 版本约束 |
| 桌面端 UI | **Element Plus** | 运营/客服后台以表格 + 表单为主，Element Plus 的 `el-table` / `el-form` 覆盖度最高 |
| 移动端 UI | **Vant 4** | 终端用户页是 H5，Vant 是 Vue 3 移动端事实标准，自带收银台/列表/下拉刷新 |
| 状态管理 | **Pinia** | 仅用于跨页共享的少量状态（当前用户、活动上下文）；**订单状态一律回后端查，不进 store** |
| 请求层 | **axios** + 自建响应壳拦截器 | 拦截器是 §1.3 ②③ 的落地点，见 §6 |
| 路由 | **vue-router 4** | |
| Mock | **MSW**（Mock Service Worker） | 拦在网络层，业务代码不含 `if (mock)`；后端到位后删 handler 即可，业务代码零改动 |
| 校验 | **ESLint + Prettier + `vue-tsc --noEmit`** | 与后端 Spotless 对等的格式闸 |
| 测试 | **Vitest**（单元）+ 可选 Playwright（E2E） | 优先给 §1.3 的状态映射与响应解析写单测，那里是资损高发区 |

### 3.2 Node 版本约束（实测）

当前环境实测 `node v18.20.4` / `npm 10.7.0`，未安装 pnpm。

- **Vite 7 要求 Node ≥ 20**，当前版本装不上最新版。
- 两条路：**① 升级到 Node 20/22 LTS**（推荐，可用最新工具链）；**② 保持 Node 18 并锁定 Vite 5**。
- 包管理器用 **npm workspaces**（npm 10 已支持），不引入 pnpm，少一个环境前置。

建议走 ①。这个决定要写进《环境与依赖》，与 JDK 21 一起作为环境前置。

## 4. 仓库结构

### 4.1 放在哪、叫什么

前端作为**独立目录 `web/`** 放在仓库根，不作为 Maven module。

**目录名不用 `mp-` 前缀，这是刻意的**：`docs/check-docs.py` 会用正则 `mp-[a-z-]+/` 从《开发规范》《分阶段方案》里抽 module 名，与根 `pom.xml` 的 `<module>` 列表**双向**比对（文档漏了报错，文档多了也报错）。取名 `mp-web/` 会逼着同步改两份文档才能让 CI 过；取名 `web/` 则完全绕开这个闸，前端目录调整不牵动后端文档。

### 4.2 结构

```
web/
├── package.json                  # npm workspaces 根
├── tsconfig.base.json
├── apps/
│   ├── console/                  # 桌面端：运营 + 客服
│   │   └── src/
│   │       ├── layouts/          # 侧边栏 + 面包屑
│   │       ├── views/
│   │       │   ├── activity/     # 活动平台（玩法无关）
│   │       │   ├── benefit/      # 权益售卖专有
│   │       │   ├── fission/      # 裂变专有
│   │       │   └── ops/          # 任务、对账
│   │       └── router/
│   ├── mobile/                   # 移动端 H5：终端用户
│   │   └── src/views/{benefit,fission}/
│   └── devtools/                 # 调试台：迁移现有 console.html 的场景断言
├── packages/
│   ├── contracts/                # ★ 契约层：TS 类型 + 枚举镜像（见 §5）
│   ├── api/                      # 请求层：axios 实例 + 响应壳解析 + 各域 API 函数
│   ├── ui/                       # 跨 app 共享组件：状态徽章、三状态线、履约明细表
│   └── mocks/                     # MSW handlers（按域拆文件，删除即下线）
└── .env.development / .env.production
```

**为什么拆三个 app 而不是一个**：三类使用者的设备、UI 库、鉴权都不同——运营用桌面端 Element Plus、终端用户用移动端 Vant、调试台只给开发。塞进一个 app 会把两套 UI 库打进同一个 bundle。共享的部分（契约、请求、状态映射）沉到 `packages/`，这才是拆 workspace 的意义。

## 5. 契约层：前端最关键的一层

`packages/contracts` 是 §1.3 三条约束的落地处，也是整个前端最该被 review 的地方。

### 5.1 枚举镜像

从 `mp-common/enums` **逐个镜像**成 TS 联合类型，五个枚举**各自独立**：

```ts
export type PayStatus    = 'WAIT_PAY' | 'CLOSING' | 'PAY_SUCCESS' | 'PAY_FAILED' | 'CLOSED'
export type GrantStatus  = 'NOT_START' | 'GRANTING' | 'GRANT_SUCCESS' | 'GRANT_FAILED' | 'GRANT_UNKNOWN'
export type ItemGrantStatus = 'NOT_START' | 'GRANTING' | 'SUCCESS' | 'FAILED' | 'UNKNOWN'
export type RefundStatus = 'NONE' | 'REVOKING' | 'REVOKE_FAILED' | 'REFUNDING' | 'REFUND_SUCCESS' | 'REFUND_FAILED'
export type RetStatus    = 'SUCCESS' | 'FAIL' | 'PROCESSING' | 'UNKNOWN'
```

配套的展示映射也**按枚举分开**声明，用 `Record<PayStatus, Display>` 这类**全键必填**的类型——后端加一个枚举值时，前端编译立刻报缺键，而不是运行时静默显示空白。

**这里应该加一道机械化校验**：写一个脚本读 `mp-common/src/main/java/com/mp/common/enums/*.java`，抽出枚举常量与 TS 联合类型逐一比对，纳入前端 CI。理由和后端 `ShapeFreezeTest` 一样——这个约束每次改动都要重新成立，靠人核对必然漏。

### 5.2 展示态派生

主单不落 `biz_status`，展示态由三条子状态线**在前端派生**（后端 `QueryOrderResp` 注释已写明「三子状态各自返回，不合并」）。派生函数放 `contracts`，**只此一处**，三个 app 共用：

```ts
// 「支付成功且退款中」这类组合无法由单一枚举表达，故派生而非落库
export function deriveDisplayState(o: OrderView): DisplayState
```

## 6. 请求层：把 §1.3 ②③ 收在一处

`packages/api` 的 axios 响应拦截器是唯一解析响应壳的地方，业务代码不碰 `code`：

```ts
// 三类结果显式分开，调用方必须处理 unknown 分支
type ApiResult<T> =
  | { kind: 'ok';         data: T }
  | { kind: 'rejected';   code: number; message: string }   // 1xxx / 4xxx 终态失败
  | { kind: 'unknown';    code: number; message: string }   // 5xxx，或 code=0 但 data.status 为 PROCESSING/UNKNOWN
```

三点设计意图：

1. **`unknown` 独立成一类**，且类型上强制调用方处理。这样「显示失败」这个动作在 `unknown` 分支根本无法写出——从类型层面阻止 §1.3 ③ 那个错误。
2. `code === 0` 时**同时检查 `data.status`**，为 `PROCESSING` / `UNKNOWN` 时归入 `unknown`。V1 走不到，但接口从第一天就是对的，V2 无需改调用点。
3. `unknown` 分支统一走**查单收敛**：短退避 `1s→5s→30s`、长退避 `30s→2m→10m`（退避序列以《技术方案》为准，前端不自定）。收敛逻辑做成 `useConverge()` composable，不散落在页面里。

请求头统一带 `traceId`（后端 `TraceIdFilter` 已支持），排查时前后端日志可对齐。

## 8. Mock 策略

**契约先行**：先按 PRD 把 `[待]`/`[V2]`/`[V3]` 接口的 TS 类型写进 `contracts`，MSW handler 实现这批类型。后端实现时以这份类型为参照对齐字段名。

三条纪律：

1. **MSW 拦在网络层**，业务代码里不出现 `if (isMock)`。后端上线后删掉对应 handler 文件，业务代码零改动。
2. **Mock 页面必须挂可见的 `MOCK` 徽章**，并在页面内注明「接口未实现，数据为构造」。理由直白：不标记的 mock 页面会被当成已完成功能，最后在演示时暴露。
3. **Mock 只造结构，不造好看的假象**——异常分支、空态、`unknown` 态同样要 mock 出来，否则前端只在 happy path 上被验证过。

## 9. 开发与部署

### 9.1 开发期

Vite dev server（`:5173`）+ proxy 转发 `/api` 到 gateway（`:8080`）。同源代理，**不需要后端加 CORS 配置**——这条要守住，避免为了前端去改后端。

```ts
server: { proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } } }
```

### 9.2 产物去哪

近期建议：**前端不进 Maven 构建，`web/` 自带 npm 脚本独立构建**。

理由：
- CI 现有七道闸（commit 格式 / Spotless / compile / 单测 / 集成测试 / 文档一致性）**没有 Node 环境**。加 Node 步骤 + 前端 lint/test 是独立一件事，不该混在这次改动里。
- V1/V2 单进程阶段，把 `dist/` 拷进 `mp-gateway/.../static/` 即可由 gateway 静态托管，与现在一致。
- 若接进 Maven（`frontend-maven-plugin`），后端开发者每次 `mvn compile` 都要跑一遍 npm install，本地构建从秒级变分钟级。收益不抵成本。

对应地要做两件小事：`.gitignore` 加 `web/node_modules/`、`web/dist/`；`web/` 下自建 GitHub Actions workspace（或后续独立 job），跑 `vue-tsc --noEmit` + `eslint` + `vitest`。

V3 拆服务后前端独立部署（nginx / OSS + CDN），届时再从 gateway static 里摘出来。

## 10. 落地节奏

对齐后端阶段，不做超前实现。

| 阶段 | 交付 | 依赖 |
| --- | --- | --- |
| **F0** 骨架 | `web/` workspace、契约层（五枚举镜像 + 枚举比对脚本）、请求层（三态 `ApiResult`）、Console/Mobile 布局与路由骨架、Devtools 迁移完成 | 无，可立即做 |
| **F1** 权益售卖正向链路做真 | 商品页 / 收银台 / 结果页 / 订单详情接真实接口；订单列表与商品数据以 MOCK + localStorage 兜底并明确标记 | 现有 3 个端点 |
| **F2** 活动平台骨架 | 活动列表 / 创建 / 详情，`playConfig` 双玩法表单分叉，全 MOCK 但结构与 PRD 对齐 | 契约先行，不等后端 |
| **F3** 跟随 V2 | 预咨询试算、订单关闭、任务看板；**`unknown` 收敛在 UI 上真实可见**（V2 才有非 SUCCESS 分支可测） | V2 后端 |
| **F4** 跟随 V3 | 裂变全部页面、退款与回收、对账看板 | V3 后端 |

**F0 是这份方案里唯一「必须先做且不依赖任何后端」的部分**，也是把当前两个单文件换掉的实际动作。

## 11. 明确不做

| 不做项 | 理由 |
| --- | --- |
| 真实登录鉴权 | 后端无鉴权体系。用顶栏切 userId 模拟身份，与现状一致 |
| 权限控制（运营/客服分权） | PRD 有角色定义但后端无权限接口，等接口再做 |
| SSR / 微前端 | 三个 app 各自独立打包足够，没有 SEO 与巨型团队协作诉求 |
| 前端把玩法逻辑做厚 | 金额、库存、资格一律服务端为准。PRD §2.2：客户端传值仅作提示 |
| 前端缓存订单状态 | 状态一律回后端查。缓存会与「三子状态线独立推进」冲突 |
| 前端进 Maven / 现有 CI | 见 §9.2 |

## 12. 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **Mock 比例过高** | 按 PRD 页面清单算，F2 结束时 MOCK 页面仍占多数。存在「前端看着做完了，实际不能用」的观感风险 | 显式 MOCK 徽章 + 本文档 §7 的 [真]/[待] 标注即为对外口径 |
| **契约漂移** | 后端实现 `[待]` 接口时若不参照 `contracts` 的类型，两边字段名会分叉 | 枚举比对脚本纳入 CI；新接口以 `contracts` 类型作为联调基准 |
| **`code=0` 语义在 V2 变化** | 现有单文件页面按 `code===0` 判成功，V2 会静默出错 | F0 的请求层直接按三态实现，不留技术债 |
| **Node 版本** | 当前 Node 18 装不上最新 Vite | §3.2：升 Node 20 LTS，或锁 Vite 5 |
| **裂变页面无从验证** | `mp-fission` 是空模块，F4 之前裂变前端只能对着 PRD 写 | 裂变页面排在最后；F2 阶段只保证活动平台层的 `playType` 分叉结构正确 |
