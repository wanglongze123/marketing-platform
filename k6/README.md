# k6 压测

对应《分阶段方案》§5.7 退出标准 14、15。**不进 CI** —— 需要真实实例与 Redis，产出是数据记录而非通过/失败。

## 前置

```bash
brew install k6                      # 或 https://k6.io/docs/get-started/installation/
docker compose --profile v2 up -d    # MySQL + Redis
cd mp-gateway && mvn spring-boot:run
```

## 两个脚本压的不是同一件事

| 脚本 | 场景 | 验什么 |
| --- | --- | --- |
| `seckill.js` | 500 VU 抢 100 库存，**每 VU 独立幂等键** | 0 超卖（退出标准 14） |
| `contention.js` | 100 VU 抢 **10 个**幂等键 | 锁在 L3 负载侧的价值（退出标准 15） |

**为什么要两个**：`seckill.js` 里每个 VU 用独立的 `clientReqNo`，不存在幂等键竞争 —— 实测两组的 `duplicateKey` 与 `conditionalUpdateMiss` 都是 0，锁与不锁没有区别可比。锁减少的是「多个请求抢同一个业务对象」时走到 L3 的次数，那需要专门构造。

这一点是实施时实测发现的：先只写了 `seckill.js`，两组数据完全一样，看起来像「锁没用」，实际是**场景压不到锁该起作用的地方**。

## 跑法

### 退出标准 14：0 超卖

```bash
k6/run-seckill.sh locked 100
```

脚本会重置库存、清零计数、跑 k6、**查库校验**、读冲突指标。

> k6 的 `check` 只能证明「接口没报错」，证明不了「没超卖」—— 超卖的失效形态恰恰是全部成功。判据必须来自数据库，见脚本里的三条 SQL 与 `verify.sql`。

### 退出标准 15：去锁对照组

两轮之间需要**重启应用**切换锁开关：

```bash
# 开锁组
cd mp-gateway && mvn spring-boot:run
k6/run-seckill.sh locked 100

# 去锁组
mvn spring-boot:run -Dspring-boot.run.arguments=--mp.lock.enabled=false
k6/run-seckill.sh nolock 100
```

启动日志里应出现 `distributed lock DISABLED` —— 没有它就说明开关没生效，跑出来的「对照组」还是开锁组。

幂等竞争那轮手工跑：

```bash
curl -X DELETE localhost:8080/api/fault/contention   # 清零
k6 run k6/contention.js
curl localhost:8080/api/fault/contention             # 读数
```

## 实测结果（2026-08-06，本地 M 系列 Mac，MySQL 8 + Redis 7 容器）

### 秒杀：500 VU 抢 100

| 指标 | 开锁组 | 去锁组 |
| --- | --- | --- |
| 成功建单 | **100** | **100** |
| `1712` 库存不足 | 400 | 400 |
| 系统故障 | 0 | 0 |
| 库存终值 `locked / available` | 100 / **0** | 100 / **0** |
| 订单数与库存占用一致 | OK | OK |
| 同一幂等键重复建单 | 0 | 0 |
| P95 | 561ms | 545ms |

**正确性结果两组完全一致** —— 这正是退出标准 15 要证明的命题：删掉 Redisson，0 超卖不受影响。库存扣减靠的是 `UPDATE ... WHERE 余量 >= n` 的行锁串行化，从来就没有分布式锁参与（技术方案 §7.4）。

### 幂等键竞争：100 VU 抢 10 个键

| 指标 | 开锁组 | 去锁组 |
| --- | --- | --- |
| **`duplicateKey`（撞 `uk_idempotent`）** | **5** | **494** |
| `conditionalUpdateMiss` | 0 | 0 |
| 成功建单 | 13 | 500 |
| `5002` 抢不到锁 | 487 | 0 |
| 实际建出的单 | 8 个键 8 笔 | 10 个键 10 笔 |

**锁的价值在这里读出来了：走到唯一索引的次数从 494 降到 5，降幅 99%。** 而两组的正确性同样成立 —— 每个 `clientReqNo` 都只建出一笔单。

> **开锁组「成功建单 13」不是缺陷**：`tryLock` 不等待（技术方案 §6.3），抢不到直接返回 `5002` 交由上游重试。真实客户端会重试，压测脚本不重试，故计数偏低。**`5002` 不是失败**，是「稍后再来」。
>
> 同理，开锁组只建出 8 个键的单而非 10 个 —— 另两个键的请求全都撞在锁上了。这是 `waitTime=0` 的预期行为。

### 这组数据说明什么

技术方案 §6.1 的论断得到实证：

> **L2 是性能优化，L3 才是正确性兜底。**

- 去掉锁，**正确性一点没变**（0 超卖、幂等唯一）
- 去掉锁，**L3 的负载涨了 99 倍**（494 vs 5 次唯一索引冲突）

若哪天去锁组的正确性结果变了，说明代码里有地方错把锁当成了正确性依据 —— 锁会因超时、宕机、时钟漂移而失效，唯一索引不会。CI 里的 `LockDisabledCorrectnessIT` 就是为守住这一点而存在。

## 已知局限

- **单机压测**：应用、MySQL、Redis、k6 都在同一台机器上，P95 含本地资源争用，不代表生产 RT。技术方案 §8.6 要求的多实例与百万级数据量属 V3。
- **不重试**：真实客户端收到 `5002` 会重试，脚本不会。故开锁组的「成功数」低于实际可达值。
- **只压了权益售卖**：裂变链路属 V3。
